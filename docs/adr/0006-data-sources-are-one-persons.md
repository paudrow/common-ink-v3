# 6. A data source is one person's, read live, and a note holds only a reference

Status: accepted by the owner of #17 on 2026-10-11, without the maintainer. Issue 1 named "data sources belonging to the member who connected them" as a candidate ADR and left the rest open; overrule any of it here.

## Context

A member's Google Calendar and Google Contacts are the first data sources (issue 1, stories 70 to 75). They differ from everything else in Common Ink in three ways. They are not the workspace's: an admin has no claim on a member's calendar. They are not Common Ink's: the records live at Google, and reading them needs a token that can also change them. And a note that mentions one is read by people the record doesn't belong to.

## Decision

**Whose it is.** A data source belongs to a person, in no workspace. Its operations (`source.list`, `event.list`, `event.update`, `contact.list`, `record.refer`, `record.read`) take no person: `src/core/sources.ts` asks for the data sources of whoever performs the operation, or of the member an agent acts for, and there is no argument by which anyone else's could be named. They need only `view` of the workspace they are asked in, so a viewer and a guest have their own calendar too. Removing a member from a workspace, or their leaving, does nothing to their data sources: they are still that person's in every other workspace. There is no operation that deletes a person, so nothing else ends a connection but the person.

**Read live, kept nowhere.** No event or contact is stored. Every read goes to where the record is kept, as the member, and comes back through the Worker to that member alone. What is stored is the connection (`source_connections`) and the references notes hold (`source_refs`). The cost is a request to Google for every view, and no offline reading. The gain is that there is no copy to leak, to go stale, or to delete on disconnect.

**A small interface.** A `DataSource` (`src/core/sources.ts`) is a calendar or contacts source with `list`, `get`, and for a source that takes changes, `update`. Whether a data source is read-only is not a flag beside it: it is read-only when it has no `update`, so the core cannot send a change to one. The core is handed `Sources`, which answers for one person at a time. The Worker supplies it (`src/worker/sources/index.ts`) from providers: Google's two, and a sample calendar and contacts where dev sign-in is on. The views and the embeds are drawn from what `source.list` answers and name no provider.

**Changing an event.** The core reads the event first and refuses before anything is sent when the data source has no `update`, or the event is not `editable`: a calendar the member can only read (`calendarList` `accessRole` below `writer`), an event they don't organize and whose guests can't modify it, or one of Google's own kinds (birthdays, events from Gmail). The change goes to Google as `events.patch` with `If-Match` set to the etag the member read, so a change made from a stale reading is refused (412, `conflict`) and never overwrites a newer one. It is made with the member's own token, so Google records it as theirs. It is not a change in Common Ink's history and can't be reverted here.

**Tokens.** This is the part that must not go wrong.

| Question | Choice |
|---|---|
| Where are they? | `source_connections`, one row per person per provider: access token, refresh token, expiry, the scopes agreed to. |
| How are they kept? | Sealed in the Worker before they reach D1 (`src/worker/vault.ts`): AES-256-GCM, a random 96-bit nonce per value, under a key derived by HKDF-SHA-256 from the `TOKEN_KEY` secret. Each value is bound, as additional data, to its person, provider and column, so a value copied to another row opens as nothing. D1 never holds the key. |
| What may read them? | Only `src/worker/sources/google.ts`, to send them to Google's own hosts in an `Authorization` header. No operation answers one, `/api/me` doesn't, nothing logs one, and errors carry only a status. |
| What without `TOKEN_KEY`? | Nothing is kept, and Google's data sources are not offered at all. Sign-in works as before. A key under 32 characters counts as none. Previews have no Google client, so they need no key. `npm run dev` adds one to `.dev.vars`. |
| What sign-in asks for | Who the person is, and the calendar and contacts scopes only where there is a `TOKEN_KEY` to keep the answer with. A deployment that would throw the grant away doesn't put it on the consent screen. |
| A grant that isn't kept | Revoked at Google at once, when it reaches a data scope: the person isn't on `ALLOWED_EMAILS` (which is only known after the exchange), Google answered for another account or to someone since signed out, there is no key, or it covers no data source in full. A token that only says who the person is is left to lapse. |
| Getting a refresh token | Sign-in asks with `access_type=offline`. Google hands a refresh token to an account only the first time it agrees, or when asked to show what is agreed to. So when a sign-in agrees to a data source and no refresh token is held, the browser is sent once more to Google with `prompt=consent`. |
| Renewing | An access token is renewed a minute before it lapses, and once when Google answers 401, and the request is then sent once more and no more. However many requests one operation has in flight, they share the one renewal. The renewed token is written by an `UPDATE` of the row that still holds the very refresh token the renewal used: a connection ended meanwhile, or ended and made again, takes nothing, and the token is not used. Renewing never creates a connection and never changes the scopes, the account, or whether a data source needs reconnecting. Only agreeing at Google does. |
| When Google stops taking them | `invalid_grant` on renewal, or 401 after it: both tokens are deleted at once and the connection is marked, so both data sources read `needs_reconnect`. A 403 for insufficient scope marks only the data source that was refused. A rate limit, a 5xx or a timeout marks nothing: the operation fails as `unavailable`. |
| Rotating the key | Changing `TOKEN_KEY` leaves every stored token unopenable, which reads as `needs_reconnect`: each member connects again. The sealed form carries a version (`v1.`) for a later scheme that keeps two keys. |
| Disconnect | `source.disconnect`, the member's own and never an agent's. The row is deleted first, then Google's revoke endpoint is called with the refresh token. If Google doesn't answer, the tokens are gone from here all the same, and the member can still remove the app in their Google account. Google revokes a grant whole, so both data sources go together, and the next sign-in asks again. |
| Sign-out | Leaves the connection. A session is one browser's; the connection is the person's, as their agents' tokens are. Signing out of a laptop must not cut off the calendar on a phone or for an agent. |

**Agreeing is explicit and repeatable.** Google lets a person untick each thing asked for. A data source is `connected` only while every scope it needs was agreed to (`SOURCE_SCOPES` in `src/worker/google.ts`), `needs_reconnect` when it was and Google has stopped answering, and `not_connected` otherwise. `source.connect` answers a path, `/auth/google/connect?source=…`, that asks for that one data source's scopes on top of what was agreed before (`include_granted_scopes`), as the account already signed in (`login_hint`), with the consent screen shown. This is the incremental path: the one way to add a data source after sign-in, to take one back up after unticking it, and the only way at all where sign-in asked for none. What comes back is kept only if it is for the same email as the member's, in the browser that asked, for the person who asked. A token that opens no data source is not kept.

**Outbound requests.** The Worker fetches on a member's behalf, so where it fetches must not be up to a member, a note or an agent. Every address is built in `src/worker/sources/google.ts` from two constants, `https://www.googleapis.com/calendar/v3` and `https://people.googleapis.com/v1`, and checked against those origins as it is sent. A record's id is only ever one percent-encoded path segment (a contact's must match `people/<letters and digits>`), a redirect is not followed, and no operation takes an address.

**A reference in a note.** A note references a record as an inline embed, `::event{<ref> <label>}` or `::contact{<ref> <label>}`.

- It is an embed and not a `[[link]]`: a link's target is a note id or a title, and `[[event:…]]` would be looked up as a title and refused by `note.write`. The embed form already means "a plugin draws this", and its name says the kind without a sigil.
- `<ref>` is twelve characters that say nothing. `record.refer` makes it and keeps beside the person which record it stands for (`source_refs`). Google's own ids are not written into notes: a calendar's id is usually an email address, sometimes a colleague's.
- `record.read` follows a ref only for the person who made it. For anyone else it answers exactly as for a ref that never existed. So another member who opens the note is told nothing of the record and can ask nothing of it.
- `<label>` is plain text in the note: the event's title or the contact's name when the reference was made. Every reader of the note sees it, in gray, the way #19 will show a mentioned contact's name. That includes whoever opens a link to the note, whose page draws the label and asks nothing. It is the member's to edit or remove, and it is never updated behind them. The owner is drawn the record's details as they are now; the label is what is left when there is no record to read.

**Agents.** A member's agent reads their events and contacts and changes their events, each through its own tool, and a read-only token changes nothing. An agent is the member's own and "can do anything the UI can, and nothing more than its member can". The risk is real: an agent reads notes other people wrote, and one that was talked into it could copy a member's contacts into a shared note. That is the same risk it already carries for the member's private notes, and the tools say so. It is not given `source.connect` or `source.disconnect`.

**Without Google.** Someone who signed in by dev sign-in has no Google account behind them. Where dev sign-in is on (this machine and Previews, by the same check as `/auth/dev`), a sample calendar and contacts can be connected, so the pages, references and changes can be tried and tested. Production cannot offer it.

## Consequences

- `TOKEN_KEY` must exist as a GitHub Actions secret before the deploy that should offer Google's data sources. Until then they are simply absent.
- Members who signed in before this see Google's consent screen once more at their next sign-in, when a data source was agreed to and no refresh token is held.
- Every view of the calendar is a request to Google per calendar shown there, up to 20 calendars and 1,000 events each per read, over a span of at most 400 days, and up to 5,000 contacts. Google's `syncToken` is not used, so there is no 410 to handle; a cache would need it and would need deleting on disconnect.
- The dashboard (#23) reads "events still ahead today" with `event.list` over the member's day and their zone. Mentions (#19) list the member's own contacts with `contact.list`.
- A reference outlives its note and is not removed with it: it is a handle beside the person, not part of the note, so `src/core/purge.ts` names no table of this.
- A second provider is a second entry in `sourcesFor`. A second kind of data source is a new member of `DataSource` and its own operations.
