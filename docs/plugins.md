# Plugins

Most of the web app is plugins. The core is the workspace's data, the editor for one note, focus, the inspector's frame, and the plugin host. The sidebar, folder tree, a folder's list of notes, tabs and splits, command palette, quick open, History, Agents, Members, and the rest are built-in plugins in `src/web/plugins/`.

This document has two readers. Someone writing a plugin of their own for a workspace reads [Third-party plugins](#third-party-plugins): that is the whole of what such a plugin is and can do. Everything before it is for Common Ink's own built-in plugins, which run in the app's page and are trusted.

The plugin API is one module, `src/web/plugin-api.ts`. Its doc comments are the reference. A plugin imports that module and nothing else from the app. `test/core/plugin-boundary.test.ts` fails when a file under `src/web/plugins/` breaks that rule.

## A plugin

A plugin is a value with an id, a name, an `activate` function, and optionally what it says of itself and the `settings` it declares. The host calls `activate` when the plugin is turned on and hands it a `PluginHost`. Everything the plugin registers is taken back out when it is turned off. A plugin that starts anything else, such as a timer, returns a function from `activate` that stops it.

```tsx
import type { Plugin } from "../plugin-api.ts";

export const wordCount: Plugin = {
  id: "word-count",
  name: "Word count",
  description: "The open note's word count and reading time, in the bottom bar.",
  icon: "text",
  settings: {
    unit: { type: "string", default: "words", enum: ["words", "characters"], title: "Count", description: "What the inspector counts." },
  },
  activate(host) {
    host.commands.register({
      id: "wordCount.open",
      title: "Go to the longest note",
      keys: ["mod+alt+l"],
      run() {
        const { notes, openNote } = host.app();
        const longest = [...(notes ?? [])].sort((a, b) => b.snippet.length - a.snippet.length)[0];
        if (longest) openNote(longest.id);
      },
    });

    host.views.register("inspector", {
      id: "words",
      label: "Words",
      icon: "info",
      for: ["note"],
      component: ({ about }) => {
        if (about.kind !== "note") return null;
        const unit = host.settings.get<string>("unit");
        const count = unit === "words" ? about.note.snippet.split(/\s+/).filter(Boolean).length : about.note.snippet.length;
        return <p>{count} {unit} in the first lines</p>;
      },
    });

    host.embeds.register({
      name: "today",
      title: "Today's date",
      render(el) {
        el.textContent = new Date().toLocaleDateString();
      },
    });
  },
};
```

Add it to `BUILT_INS` in `src/web/plugins/index.ts`. Its place in that list is its place in the palette, the inspector's bar, and every other slot.

## What a plugin is handed

- `host.commands` registers commands, lists every command, and runs one by id. A command's `keys` are its default chords, and its `group` the heading the keyboard shortcuts list it under. `host.commands.list()` says of each command every chord that runs it now (`keys`, as a person reads them) and the first of them (`shortcut`), with the member's keybindings in place of its own.
- `host.views.register(slot, view)` puts a view in a slot. The slots are `column`, `section`, `editor`, `folder`, `inspector`, `page`, `bar`, `overlay`, `mark`, `tool`, `notice`, and `settings`. A `settings` view is a section of Settings that holds no setting, listed after the app's own and before Account at `/settings/<id>` under its `label`, which a search of the settings never finds: the Tags plugin's list of every tag. A page gets a `go.<id>` command, and its `order` places its link among the others in its nav: lower first, and pages with none after them. An inspector view gets an `inspector.<id>` command. A page is also shown at every address under its path, so the Tags page at `/tags` is the page at `/tags/work` too, and reads which from `app.path`. A page registered at exactly that address wins. A page is opened in the editor area as a note is, which with Tabs and splits on is in a tab, and it does nothing for that: see [Pages are tabs](#pages-are-tabs). A page with `home: true` is where the app goes from `/` when the editor area has nothing to return to, opened as any page is: the Dashboard.
- `host.embeds` registers an embed, drawn wherever a note says `::name{config}`, or `:::name{config}` … `:::` for a block embed. `host.embeds.list()` is every embed that is on, as a menu would offer them. It also registers an address embed (`{ name, title, claims, below }`), which has no syntax and is in no menu: a web address alone on a line that it claims is shown below that line. See "Below the line".
- `host.completions` registers a completion: a list offered at the cursor while the member types after a trigger, such as the insert menu on `/`.
- `host.editorExtensions` registers an editor extension, added to the editor of every note. It is a value, or a function of the editor that is told its note.
- `host.onNavigate(listener)` calls the listener each time the app arrives at an address.
- `host.onNotes(listener)` calls the listener each time the notes the member can see change: one made, renamed, moved, or changed by anyone. `host.app().notes` then holds them as they are. It is how something drawn from another note's title, such as a link, knows to draw itself again.
- `host.report(error)` says on the Plugins page that the plugin is on and something it is for didn't work.
- `host.app()` is the app as it is now: the open note, the notes and folders, and what can be done about them. A view is handed the same thing as its `app` prop.
- `app.path` is the address the app is at and `app.query` its query, such as `?q=plan`, which a page reads with `URLSearchParams`. `app.go(path)` goes to an address, query included. With `replace: true` it takes the place of the current entry in the browser's history, which is how the Search page keeps what is typed in its address without Back retracing each letter.
- `host.perform(op)` performs a workspace operation as the member. A refusal rejects with an `Error` whose `message` is the server's reason and whose `code` is the kind of refusal, such as `conflict` or `forbidden`. The operations are the ones in `src/core/protocol.ts`, except the two on settings. It also refuses every operation that changes who is in the workspace or reads its invites; `member.list` goes through, and tells an admin the members' emails and anyone else their names and roles alone. A plugin that isn't Common Ink's own is refused the member's data sources as well: `source.*`, `event.*`, `contact.*` and `record.*`. It is refused the member's pins and their last visit too: `pin.*` and `visit.*`.
- `host.settings` reads the plugin's own options, and changes one it declares `remembered`.
- `host.storage` keeps JSON for this plugin, in this browser, for this workspace and this member.
- `host.agents` lists, connects, and disconnects the member's agents.
- `host.members` invites by email, sets a member's role, signs a member out everywhere, removes a member, leaves, and lists and revokes invites, as the member. The server lets only an admin do all but leave and signing themself out. It is a capability of its own, apart from `host.perform`, so that it can be given to the Members plugin and to no other. After a change that may be to the member themself, `app.reloadWorkspaces()` has the app read again which workspaces they are in and their role in each. A change of role draws the app again from the start, since a plugin is handed the role when it starts.
- `app.toggleOverlay(id, state)` opens an overlay and hands it `state`, which the overlay's view is given as a prop. The Share dialog is the overlay `share`, handed `{ noteId }` or `{ folderId }`, so any plugin can open it while the Sharing plugin is on (its command `sharing.share` is then listed).
- `app.canEdit` says whether the member may change something in the workspace. Whether they may change one note is that note's `access`, which is what an editor, the history controls, and the Info tab go by. `app.canCreateNote` says whether `app.createNote()` can make a note where it would put one, and `app.createNote()` rejects with the server's reason when it is refused. `app.folderId` is `SHARED_WITH_ME` while the list of the notes shared with a guest whose folders they can't see is in front, or one of those notes is, and such a note's `folderId` is null.
- `host.sharing` reads and changes who a note or a folder is shared with, as the member: `of(on)` answers the `Sharing` of one note or folder, `grant(on, to, access)` shares it with a person or changes what they have, where `to` is an email or, for a member of the workspace whose email only an admin is told, `{ memberId }`, `link(on, kind | null)` sets or removes its link, `revoke(grantId)` takes a grant back, `setPrivate(noteId, private)` makes a note private or stops it and answers how many grants and links other people had put on it, which go as it becomes private, and `all()` lists every grant for an admin. `on` is `{ noteId }` or `{ folderId }`. The server decides who may do each, and a view shows only what its answers say: `Sharing.canShare`, `Sharing.note.canSetPrivate`, and a note's `access`. It is a capability of its own, apart from `host.perform`, which refuses `grant.*`, `note.setPrivate`, and `shared.*`.
- `host.sharing` takes an upload too: `on` may be `{ uploadId }` for `of`, `grant` and `revoke`, and `setPrivate({ uploadId }, private)` makes an upload private as `setPrivate(noteId, private)` does a note. `link` is refused for one by the server: an upload has no link of its own, and only a link on a folder opens the uploads in it. The Share dialog takes `{ uploadId, name }` and leaves its Link section out. `host.perform` refuses `upload.setPrivate`.
- `host.uploads` is the workspace's uploads as notes refer to them, and their bytes. `referred(id)` is what the app was last told of an upload, by the read of a note that refers to it (`note.read`'s and `shared.read`'s `uploads`) or by `learn`: its name, type, kind, size and state, `null` for one that isn't there or that the reader can't see, which nothing tells apart, and `undefined` for one nothing has been said of. `onReferred(listener)` hears when any of that changes. `learn(uploads)` tells the app what an upload is now, after an operation that made, changed or removed it, so every note showing it follows. `address(id)` is where its bytes are asked for, good only for whoever is looking: the member's session in the app, and on a link's page the link, never the workspace. `tabAddress(id)` is where it opens in a tab of its own: the app's address with `?open=tab`, which sends a PDF on to the site kept for files, or null where the server has none (`FILE_ORIGIN`) and on a link's page. `bytes(id, upTo)` is the first `upTo` bytes of an upload, asked for at `address(id)` with a `Range` header and answered the same way, on a link's page by the link, and rejects with the server's refusal, `not_found` for one the member can't see: the uploads plugin reads text files and PDFs with it for their previews, since no plugin may `fetch`. `send(file, { name, folderId, private }, onProgress, onStarted)` sends a file of up to 25 GB as the member and rejects with the server's reason: one over 8 MB goes in parts, several at once, sent again to a fresh address when one fails and given up on (and aborted) only after rounds that store nothing, and `onStarted({ id, kind })` is told its id, and the kind its name says, as soon as it has one. `fileClass({ type, name })` from the plugin API says what a person calls a file (image, video, audio, pdf, text or other, `FILE_CLASSES`, with text told by `TEXT_ENDINGS`), the same classification `type:` finds uploads by. `upload.list` takes a `query` in the query language and answers a page of uploads, each with its `uses`, and `next`, the `after` of the page after, as every list that pages does; `upload.place { id, noteId }` is asked before an existing upload's embed is written into a note. Listing, reading, moving, archiving, trashing, restoring and purging are `host.perform`'s `upload.*` operations, which, like `host.uploads` itself, only Common Ink's own plugins are given. `upload.create`, `upload.open` and the steps of a file sent in parts (`upload.start`, `upload.resume`, `upload.part`, `upload.finish`, `upload.abort`) are refused to every plugin as operations: the bytes go through `send`, `address` and `bytes`. `openUpload(host, upload)` in `plugins/uploads/opening.ts` is the one place that says how a file opens (a preview over the app, the app's `/file/<id>` page, or a download), for a chip and for the Uploads page alike, and `previewUpload` shows any upload larger over the app.
- `app.readMarkdown(text)` draws markdown that is not a note, such as an uploaded file's, to be read: as a link's page draws a note (`useDrawing` in `src/web/drawingHost.ts`), with the drawing plugins and nothing of the workspace behind them, so a link to a note or an upload in it goes nowhere and HTML in it runs only when Run is pressed, whatever the member's `html.run` says.

- `app.notes` is every note the member can see that isn't in Trash: the live ones and the archived ones, told apart by `state`. A listing leaves the archived ones out unless the member asked for them, with a toggle of its own that starts off; `listable(notes, includeArchived)` in `plugins/lib/listable.ts` is that rule. `app.trashed` is the notes in Trash, which no listing shows: they are there so a tab or a link can say what one is. `app.note`, the open note, may be in either. A note's state is not a change to the note, so its revision stays: anything that reads again "when a note changes" compares `state` as well.
- `app.left(noteId)` is for an editor area: it says a note is in none of its tabs now. The Tabs plugin calls it when a tab on a note is closed or another takes its place. The app then sends what was typed in it and asks the server to discard it (`note.discard`), which removes outright, not to Trash, a note nobody ever wrote in, one that has never had anything in it but spaces or a lone `#`, and refuses any other and any that is open somewhere else. Switching tabs is not leaving a note. Without an editor area, a note is left when the address goes elsewhere.
- `app.noteChanged(note)` tells the app a note as it is now, after an operation that answered with it: its text, its folder, or its state. A folder's list, quick open, open tabs and links follow at once. Folder counts are the server's, so `app.refresh()` after a change of state.
- What the editor area has in front is `app.opened`: `{ kind: "note", id }`, or `{ kind: "folder", id }` for a folder's list of notes, where `id` is a folder's id, `ALL_NOTES` for every note, or `SHARED_WITH_ME` for the notes shared with a guest who can't see their folders. `app.noteId` and `app.note` are the note's when a note is in front and null otherwise. `app.folderId` is the folder in front: the one whose list is open, or the folder of the note in front, which is what the folder tree marks. `app.openFolder(id, { preview })` opens a folder's list (a preview unless said, which gives way to the next thing previewed), `app.folderPath(id)` is its address (`/folder/<id>`, `/folder/all`), and `folderTitle(folders, id)` is what it is called. `app.openNote(id, { background: true })` opens a note in a tab of its own without leaving what is in front. There is one preview in the window at most, so a note previewed takes the place of whatever preview is there, a folder's list among them. `app.createNote(folderId?)` puts the note in that folder when it is one, otherwise in the folder in front, otherwise in Unsorted, and answers its id. With `{ open: false }` it makes the note without opening it, for whoever opens it somewhere of their own.
- **The `folder` slot** draws a folder's list of notes wherever a folder is open: in a tab when the tabs plugin is on, alone at the folder's address when it is off. It is handed `folderId`, which may name no folder the member can see, and `readNote(noteId)`, which draws a note's text to be read and not changed, as its editor draws it, at its full height. The last view registered is used. With none, the core lists the folder's notes by title. A page that lists notes the same way draws them with `app.readNote(noteId)`, which is the same function: the Search page is the note list's `NoteFinder` (`plugins/noteList.tsx`) of every note, with its view kept in the address where a folder's tab keeps its own for as long as the app is open. With no `editor` view, `/` lists every note, and the command `notes.all` opens that list from anywhere, so there is a way to a note whatever is turned off. No page can be registered at `/folder` or under it.
- **The `editor` slot** is asked to open what the app would otherwise go to: `open(tab, { preview, background })` with a note, a folder's list or a page, and it calls `app.show(tab)` with what ends up in front. `returnsTo()` is what it has in front whatever the address says, or null with nothing open: the app asks it at `/`, to leave the address to that tab, and at an address that names no page, to know a tab kept there. It is handed `renderNote`, `renderFolder` and `renderPage` to draw what its tabs hold, `empty` to draw where nothing is open (a line saying to pick a note). `renderNote(id, { focus: true, onFocused })` has the note's editor take the cursor once the note is there, which is how a note moved to another group, where its editor is drawn anew, keeps the cursor: the Tabs plugin asks for it after a split or a send, and puts the cursor on the tab itself where what moved is a folder's list or a page. There are no buttons for the sidebar and the inspector to place: their edges and their commands open and close them. Focus is the editor area's own to offer: it draws a button for it wherever something can fill the window (the Tabs plugin puts one at the right end of every group's tab row), reads `app.focus`, and calls `app.setFocus(on)`. While `app.focus` is true it puts `data-focus-mode` on its `.groups` element and `data-front` on the one `.group` to show, and the app's styles lay that group over the window and hide the rest. A change that moves a tab to another group (a split, a send) calls `app.setFocus(false)`, so the member sees where it went. An editor area with tabs also has `tabs()`, every tab open as `{ opened, pane }`, pane by pane in reading order (the first pane is 1), which `app.openTabs()` answers with; without it `app.openTabs()` is what is in front. An editor area that can show two things at once also has `split(tab, side)`, which opens a note, a folder's list or a page in a part of its own, right of or under what is in front, and keeps it there. `app.openBeside(tab, side)` goes to it, and is null where there is no such editor area.
- **The `column` slot and the closed sidebar.** There are three things a member opens and closes, each kept in the browser: the sidebar (`view.toggleSidebar`, `mod+\`), the inspector's panel (`view.toggleInspector`, and `inspector.<id>` for each panel) and focus (`view.toggleFocus`, `mod+.`). In focus what is in front in the editor area fills the window. At an address with nothing there no group is drawn, so nothing is hidden either: the window is whole until something is in front again. Nothing is taken out of the page for it: the `column` view, the inspector's panel and its bar stay drawn, out of sight (`visibility: hidden`), so leaving focus puts everything back as it was. A `column` view is always drawn. While `app.sidebarOpen` is false it draws itself as a narrow bar of icons, `<nav class="rail">`, for what it lists when open. The app draws the edge beside it, which the member drags or presses to fold the sidebar and open it (and the same for the inspector's panel, when it is pinned), so the view needs no button for that; `app.toggleSidebar()` is there if it wants one. From its bar the view can show a section over the page without opening: `app.sectionsOpening(opened, id)` draws that one of `app.sections` and calls `opened` each time it opens a note, a folder's list or a page, which is when the Sidebar plugin's picker goes away. A section needs to do nothing for this: it calls `app.openFolder` and the rest as it always does. A `section` view says what stands for it there with `label` and `icon`, as Folders and Tags do: `app.sectionNames` is those, in order, and the bar has an icon for each, which shows that section over the page. There is no `rail` slot any more: only the Sidebar plugin used it, for icons once shown down the left edge, and the closed bar is the sidebar's own to draw.
- **A page's link drags and splits by itself.** The Sidebar plugin draws every page that has a `nav` with one component, `PageLink`, in the open sidebar, under More, and in the closed bar. That link is dragged into the editor area as a tab is, to the middle of a group or to one of its edges, and its menu has "Open in a split right" and "Open in a split down" wherever `app.openBeside` is there. A plugin that registers a page does nothing for either. A page registered `transient` with the function that finds where it leads, as Today is, drops that place instead: its link is dragged, and the Tabs plugin awaits the function where it is dropped. A view of its own that wants the same spreads `draggableAs(what)` on the element, as a folder's row, a tag, a crumb and a note's card do, and calls `app.openBeside` from its menu. `what` is an `Opened`, or `{ kind: "new note", folderId }`, which the Tabs plugin makes with `app.createNote(folderId, { open: false })` and opens where it is dropped, so New note drags too. Every drag to the editor area goes through it, so all of them land the same way: an edge splits, the middle adds a tab and the tab bar puts it at the gap. It sets no cursor and no drag image of its own: what is dragged is clicked too, and keeps its pointer, and the browser draws it as it is. `carried` and `carriesTab` are for the side that takes the drop. A plain link to an address of the app's own drags too, with nothing spread on it, as a note's link on the Dashboard or in a page's text does: the Tabs plugin reads the address from the drag (`linkIn`, from `text/uri-list`, or `text/plain` when the drag began on a link) as it starts in the window, takes it only where going there opens something, and drops what going there opens (`openedAt(address, app.pages)`: a note, a folder's list, or the page it names, at that address). A link to another site, one to an address that opens nothing, and one dragged in from outside the window are left to whatever is under it, as before: a note writes it in. A link inside a plugin's frame, as Backlinks' are, is a real link to the note's address, but Chrome takes no drop from a frame of another site into the page around it, so it drags only to the browser's own address bar and tabs. A tag drawn in a note and a todo's row aren't dragged, as that would fight selecting their text.
- **The `bar` slot: the bottom bar.** One thin line along the foot of the window, 26px tall, for small things to glance at, as an editor's status bar is. Any plugin puts an item in it: `host.views.register("bar", { id, component, side, order })`. `side` is `"left"` (the default) or `"right"`, the end it sits at. `order` places it among the others at that end, lowest first, 0 unless said; items of one order stay in the order of their plugins. The component is handed `app` like any view and draws its content, text or a button, which the app sets in the bar. One that returns nothing takes no room. The bar is drawn while any plugin has an item in it, whether or not the item has something to say, so nothing above it moves as items come and go, and with no item registered there is no bar. In focus it is out of sight; an item registered with `live: true`, something that changes as it is watched such as a running timer (Note clocks, Quick timer, an upload being sent), is drawn in focus at the foot of the note instead, on one quiet line with vim's mode and whether the note is saved. A count is not live. Word count (`word-count`) is the built-in that uses it: at the right end, the words and reading time of the note in front, or how many of its words are selected.
- **`reline(lines, change, before, by)`** is exported for a view that marks a note's lines by who wrote them, as `note.blame` answers. Given one value for each line of the note `before` (none for a note with no text), it gives back one for each line after the CodeMirror `change`: a line the change writes or edits is `by`, and every other line keeps its value. It reads lines as History does, so a line put in after another is not an edit of that one. Blame mode keeps its bars true to typing with it between reads of `note.blame`.
- **`useOpenNote(noteId)`** is a hook the API exports for a view that says something of a note being written, such as a bar item about `app.noteId`. It answers with `{ text, selected }` as the note's editor holds them now, typing not yet saved included, and draws the view again as either changes. It is null when the note isn't open in an editor. A note open in several editors at once, as another editor area may have it, is read from the one the member was last in, and from another when that one closes. `text` is the same string until the note changes, so a view can count it once and not again as the caret moves. Nothing is asked of the server.
- **The `inspector` slot.** The inspector is a narrow bar of icons at the right of the window, one for each view in the slot, and a panel that one of them shows. The bar is the same whatever is in front: an icon is never added or taken away by what is open, and the bar never closes by itself. An icon shows its panel over the page, where it stays until the member presses elsewhere or presses Escape; the same icon again closes it. The panel's header has one control, a pin, which puts the panel beside the page, where it stays. Which panel, whether it shows and whether it is pinned are kept in the browser for each member as they last had them (`src/web/inspectorState.ts` is the whole rule, as one reducer); a member's first time has no panel open and none pinned. In focus neither the bar nor a panel shows. `badge(app)` flags a view's icon, as History flags changes the member hasn't seen. Each view gets a command, `inspector.<id>`, titled "Toggle <label> panel", which does what its icon does and takes a key in Settings as any command does; `app.togglePanel(id)` does the same from a plugin.
- **What a panel is about.** A panel is about what the editor area has in front, which the view's component is handed as `about` (`About` in the API): `{ kind: "note", note }` for a note; `{ kind: "folder", folderId, name, notes }` for a folder's list; `{ kind: "notes", label, notes }` for the notes a page says it is showing. A view says which of these kinds it has something to show `for`, as a list: History and Note info are `for: ["note", "folder", "notes"]`, and Backlinks is `for: ["note"]`. With anything else in front the component is not drawn, and the panel says "Nothing to show for this view". That line is the inspector's to draw, so a view never draws an empty state of its own for a kind it does not cover.
- **A page says what it is showing.** <a id="a-page-says-what-it-is-showing"></a>A page is in front as a note is, and the inspector cannot know what a page has on it. So the page says: `useInspected(app, showing)` from the plugin API, called in the page's component with the `app` it was drawn with.

  ```tsx
  function Todos({ app }: ViewProps) {
    const open = useOpenTodos();
    // The notes these todos are in. History is then their history, and Info counts them.
    useInspected(app, { kind: "notes", label: "Open todos", noteIds: [...new Set(open.map((t) => t.noteId))] });
    return <TodoList todos={open} />;
  }
  ```

  `showing` is `{ kind: "notes", label, noteIds }` for a set of notes under a name the member would know them by (the notes a search found, the notes with open todos, the notes that mention a contact), `{ kind: "note", noteId }` where the page is about one note (a contact's own note, the one result picked), or `null` while it has nothing to say. It can change as often as the page does: the hook tells the inspector when its value changes, by value, and takes it back when the page is closed. Ids of notes the member can't see, or that are gone, are left out. A page in a split that is not in front has said what it shows all the same, and the inspector is about it once it is in front. A page that never calls it is nothing to be about, and every panel says "Nothing to show for this view" there. Outside a page `app.inspect` does nothing. On main two things use the seam: a folder's list, which the app itself knows the notes of, and the History page, which is about the notes whose changes are ticked: one note is that note, so Info shows where it lives and its address, and with nothing ticked the page says nothing, since its own list is all there is to show. The Todos page calls it with the notes its listed todos are in, labelled "Todos". The Search and Contacts pages are to call it with the notes they list.
- **Pages are tabs.** <a id="pages-are-tabs"></a>`Opened`, what the editor area has in front and what `app.opened`, `app.show` and the `editor` slot's `open` speak of, has a third kind: `{ kind: "page", id, path }`, where `id` is the page's id and `path` the address it is at. The core makes it from the address, so `app.go("/search")`, a link, the `go.<id>` command and Back all open or turn to the page's tab, and no plugin registers anything more than its `page` view. A page is one tab wherever under its path it is: going from `/plugins` to `/plugins/tabs` moves that tab and opens no other, and the tab keeps the address, so it comes back to it when it is turned to again or the app is reloaded. A page registered with `tabAt` has a tab of its own for each `key` that `tabAt(path)` gives an address under its path (without the query), called its `title`: each tag's page is `#name`, keyed by the tag's name in lower case, so two tags sit side by side, `/tags/Garden` and `/tags/garden` are one tab, and `/tags` is one more. The Tabs plugin keeps the key on the tab (`ownTab` in the layout it keeps), Quick open names and tells such tabs apart by it, and a layout kept before a page had `tabAt` takes its one tab over as the tab at that address. Two pages can be open side by side, so a page is drawn with an `app` whose `path` and `pageState` are its own and whose `opened` is itself, with `noteId`, `note` and `folderId` null as they were when a page had the editor area to itself. `host.app()` is still the app as a whole, at the address of the tab in front. A page is drawn only while its tab is showing, so what it must keep while another tab is in front belongs in its address. One page is not a tab: a page registered `transient` only leads somewhere else, as Today (`/today`) opens the day's note and puts it at its own place in the browser's history, so it is drawn in place of the editor area for that moment and leaves no tab behind. The editor area stays as it is underneath, out of sight, so no open editor is made again. A tab kept on a page that has gone since, as when its plugin was turned off, is still a tab: the core asks the editor area's `returnsTo()` what it has in front at an address that names no page, and draws that tab in its row, where it says there is nothing at its address and can be closed. The Tabs plugin keeps each page's name with its tabs, so such a tab is still called what the page was, and by its address where no name was kept.
- **`HelpOverlay`** from the plugin API is help over the page, one look for every help in the app: `<HelpOverlay title onClose>` draws its children in a modal dialog with the title and a close button. Escape, the close button and a press on the page around it call `onClose`; Escape there is the dialog's alone, so a panel it was opened from stays open, and a dialog opened over it is pressed in without closing it. It takes the keyboard while open and gives it back on closing to what had it, such as the button that opened it. The query syntax in Advanced and the keyboard shortcuts are drawn in it.
- **`ResizeHandle`** from the plugin API is the edge between two parts of the window that is dragged to give one more room: a focusable `role="separator"` with the arrow keys, Home, End, Enter and a double-click to put it back. The core uses it for the sidebar's and the inspector's inner edges, whose widths it keeps in the browser for each member, and Tabs and splits for the edge between two groups. The `column` view, while it is open, and the inspector's panel are given their width and do nothing for it. The panel's edge is there while it is pinned: over the page it is as wide as it was last dragged to.
- **Back and forward.** The app keeps where the member has been in this browser (`src/web/travels.ts`, a reducer with its tests in `test/core/plugin-travels.test.ts`): a stop for each note, folder's list and page put in front, a page at each of its paths (a person's page and the next are two), with its query as it was left (what Search was asked, the Calendar's `?view=…&day=…`). Settings is left out. A note's stop keeps where its cursor was, and the core's `nav.back` and `nav.forward` commands (Go back and Go forward: ⌘[ and ⌘] on a Mac, where they take the editor's indent keys in a note; Alt+← and Alt+→ elsewhere, where Ctrl+[ is vim's Escape) walk the stops, opening a tab closed since, turning to the pane a tab is in, and putting the cursor back. A jump inside a note is a stop of its own: an editor extension says one happened with a transaction carrying `noteJump.of({ from, to })` (exported from `plugin-api.ts`), as vim does for each jump its own list would record (G, gg, a search, `%`), so vim's ctrl+o and ctrl+i, which run the same two commands, walk vim's jumps within a note and the places between notes as one list. `app.recent()` is every place visited, the latest first and each once, which quick open lists after the open tabs before anything is typed. It is not the browser's history: Back in the browser still retraces the addresses as before.
- `app.notify({ message, icon, action })` tells the member something that just happened, in a card at the foot of the pane the member is working in, centred under it and above anything kept at its foot such as vim's bar, as v1's toasts: an icon in a tile (`info` unless said), the message, and `action`, one button such as Undo. Every notice of the app is drawn this way (`src/web/Toasts.tsx`): the todos plugin's "Task completed" and "Task abandoned", Archive and Trash's "Archived" and "Moved to Trash", and History's and Agents' "Reverted …". Cards stack, the newest at the foot and three at most (`stacked` in `src/web/notices.ts`); one with the same message as a card shown takes that card's place. A card goes after five seconds, or ten with a button, counted only while neither the pointer nor the keyboard is on it; a press on it or Escape sends it away. While what `action.run` answers is on its way the card stays, without its button; a notice it answers with is said in the card's place ("Undone: …", or why it couldn't be), and nothing sends the card away. It is laid over the app, so nothing moves when one comes or goes. `stays` keeps a card up with no timer until it is answered or pressed, for a question such as an offer to share or the Todos page's "Order changed" with Refresh, and `notify` answers with what takes the card down. It is for what the member just did and may want back, not for a standing fact about a note, which is a `mark` or a `notice` view.
- An open note has no bar above its text: it begins with its own heading. The `mark` slot is a word or two about a note in a quiet line under its title, in every editor showing it: the Archive and Trash plugin's "Archived · Unarchive". The line is a block widget after the note's first line (`underTitle` in `src/web/NoteEditor.tsx`), takes no room while no mark says anything, and the text under the title moves down by its height when one does. The `tool` slot is a quiet button at the note's top right, in its group's tab row before Focus, with an `order` (lowest first, 0 unless said): the Dashboard's pin (-1, not offered on a note that is archived or in Trash), Archive (0, Unarchive with its own icon while the note is archived) and the note's "…" menu (1), which holds what its card's menu does but the splits. An editor-area plugin draws them with `renderNoteTools(noteId)`. Whether the note is saved is said in the bottom bar's right end, as VS Code does, for the note in front; nothing in the note moves as it changes. The `notice` slot is a banner above the text, for what changes what the member can do with the note: that it is in Trash. The Note list plugin's breadcrumbs (`NoteCrumbs`) are a `notice` view too and come first: one slim line, the workspace, the folders down to the note's, and the note, each folder crumb opening a searchable list of its subfolders and notes (`noteCrumbs.ts`) from what the app already holds. Each is handed `note`, and draws nothing when it has nothing to say of it. When a banner appears the text moves down by the banner's height and no further.

A built-in plugin does not call `fetch` or read `localStorage`: it goes through the host. A third-party plugin has neither to call, since it does not run in the app's page at all.

## What a plugin says of itself

Three optional fields are what the Plugins page shows of a plugin. Every built-in has the first two, which `test/core/plugin-declarations.test.ts` checks.

- `description`: one line on what it is for, said beside its name in the list and at the top of its details. It names no other plugin, so a row is found by its plugin's name alone.
- `icon`: one of the app's own icons, by name (`IconName`). Without one the plugin stands under the picture every plugin has.
- `screenshots`: pictures of it at work, shown in its details: each `{ src, dark?, alt }`. `src` is a file the app serves, `dark` is the same picture taken in the dark theme and is shown in its place there, and `alt` says what the picture shows and is its caption. Kanban, Tables and Todos have them, in `public/plugin-shots/`. `node scripts/plugin-screenshots.ts --url <app url>` takes them again from the running app in both themes; add a plugin to its list to give it one.

Nothing else on the Plugins page is written by hand. A plugin's details list what it adds from what it registered: its commands, its views by slot, its embeds, its completions, its editor extensions and its settings (`PluginState.adds` in `src/web/pluginHost.ts`). A plugin that is off is listed with what it added when it was last on, and one that hasn't been on since the app loaded says so, since nothing but running `activate` could tell.

## Options

A plugin's `settings` are its options, by name. Each is a `Setting`: a `type` (`boolean`, `string`, `number`, `integer`, `chords`, `list`, words with a `maxItems` and a `maxLength` each, or `folder`, a folder's id or `""` for the default, which names that folder in `defaultFolder`), a `default`, a `title`, and optionally a `description`, an `enum`, `maxLength` or `defaultWithoutEmbedSite` for a string (its default on a server whose HTML embeds have no host of their own, as `/api/me` says: `html.run` asks first there), and a `minimum` and `maximum` for a number. Settings draws a `folder` setting as a list of the folders the member can edit, by their paths, with `defaultFolder` first for `""`, and the JSON holds the id. What a folder id the member can no longer edit means is for whoever reads the setting to say. A value the member wrote that the setting can't take reads as the default, or, for a string that gives `unreadable`, as that: a setting that guards something names its safe choice there (`html.run` reads an unreadable value as `ask first`). The words are JSON Schema's. They are plain data, so the app lists them without running the plugin, and they stay listed while it is off.

An option named `unit` in the plugin `word-count` is the setting `word-count.unit`. The member changes it in the plugin: its details on the Plugins page have every option it declares, each with the control its schema asks for, the reason a value was refused, and Reset. The Settings page has the same options, in the plugin's own category under "Plugins" and in the JSON. Both draw one component (`SettingRow`) and write the one setting, so they are always in step, and only a value that differs from the default is kept. A plugin does nothing for either: declaring the option is all.

`host.settings.get(name)` is the option's value now: the member's when it is valid, the default otherwise. A view is drawn again when settings change, so reading it while drawing is enough. Anything else calls `host.settings.subscribe(listener)`.

A plugin cannot change settings, other than one it declares `remembered: true`: an option it remembers from what the member does in its own views, so it is kept on the server with the member's settings in the workspace and not in one browser, such as which calendars the Calendar shows (`calendar.hidden`) or the order the Todos page is sorted in (`todos.sort`). `host.settings.set(name, value)` changes that one, as the member, and throws for any other; it answers false when the member's settings aren't read yet or the value isn't one the setting takes. Settings lists it like any other option, with Reset, and a remembered `list` with Reset and no field to type in. Nothing that guards anything is remembered, so `html.run` stays the member's alone. The key `set` writes must be the plugin's own declaration: a dotted name, or an id that would make another's key (such as `keybindings`), is refused, and a value over 10,000 characters of JSON is not kept. The host tells plugins when the member's settings are read, even when nothing in them changed, so a plugin waiting to move something it kept in the browser can. For everything else the host has no call, and `host.perform` refuses `settings.write` and `settings.read`, so a plugin can't change them through the server either, or read another plugin's. What it sends is a copy taken once, so an operation whose `type` reads one way when it is looked at and another when it is sent is sent as it was looked at. A plugin whose id an earlier plugin has is left out, since its settings would be that plugin's. `test/core/plugin-host.test.ts` checks the refusal with a plugin that tries.

Some names are the app's. A command whose id starts with `go.`, `plugins.`, `settings.`, or `inspector.` is refused, and so is a page at an address another page has, and the plugin that asked doesn't start. A page still gets its `go.<id>` command and an inspector view its `inspector.<id>` command, which the host adds. The core and the Settings and Plugins pages start before every other plugin, so none can take an id they need.

The name `enabled` is taken. Every plugin that can be turned off has the setting `<id>.enabled`, and a plugin that declares its own doesn't start.

## A theme over the theme: Night shift

A plugin can change how the whole app looks by setting the design tokens on the page's root, which is how every rule of `src/web/style.css` is colored. Night shift (`plugins/nightShift/`) is the one that does. Off by default, it is a red-on-black theme that sits on top of the light or the dark one.

- **The tokens are set inline on `<html>`**, which beats the stylesheet's `:root` rules for both themes, so the theme setting is left as it was and turning Night shift off takes every property it set off again, leaving the page exactly as it was (no `style` attribute is left). `theme.ts` is the whole palette: `nightTokens(strength)` is one value for each token of the stylesheet's `:root`, and a few more for what the stylesheet colors by hand (code in a note, a column's swatch). Every color in it has no blue at all, and green only as far as the strength allows: `tone(level, strength)` is red at a brightness with the strength's share of green (none for deep red, 10% for red, 32% for ember, 60% for amber). `test/core/plugin-night-shift.test.ts` checks both for every token at every strength, and the contrast of the text on each background.
- **`data-night-shift` on `<html>`** (its value is the strength) is what the end of the stylesheet is keyed on, for the colors it can't take from a token: swatches, who wrote a line, a person's initials, a calendar's own colors, a checkbox's gray and a check mark's white. Every rule there begins with it, so nothing applies with the plugin off. `themeNow()` answers `dark` while it is there, so a frame drawn in the app's theme, such as a post, is asked for a dark one. A new color written by hand in the stylesheet belongs in `nightTokens` or in that block: `test/browser/night-shift.spec.ts` sweeps every page, dialog, menu and toast for any color with blue in it.
- **The window follows it.** `followWindowColor()` in `src/web/theme.ts` gives every `<meta name="theme-color">` the root's background each time the look changes (`onLook`: the theme, or Night shift coming, going or changing strength), so the title bar and the system's picture of the window match the page. A plugin's frame is sent the new colors on the same signal.
- **Toggling is a remembered setting.** `night-shift.on` (true unless the member turned it off) is `remembered`, so the command Toggle night shift, `mod+shift+x`, can change it with `host.settings.set`, and it follows the member to any browser. The plugin being on is the Plugins page's switch as for any plugin; that switch makes the command exist, and the setting says whether the theme is showing. The key is a member's to rebind like any other.
- **Tinting pictures** is the setting `night-shift.tint`, off by default. With it on, `img`, `video` and `canvas` get a filter, `url(#night-shift-tint)`, an SVG `feColorMatrix` the plugin keeps in a hidden `<svg>` that turns what is drawn to its brightness in red and drops blue whatever it holds (a CSS `sepia()` and `hue-rotate()` can't). A frame from another site is sandboxed and can't be restyled inside, so `.embed-below:has(iframe)` gets two layers over it, a gray backdrop and a multiplied red, both `pointer-events: none` so that every press goes to the frame (and to the guard that sits over it, `frameGuard.ts`). Nothing is asked of the network, and nothing of the member's location.
- **Read a setting after `activate` returns, not in it.** `host.settings.get` while a plugin is starting has the host build its list of what each plugin adds before the plugin is running, so the plugin's options are listed as off until something else changes. Night shift applies in a microtask for that reason.

## Holding the line: Typewriter mode

Typewriter mode (`plugins/typewriter/`) keeps the line holding the cursor at one height in the note's pane, and scrolls the text under it. Off by default, it is an editor extension made from the plugin's settings: `hold.ts` has `typewriter(hold, writing, keep)`, where `hold` is the height as a share of the pane, whether to dim and whether vim's z keys set the height, or null for off; `writing` knows the editor the member is writing in; and `keep` writes a height vim asked for, false when it couldn't.

- **It takes the editor's scrolling over.** The editor asks for the cursor to be scrolled into view for typing, moving, undoing, finding and vim's keys, and never for a click, the mouse wheel or what someone else types. `EditorView.scrollHandler` answers each ask by setting only the pane's `scrollTop`, in the measuring that follows the ask (the layout can't be read while it is made), so the line's middle is at the height: never `scrollLeft`, which is how nothing moves sideways. The pane is the nearest box around the editor that scrolls, so a split's and focus's panes are each their own; with none, the handler leaves the scroll to the editor. A line is held whole inside the pane: height 0 has its top at the pane's top and 100 its foot at the foot.
- **The room is measured.** The note's container is taller than its pane, so a share of it would put the first line lower than the height. The plugin measures the first and last rows and sets `--typewriter-above` and `--typewriter-below` on the editor's text, which the stylesheet makes its padding, with the editor's own padding taken away. It does so in the same measure as the scroll, so a line at either end of the note goes to its height in one step, and when new room above moves the text the scroll moves with it, so what is on screen stays where it is. A pane not shown, with no height, is left until it has one. The room is left on the text when the hold changes or ends: it is drawn only under `.cm-typewriter`, and a new hold begins from it.
- **The line goes back to its height** when the pane changes size, when the text changes size with nothing typed (a new text size, a picture loading) and when the height changes, only in the editor the member is writing in and only if it was there: after a wheel, a touch or a press on the pane it stays where the member put it, and another's pane stays as it is on screen. With focus, the editor keeps its lines in place itself as their heights change and adds that to any scroll made while it measures except one it was asked for, so there the plugin asks for the scroll, once the update is over.
- **Turning it off leaves the cursor's line where it is on screen.** Each measure notes where the line is, and the extension that is left once it's off scrolls it back there when the room has gone, as far as the top of the note, or the editor's own room under the last line, lets it.
- **Settings.** `typewriter.on` is `remembered`, as Night shift's is, so Toggle typewriter mode, `mod+shift+y`, changes it. `typewriter.height` is remembered too, 0 to 100: Typewriter: keep the line at this height writes where the cursor's line is in the editor that had focus last, since the command palette has it while the command runs, and turns the mode on. `typewriter.dim` fades every block no range of the selection touches, with a line decoration over what is drawn. A block is found in the note's markdown syntax tree, from the end of the line's words: a list item, a todo too, is its own lines and their wrapped and continuation lines, without the lists inside it or the items beside it; otherwise it is the innermost block around the line, whole, such as a heading, a paragraph, a paragraph of a quote, a table or a code block. A blank line between blocks, or a quote's `>` alone, is lit alone; one inside a list item is lit with the item. Where the tree isn't parsed past the line yet, as far down a long note, the block is the lines between blank ones, until the parse reaches it. A selection made with shift or vim's v and V lights every block it covers, as more than one cursor lights each one's. Lines go dim and light at once, as the scroll jumps. A change to `on`, `height`, `dim` or `vimSetsHeight` makes a new registration. The hold reaches the editor's plugins as a facet, so they stay as they are and only measure again; a change to any other setting makes none. A setting written before the member's settings have loaded fails, with a notice, once until one is written.
- **Vim's z keys say where the member wants the line.** vim's zt, zz and zb (and z<CR>, z., z-) send their scroll with the user event `scroll.cursor.start`, `scroll.cursor.center` or `scroll.cursor.end`, so the place goes with the scroll and nothing landing before it is drawn can lose it. With `typewriter.vimSetsHeight` on, the default, the plugin holds the line there at once and writes the height as 0, 50 or 100, or holds it at the height it had if that can't be written. A scroll to the middle that the member didn't ask for that way, such as Go back to a place in a note, holds the line at the height and leaves the height alone. The user event is how one plugin tells another what was asked without importing it.
- `test/core/plugin-typewriter.test.ts` checks the blocks lit, the scroll and the room against numbers, and `test/browser/typewriter.spec.ts` checks the line's place in the pane to 4 pixels as the member types and moves, with vim, in a split and in focus, and in every frame drawn as the height changes and the mode goes off and on.

## Widgets and where they live

A widget is a small live thing to glance at or press. There are three places one lives, and each has a built-in plugin or two that can be turned off like any other.

| Where | How a plugin adds one | Where its state is | Built in |
| --- | --- | --- | --- |
| In a note, inline | `host.embeds.register({ name, render })`, written `::name{config}` | The note: its config | Timer (`timer`), Stopwatch (`stopwatch`), Event (`calendar`), Contact (`contacts`) |
| In a note, as a block | `host.embeds.register({ name, block: true, render })`, written `:::name{config}` … `:::` | The note: its config and body | Kanban board (`kanban`) |
| In a note, below its line | An embed, inline or block, that also gives `below: { box, render }`, or an address embed: `host.embeds.register({ name, title, claims, below })` | The note: its config and body, or the address | A video's or a post's address alone on a line (`media`), HTML (`html`) |
| The bottom bar | `host.views.register("bar", { id, component, side, order })` | Whatever it shows: the open note, the app | Note clocks (`note-clocks`) at the left end. Word count (`word-count`) at the right is the same slot from a frame: see [One interface for a plugin that runs shut off](#one-interface-for-a-plugin-that-runs-shut-off) |
| From the command palette only | A command that asks what it needs with `ink.prompt`, and a `bar` view that shows it | This browser, for this member and workspace: `ink.storage` | Quick timer (`quick-timer`), which runs shut off |

Every embed with a syntax is in the `/` menu and the `::` menu, by itself or, with `menu: false`, through the `pick` of another that writes it (a picture, a video and a recording are written by "Upload an image", "Upload a video", "Upload a recording", "Upload a file" and "Insert an upload"), or, with `menu: false` and no `pick`, by another way in (a contact's and an email's references are written by `@`, `refer_record` and by hand), and every command-started widget is a command in the palette. An address embed is written by pasting or typing its address and by nothing else.

The other slots are not places for widgets. `column`, `section`, `editor`, and `page` are the structure of the app: where notes are found and read. A `section` is not drawn with the sidebar closed, so a widget there would be out of sight just when a timer matters. The `inspector` holds panels about what is in front, and which panels it has is part of the product (History, Backlinks, Info), so a count or a clock is in the bottom bar and not a fourth icon. An `overlay` is where a command-started widget asks its question, not where it stays.

**The bottom bar** is the `bar` slot described above: one line along the foot of the window, drawn only while some plugin has an item in it, 26px tall whatever is in it, so a widget that appears or goes moves nothing above it. It is out of sight in focus, where only the tab in front and the way out are shown: a clock in the note itself still runs there. A bar item that has nothing to show draws nothing. A clock in the bar is a button of class `bar-clock`, which fills the item the app wraps it in. `useOpenNote` gives a bar widget the text of the note in front; `plugins/lib/openNotes.ts` does the same for a plugin that also scrolls the note to a place in it (`show(noteId, at)`), through an editor extension of the plugin's own.

**A widget with no note** says where its state is. The quick timer keeps `{ length, since }` under `host.storage`: it runs on through a reload in this browser, another browser doesn't have it, nobody else sees it, there is one at a time, and nothing is written to any note or to History. A viewer can run one.

**Widgets don't flash.** A widget appears whole, at its size, in the first frame it is in, and is changed where it stands after that. `test/browser/widgets-steady.spec.ts` watches every frame from the start of the page, through a reload, typing elsewhere, someone else's change, the embed's own rewrite, a plugin turned off, and a tab or split opening: no frame shows an embed as written or empty, none is taken out of the page, and each stays the same element at the same place and size. The cursor passing through the note leaves each the same element too, lower only while its own text is shown above it, and back where it was after. What that asks of a plugin:

- Register an embed in `activate`, not after something has loaded, and draw all of it before `render` returns. An embed whose drawing needs code that isn't loaded yet still registers at once and draws a holder of its final size, which it fills in place. Otherwise the note shows `::name{}` first.
- Give `render` a `Drawn` with `update` when the embed can change what it drew, as the clocks do: the same button shows the new time. Without it the embed's element is emptied and drawn again in one step, which keeps the element and its place and loses anything inside it that the embed didn't keep itself, as kanban keeps a half-typed card.
- Keep its size when its state changes. The clock's reset button is there, and can't be pressed, before there is anything to reset, and its start button is one width whichever word it says, so starting it doesn't push the rest of the line along.
- A tab that comes back makes its editor again, so those are new elements, drawn whole in their first frame.

## Embeds

An embed is drawn where a note writes its name. An inline embed is written `::name{config}` on one line. An element an inline embed draws with a `data-follow` attribute is what vim's `gd` clicks with the cursor on the embed, as a file's link and a reference's chip are: give it to whatever a click opens. A block embed, one registered with `block: true`, is written on lines of its own:

```
:::kanban{}
## To do
- write the announcement
## Done
:::
```

The lines between the opening and the closing `:::` are its body. An embed is written one way: `::kanban{}` and `:::timer{5m}` … `:::` both stay as text. So does a block with no closing line, one inside a code fence, and any name nobody registered.

Each embed is drawn in a card the host draws around it: a border, the embed's title in small capitals, what the embed draws, and one options button where the embed has options. An inline embed's card stands on its line, with the title, the drawing and the button in a row. A block's card has the title and the button in a head, and the drawing under it. The title and the button's icon are drawn by the stylesheet, so a card adds no words to its line. A card has about half a line of room above and below it, the same with the cursor on the embed as off it.

An embed always stays drawn, the element it was. With the cursor on it, it is shown as written too, above its drawing, so it can be changed as text, the way the markup around it is:

- **An inline embed.** Its drawing is a widget of its own before the embed's text, and the text is hidden after it. With the cursor on the embed, the text is shown in rows of its own at the top of its line, from the line's left edge, in small monospace. The rows are as tall as the text needs at the width there is, so the card and everything after it are lower by exactly those rows and nothing moves sideways. Two embeds on one line each get their own rows, in order. A running stopwatch keeps running under its text.
- **A block.** Its drawing is a widget of its own under the block's lines, and the lines are hidden above it. The cursor goes into the lines as into any text: Down from the line above lands on the line that opens the block, Up from the line below lands on the one that closes it, and vim's `j` and `k` do the same. While the cursor is in them the lines are shown above the card, in the same small monospace, and the card is lower by them and no more, and what is typed there is drawn at once. They are hidden again when the cursor leaves. A key that jumps, such as Ctrl+End, a press and a search go where they say and not into the block. Where two blocks have no line between them, a step goes into the nearer one, and from its far line into the next.

**An inline embed that is all below its line** leaves `render` out, as an uploaded picture, video or recording does. It has no card and nothing in its line: while the cursor is elsewhere its text is hidden and draws nothing, and with the cursor on it (inside it or touching its edge) the text is shown where it is written (`.embed-written`, small monospace in the accent's colour), not in rows above. A line that is that embed and nothing else takes no room while the cursor is elsewhere (a block replace, as an address's line does), and what is below it is where the line was, as far below the words above as above the words below: the blank lines around it are its gaps. With the cursor anywhere on that line the line is shown (`.embed-alone`, the same small monospace) above what is drawn, which moves down by that line and is not drawn again; a step of the arrow keys or of vim's `j` and `k` stops on it. One whose `below.box` gives no room for what the note says stays as text. An embed that gives both `render` and `below` with `below.alone` is drawn by `render` among words and kept below a line it is alone on, as an uploaded file is a chip in a sentence and a preview on its own line. A block always has `render`.

A drawing takes no keys from the note: there is no moving through what an embed draws with the arrow keys. What an embed draws is pressed with the pointer, and changed with the keyboard as its text.

The cursor counts from the first time it is put somewhere or something is typed. A note opens with its cursor at its start, where nobody put it, so an embed at the top of a note opens drawn and nothing moves under the first press on the note. After that the cursor's place goes on counting when the keyboard leaves the text for a button of the embed itself, so what is shown above an embed doesn't go from under the pointer that is pressing it.

`embed.edit()` puts the cursor in the embed as written, as moving the cursor onto it does: in an inline embed's config, or in a block's opening line. For a block, `embed.edit(at)` puts it `at` characters into the body, which is how a press on a kanban card lands at the end of that card's line. A press on a card's own edge or title, off what the embed drew, does the same as `embed.edit()`.

### Options

An embed that declares options has one options button in its card, with three sliders on it. An embed with none has no button, and neither has a member who can't change the note. The button opens a panel beneath the embed, as wide as its card (or, for an embed whose drawing is below its line, as wide as that room), laid over the app so it moves nothing in the note. A card whose foot is out of the window, as a long board's is, has the panel beneath the button instead. The panel holds a field for each option the embed declares and nothing else.

Most options are declared as data, and then the host does everything: it reads each from the embed's config as an `id=value` word, draws its field, refuses a value the option can't take with a sentence saying what it takes, and writes the value back as a word at the end of the config (the default as no word at all, and every word that is no option's left where it was). The HTML embed's height is declared this way, and so is every option a third-party plugin's manifest gives its embed:

```ts
host.embeds.register({
  name: "html",
  title: "HTML",
  options: [{ type: "number", id: "height", label: "Height", min: 40, max: 2000, step: 1, default: 320 }],
  /* render, below */
});
```

Each is a `DeclaredOption` (`src/core/embedOptions.ts`) with an `id` (a small letter, then letters, digits and `-`), a `label`, a `default`, and a `type`:

| `type` | Written as | Drawn as | Also takes |
|---|---|---|---|
| `text` | `to=Ada`, `to="Ada Lovelace"` | a field | `maxLength`. No quotes, braces or line breaks. |
| `number` | `times=3` | a field, with what it takes under it | `min`, `max`, `step` |
| `toggle` | `loud=on`, `loud=off` | On and Off | |
| `choice` | `show=dots` | one button per value | `values`, one word each; no `default` means the first |
| `colour` | `tint=green` | a dot for each of `SWATCHES`, and none | |
| `duration` | `for=1h30m` | a field; `90`, `90m` and `1h30m` are one value | |
| `date` | `until=2026-10-31` | a field | empty is none |

A number written past either end of its range, as by hand, is read as that end; a number or a duration emptied in its field is its default again. `optionValues(options, config)` from the plugin API reads them all at once, each as its type (a number as a number, a toggle as true or false) or its default, which is what the HTML embed draws its height from. The table and the refusals are tested in `test/core/embed-options.test.ts`.

An option that lives anywhere else in what the note says, as the timer's length (the config's first word) and a board's column colours (its body) do, is given as `fields` and `set` instead:

```ts
host.embeds.register({
  name: "timer",
  title: "Timer",
  render,
  options: {
    fields: ({ config }) => [{ id: "length", label: "Length", kind: "text", value: lengthIn(config), hint: "Write it like 25m." }],
    set: ({ config }, id, value) => (durationOf(value) ? { config: withLength(config, value) } : "Write it like 25m."),
  },
});
```

`fields` and `set` are given what the note says of the embed now, `{ config, body }`, and nothing else. A field is `kind: "text"`, typed and taken on Enter or when the keyboard leaves it, or `kind: "choice"`, one of a few `choices`. A choice with a `swatch` is drawn as a dot of that colour: one of `SWATCHES` (`red`, `orange`, `yellow`, `green`, `blue`, `purple`, `pink`, `gray`), or `""` for none. Any element with `data-colour` set to one of those names has `--swatch` to draw with, one value for both themes, meant to be mixed into the theme's own surface with `color-mix` as a kanban column does. `set` returns the new `{ config, body }`, which the host writes exactly as `embed.update` does, so it is the member's change, saved, recorded, undone, and seen in every other open editor. Or it returns a sentence saying why the value can't be taken, which is shown under the fields and nothing is written. The embed is then changed where it stands, as after any rewrite, and the panel stays open and shows the new values. `fields` that returns none, as for a config that can't be read or a board with no columns, leaves the embed with no button, and closes the panel if it was open.

The timer's option is its length and the stopwatch's is how long it has run. Kanban has a colour for each column, and HTML its height. `test/browser/widgets-cursor.spec.ts` covers the button, the panel, and each of these.

`render(el, embed)` draws into `el` and is handed `embed.config`, `embed.body` (a block's lines, each with its line break), `embed.noteId` (the note it is written in, as a reference's chip needs to leave that note out of the notes it offers), `embed.readOnly`, and two functions:

- `embed.update({ config, body })` rewrites the embed in the note. It is an ordinary edit in that editor by the member: it is saved with their typing, synced, recorded in History as their change, and undone the way typing is. Give only what changes. The edit covers only the characters that differ, so typing elsewhere and other people's changes merge around it.
- `embed.edit(at?)` puts the cursor in the embed as written, which shows its text above its drawing.

`embed.readOnly` is true when the member can't change the note, as a viewer can't. The note's editor is then read-only as a whole: no typing, no keys, and `update` does nothing, whatever calls it. An embed draws what it shows and leaves out the controls that would call `update`: the timer is a time that can't be pressed, and the board has no "Add a card", no colours to set and nothing to drag.

`update` called from inside `render` is carried out right after the drawing, since the editor can't be changed while it draws. An embed that tidies its own config that way is drawn twice.

Two members can act on one embed before either sees the other's change, and the server merges their writes as text. An embed's reading of its config should stand that: two presses of one timer leave two `since=` words, and the timer reads the last and writes one back on the next press. Two moves of one kanban card to different columns leave the card in both, which a merge of text can't tell from two cards, so one of them is deleted by hand.

An embed keeps what it knows in the note. The timer keeps its length and how it is running in its config (`::timer{5m since=2026-10-10T12:00:00.000Z}`), so a reload and another member see the same time, and nothing ticks into the note: the time shown is worked out from the instant it started. Kanban keeps nothing but the markdown: `parseBoard` and `serializeBoard` in `plugins/kanban/board.ts` read the body into columns and cards and write it back line for line, so what a board doesn't understand stays where it was. A column's colour is the class its heading ends with, the way Pandoc and kramdown write one: `## Doing {.blue}`. Only the eight names in `SWATCHES` are read as a colour, and any other braces are part of the title.

A clock says what its buttons do: the time, then Start (Stop for a running stopwatch, Pause for a running timer), then Reset. What the buttons say is drawn by the stylesheet from `data-label` and is not text in the note's line, so the time is all a clock adds to it, and the button is as wide whichever word it says.

Each time the note says something else of an embed, whoever changed it, the embed's `update` is called if `render` gave one back, and otherwise `render` is called again on the same element, emptied. Focus then goes to the element whose `data-focus` equals that of the element that had it, so a control that rewrites the note keeps the keyboard. To send focus somewhere else, set `data-focus` on the focused element before calling `update`.

`update` is checked against the note as it is when called. A drawing that has left the editor, or one of an embed that the note no longer writes that way, does nothing, so a rewrite computed from a stale body can't land on someone else's newer text. A config holding `{`, `}`, or a line break throws, and so does a body with a line that is only `:::`: an embed can't write its way out of its own range. `test/core/plugin-embed-syntax.test.ts` covers the syntax and the edits, and `test/browser/widgets.spec.ts` the rest.

`starts` is what the insert menu writes for a new one: `{ config: "5m" }` for the timer, and a body of three empty columns for kanban. `description` is what the menu says it makes, in a line of words, and `preview` what it shows beside the list while it is highlighted, a `CompletionPreview`: the built-in embeds give a small picture drawn with `sketch` in `plugins/lib/sketch.ts`. An embed with neither is listed by its title alone. The menu never shows an embed's syntax.

`pick` is for an embed a menu can't write, because what it holds is made by doing something: `{ title, description, preview, insert }` (an `EmbedPick`; an older `detail` is read as its `description`), or a list of them for an embed reached more than one way. The insert menu lists each under its title after the embeds it writes, in the order given, found by its title alone, and picking one writes what its `insert` answers, as a completion item's function `insert` is written: it is told the `InsertAt` and answers later, or answers `""` at once to take out the `/` and what was typed after it and write in its own time. The `file` embed has five, each found from the editor it was picked in by the `anchor`, which is in that editor's scroller. "Upload an image", "Upload a video", "Upload a recording" and "Upload a file" (`SENDS` in `plugins/uploads/index.tsx`, `pickInto` in `sending.ts`) open the file picker with `accept` set to `image/*`, `video/*`, `audio/*` or nothing, keep the place they were picked through whatever is typed, and answer `""`; each file chosen is then sent and written there as a paste would be, whichever entry sent it, so the bar says how far it has got and one sent in parts has its line written as soon as it has an id. Not "Upload audio", whose word would answer `N /A`. "Insert an upload" opens a popover at the cursor (a CodeMirror tooltip from the plugin's own editor extension, `plugins/uploads/inserting.tsx`) with a field whose words go to `upload.list`'s query, and the uploads the member can see, latest first. Up and Down move, Enter calls `upload.place` and writes the upload at the cursor: a picture, a video or a recording on a line of its own as a pasted one is, a file as a chip among the words. Escape closes it and gives the keyboard back to the note, which is as it was before the `/`.

### Below the line

An embed that shows more than fits in a line, such as a video or a frame, gives `below`:

```ts
host.embeds.register({
  name: "clip",
  title: "Clip",
  render: (el, embed) => void (el.textContent = "Clip"), // what stands in the line
  below: {
    box: ({ config }) => (clipIn(config) ? { ratio: 16 / 9 } : null), // or { height: 320 }
    render(el, { config }) {
      el.append(playerFor(clipIn(config)!));
      return () => {/* stop what was started */};
    },
  },
});
```

**An address embed** is what is shown for a web address written alone on a line, which is how a video or a post is written (`plugins/media/`):

```ts
host.embeds.register({
  name: "video",
  title: "Video",
  claims: (address) => videoIn(address) !== null,
  below: { box, render }, // the address is `config`
});
```

It has no syntax: its name is one among the address embeds only, and what a note that says `::video{…}` shows is up to an embed with that syntax, as the Uploads plugin's is for an uploaded video. The first registered whose `claims` answers true for an https address has it, and an address in a paragraph, a list or code is never asked about. `update` does nothing for one. While the cursor is elsewhere the address's line takes no room (a block replace), and what is below it is where the line was, a paragraph's gap below the words above and the same above the words below. With the cursor on the line the address shows above it (`.embed-address`: the code face at 0.74em, the accent's colour, a ↗ after it) and the box gets an edge of the accent's colour (`.embed-below-on`); what is below it moves down by that line, and is not drawn again. Pointing at what is below it shows nothing, as nothing else in a note is shown as written under the pointer. A step from the line next to it, by the arrow keys or vim's `j` and `k`, stops on it, though the editor would step over a line out of its flow.

**A block's `below` is the body of its card.** The card the host draws for the block has the block's title and its options and ends open, and the room under it has the bottom corners, as wide as the card, and as much room under it (0.8em) as the card has above it. A block that keeps something below should draw nothing in `render`.

`box` says what room to keep, from what the note says of the embed alone, so the room is there in the first frame painted and nothing moves when what fills it loads. The room is under the line that writes the embed, or under a block embed's closing line, and stays while the cursor is on that line: the line is shown as written and what is below it is not touched.

`box` may give `share`, more than 0 and up to 1, for a room that takes that much of the column's width (with `maxWidth` still the most it is), at the same shape.

`below.render` draws into an element the host keeps outside the note's text, laid over the room. CodeMirror makes its own elements again whenever it likes, and drops the ones scrolled out of sight, and a frame that is taken out of the page, or only moved in it, loads again. So the element is made once, the first time the room is on screen, is never moved in the page, and is only placed where its room is after each change. It lasts while the note says the same of the embed: through typing anywhere else, lines added and removed, the cursor, another member's change, and scrolling far away, where it goes on running. `keep` in `src/web/belowIdentity.ts` says which embed is which after a change. When the note says something else of the embed, what `render` returned is called, the element is emptied, and `render` is called again in it. A `render` that returns `{ update, stop }` (a `BelowDrawn`) is asked to `update` instead, in the elements it drew, as an uploaded video goes on playing at another width. `render` and `update` are handed `column()` too, how wide the note's column is in pixels at that moment, for a control that offers widths as shares of it. An edit that passes through a config with nothing to show, such as a video's id with a letter deleted, takes the element out, and the next one is new.

**The room comes from the note.** What is only known after loading gets into the note: `render` is handed `update`, which rewrites the embed as `Embedded.update` does, and `box` then reads it. This is the rule for pictures and files (#22): the upload writes a picture's size into its config when it is inserted (`::image{id 1200x800}`), so its room is right from the first frame for everyone. One written by hand without a size gets a usual room, and writes its size with `update` once it has loaded, which moves the lines below it once and never again. A test in `test/browser/media.spec.ts` does exactly that with a fixture embed. The exception is what the note has nowhere to hold: an address has no config. `render` is handed `resize(height)`, which gives a room sized by `height` another height for as long as that embed is kept, and moves what is under it once. A post uses it when its frame says how tall the post is, and keeps the height in `host.storage` so that `box` answers with it the next time and nothing moves then. `box` may also give `maxWidth`, in pixels, for what is drawn narrower than the column.

**Nothing pops in.** What loads after its room is drawn, another site's frame or an HTML embed, holds the room with a placeholder its size until it is drawn: `arriving(into, frame)` in `plugins/lib/arriving.ts` lays a pulsing `.embed-loading` over the room and keeps the frame there but unseen (`.embed-arriving`, opacity 0) until `arrived()` is called. A post calls it when its frame says how tall it is, or a while after its page has loaded if it never says; `again()` puts the placeholder back while a post is asked for in the other theme. A frame that never loads, or errors, is taken out and the room shows a link to the post, so it does not stay an empty box. A room comes on screen when the note is scrolled, by the editor or by anything around it, and is drawn then: in sight means inside the window and inside every element around it that scrolls or clips, such as a pane of a split. A block the cursor is in is not drawn again at each key: what was drawn stays until the cursor has left the block, and then what the block says is drawn once, so HTML half written never runs.

Not covered: a tab switch or a split makes the editor again, so what was below a line starts over (#36).

`test/browser/media.spec.ts` holds a playing video to this through each kind of change, and checks every painted frame for a room without what fills it.

`box` may give `width` beside `ratio`: `{ ratio: 4 / 3, width: 640 }` is a room no wider than 640 pixels, narrowed to the note's column at the same shape. It is how a picture isn't drawn larger than it is. Like everything `box` answers, it comes from the note's text alone.

### Frames

What is asked of other sites when a note is opened, once its media has been on screen: a video's picture (`i.ytimg.com`) and what it is called (`www.youtube.com/oembed`, through `askSite`, with no cookie and no referrer), and each post's own frame (`platform.twitter.com`, `embed.bsky.app`), which loads what that site loads. So those sites learn that someone at this address opened something with that video or post in it, without a press. The maintainer chose this over a button to load each one. A video's player (`www.youtube-nocookie.com`) is still not asked for until play is pressed. An HTML embed runs by itself the first time its room is on screen, in its sandbox, unless the member's setting `html.run` is `ask first`, when it waits for Run (the maintainer's choice). It asks nothing of another site either way. A changed embed starts over: what was run is not remembered past the element it ran in, for any member.

**The keyboard stays with the app** (`src/web/frameGuard.ts`). A frame can focus itself, and whatever is typed after that goes to it and not to the note. The host guards every frame drawn below a line: a frame may have the keyboard only while the member's pointer is on it, having moved or pressed there since their last key or press elsewhere in the app, or right after they pressed Tab. A frame that takes it any other way loses it before another key is typed, is stopped, and its room says so with a button to show it again. A shield lies over a frame until the pointer moves on it, since a frame swallows the pointer events over itself. While a frame has the keyboard its box shows "Back to the note", and a click anywhere in the app does the same. What this does not stop: a frame the member is pointing at can take the keyboard without being clicked. An embed's frame drawn anywhere but below a line is not guarded, and no built-in does that.

**Another site's frame** is sandboxed (`allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-presentation`: it runs as its own site and can open its own links in a new tab, and can't take the app's window anywhere), is sent the app's address and never the note's (`referrerpolicy="strict-origin"`; YouTube refuses to play with none), and its address is built from an id checked against a pattern, never from the note's text. The Worker lists the sites the app may frame (`FRAME_ORIGINS` in `src/worker/frames.ts`) in the page's `frame-src`, so an embed for a site that isn't there shows nothing. Social sites are the ones with a frame of their own that works sandboxed and whose address follows from the post's: X, and Bluesky for an address that carries the account's DID. A post is asked for in the app's theme (`themeNow`, and again on `onTheme`), is as wide as its site draws one (550 pixels), and its box has no border of its own and is cut to the post's corners, so there is one edge and it is the post's. Its height is taken only from a message that comes from its own frame and its own origin. A site that offers only a script to run in the page is left out. Once the member has started one, that site's frame is that site's: it can go to another address the page may frame, and it can add entries to what Back goes through.

**HTML from a note** is never read as markup by the app. `sandboxed(html, { title, refused, drawn })` from the plugin API makes a frame for it; `drawn` is called once the shell has put the HTML on its page (the shell posts `{ embedFrame: "drawn" }` on its inner frame's `load`, and `drawn` is called anyway three seconds after the HTML was handed over, for HTML that stops its own page from loading), which is when the HTML embed takes its placeholder away. The frame element carries no `sandbox` attribute: the shell's own response header shuts it in, and the app hands the HTML over only to a document that answers from an origin with no name (`event.origin === "null"`), which is what the header gives it. If no such answer comes in ten seconds, `refused` is called, nothing has run, and the HTML embed says so in its room. With the attribute, the browser in the Claude desktop app refuses the request for the shell on a local address (`net::ERR_BLOCKED_BY_CLIENT`) and the embed was a white box. The HTML is given a first line of the app's own: a doctype, the theme as its colour scheme, and the app's background, ink and face on `:root`, so a bare snippet reads as the note does in either theme and the HTML's own styles win over it. The Worker serves a shell at `/embed-frame` that holds nothing, with `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; frame-src 'none'; …`. The app hands the shell the HTML as a string, and the shell puts it in a frame of its own as that frame's whole document (`srcdoc`). That inner frame has no address, an origin no other document has, and the shell's policy. What `test/browser/media.spec.ts` proves of it, by trying from inside:

- It can't read the page around it, the member's session, cookies, or anything the browser keeps.
- It can't fetch, send, or load anything: not from the app, not from anywhere.
- It can't send its own frame, the shell's, or a frame inside it to any address, by `location`, a link, a refresh, or a form. The shell's policy governs it, not the page's, so the sites the app frames are out of reach too. It can't open a window, move the app's, or add to what Back goes through.

What it can do, which nothing a browser offers today closes: **open a WebRTC peer connection.** Chrome does not recognize CSP's `webrtc 'block'` (sent as a header and as a `<meta>`, it logs "Unrecognized Content-Security-Policy directive" and candidates are still gathered), no `Permissions-Policy` feature names WebRTC, and deleting `RTCPeerConnection` before the embed runs is undone by a frame the embed makes inside itself from `srcdoc`, which runs script with one of its own (tried: it answered `function`). A running HTML embed got a `srflx` candidate from a public STUN server, which shows that server the reader's public address, and with a prepared peer a data channel carries anything the embed holds. So an HTML embed is without network except for WebRTC, from the moment it runs, which is as soon as it is on screen unless the member asks to be asked first.

It can also post messages to the shell, which listens for nothing after the first one from the app, and spend the reader's processor. Where the browser keeps the frame in the app's own process, a loop in the HTML stops the whole tab: Chrome on a computer puts a sandboxed frame in a process of its own, so the app keeps answering there, but a browser without that (Safari today, and Chromium as Playwright starts it) does not. So the HTML embeds plugin lists, in `host.storage`, each HTML running in this browser (`plugins/html/running.ts`, by a hash of the text), and a page takes its own out when it is left (`pagehide`). A page that stopped answering is never left that way, so its HTML is still listed when it is opened again, in that tab or another, and it asks before it runs, saying why; pressing Run takes it off the list. HTML that runs in another tab at the same time asks too. A loop that only starts after the page is left as usual is not caught.

Where the shell is served from: in Previews and on the built Worker CI tests it is the app's own host, which is the only host each of those has. Its origin is still its own, and the inner frame's another, because the response header says so. The member's session cookie goes with the request for the shell, which is the same empty document for everyone. Setting `EMBED_ORIGIN` on the Worker to a host kept for embeds (and routing that host to the Worker) serves it from there instead: that host answers with the shell and nothing else, and the app's host sends the frame to it (a redirect from `/embed-frame`, and the page's `frame-src` names it). In production a deploy sets it (`npm run deploy`, in `package.json`) to the Worker's own `workers.dev` address, `https://common-ink-v3.draftox.workers.dev`, which `wrangler.jsonc` turns on for this alone: that host is checked before anything else the Worker answers, so it serves the shell or nothing, never a page of the app or even `/health` (the built files under `/assets`, which skip the Worker on every host, are there too, as they are on commonink.app), and HTML embeds run by themselves on commonink.app. Previews and the built Worker CI tests don't set it, so there it is the app's own host and HTML asks first. The dev server (`npm run dev`) sets `EMBED_ORIGIN` to `http://embed.localhost:<its port>`, a host of its own that the browser takes to this machine, so on this machine HTML embeds run by themselves; with `--host`, where other machines reach the server and `embed.localhost` would be themselves, it doesn't, and they ask first. For that, the dev server keeps to the port it is given (`strictPort`). For a loop in HTML to be unable to stop the app in a browser that keeps each site in its own process, that host must be another site, not only another origin: a registrable domain of its own (not `embed.commonink.app`, which is the same site), or a `*.workers.dev` name, each of which is its own site.

**The network** is off for an HTML embed until an admin allows it. HTML embeds have one permission in the workspace's record of its plugins, `network`, with the sites an admin lists (Plugins page, "HTML embeds"). It belongs to the workspace and not to a note or a plugin: an HTML embed is a note's text, so the allowance is "HTML written in this workspace's notes may reach these sites, once a reader presses Run". While it is allowed, the Run button names the sites, and the frame is opened with a grant: `plugin.frame` answers a token, good once and for a minute, and the Worker answers `/embed-frame/g/<token>` with the same shell under a policy whose `connect-src`, `img-src`, `media-src` and `font-src` name those sites and no other (`embedPolicy({ network })` in `src/worker/frames.ts`). Script is never loaded from a site, and the inner frame keeps `frame-src 'none'`: a grant of the network is not a grant to leave. The grant is a token and not a variant of the shell's address because any frame can be sent to any address its ancestors' `frame-src` allows: an embed can't guess a token, a used one answers 404, and only the hash of one is kept. A frame's requests carry no session: its origin is its own, so the member's cookie doesn't go with them, which `test/browser/third-party-attacks.spec.ts` checks on the wire. A guest and a link's page get no grant.

## Completions

`host.completions.register({ id, trigger, items })` offers a list at the cursor. It opens when the member types the trigger at the start of a line or after a space, and not inside code, so the `/` of a URL, a path, or a date opens nothing. `items(typed, { noteId })` is asked on each keystroke for what to offer for the text typed after the trigger in that note, best first, and may answer with a promise. Once the list is open, one that answers at once is asked within each keystroke, so a letter and Enter in the same breath picks what that letter narrowed to. The list first opens a moment after the trigger is typed, so a trigger, letters and Enter with no pause at all between them can still reach Enter before there is a list, and break the line. Completions whose triggers both fit share the list, grouped by each item's `kind`, the groups in the order of `COMPLETION_KINDS` in the plugin API (people, dates, notes, folders, uploads, events, blocks, embeds, and last what is new, such as a contact to create), with items of no kind before every group. Within a kind the items come one completion's after another's, by their `order` (lower first, 0 when not given) and then in the order of their plugins, each completion's in the order it gave them. Where the list holds more than one kind each group is headed by the kind's heading (`grouped` in `src/web/completionGroups.ts`, drawn as CodeMirror's sections), so `[[` reads Notes then Events, and `@` People, Dates, Notes, Folders, Uploads, Events, and New. A new kind of thing is a row in `COMPLETION_KINDS`, and its row is where its group goes. With nothing from any of them the list stays while the member is still typing the word that stopped fitting: from where it last offered something, letters and digits alone keep it, showing one row, No matches, that is never highlighted, leaves Tab and Enter to the note, and closes the list when clicked. So Backspace back to what fit finds the list there and fills it again, as CodeMirror opens no list on a deletion. A space, a bracket or any other mark after it closes the list, since that is prose or syntax written by hand, as in `::timer{5m}`, and so does a word that fits nothing after a prose trigger that follows other words, as `yes /no` does, and a list that opens on a fresh key with nothing to offer stays shut (`NOTHING` in `src/web/completing.ts`). A completion that offers to create what was typed, as `#` and `@` do, shows that instead. The first item is highlighted as the list shows, and Enter and Tab pick the highlighted item, except where it is of a kind that `waits` in `COMPLETION_KINDS`, as what is new does: it makes something outside the note when picked, so it is never highlighted of itself, Enter stays a new line, and Tab, or an arrow key then Enter, picks it. A completion whose trigger is written in prose too gives `prose: true`: after other words on its line its list shows with nothing highlighted and Enter is always a new line, since a `/` and a word there are as likely the member's own. Tab then picks the first item, and the arrow keys then Enter, or a click, pick any. At the start of a line, after blank space, a quote's `>` or a list item's mark and box, it is as any other. Completions share one list, so a prose trigger after words leaves the whole list unhighlighted, other completions' items too. With no list open Tab is whatever it is elsewhere in a note. Each item has a `label` and `insert`, the text that takes the place of the trigger and what was typed. `description` is a line under the label that says what the item is in words, such as a note's folder or an event's day, and `detail` is said after the label, more quietly, in the code font. `preview` is drawn beside the list while the item is highlighted: plain data, `{ image?, text?, facts? }`, a picture's address, words to read such as a note's first lines, and name and value pairs such as an event's calendar, drawn the same way for every item (`drawn` in `src/web/completing.ts`). Where there is no room beside the list, as on a narrow screen, the preview isn't seen. A group's heading is hidden from a screen reader, since a listbox holds options alone. `insert` may be a function answering a promise, for text made only when the item is picked, as an event's reference is (`record.refer`), and it is told where it goes, an `InsertAt`: the note, `noteId`, as an upload needs to be placed there; `anchor`, an empty element at the cursor that scrolls with the text, for a popover to hang from, as Pick a date… does, there until the item is written or isn't; and `focus()`, which gives the keyboard back to the note, as a popover closed with Escape does. What it answers is written once it does, where the trigger and what was typed still are, the cursor after it unless typing went on meanwhile, and null, a refusal (the completion's plugin is told, as for `items`), or a change to that text meanwhile writes nothing. `tone` colours the label: `accent` is the theme colour and `muted` is gray. `select` leaves part of it selected, `block` puts it on lines of its own, in place of blank space, a quote's mark or a list item's mark that is all that comes before it (with `select`, the cursor goes there and not to the line after), `apart` keeps such a block a blank line from words on the line under it, as a table needs, which would take them in as a row, and `spaces: true` on the completion lets what is typed hold spaces, as a note's title does. `anywhere: true` opens the list wherever the trigger is typed outside code, right after a bracket or a word too. It is for a trigger nobody types by accident, as `[[` is, and wrong for `/` or `@`.

```ts
host.completions.register({
  id: "people",
  trigger: "@",
  items: (typed) => people.filter((p) => p.name.toLowerCase().startsWith(typed.toLowerCase())).map((p) => ({ label: p.name, insert: `@${p.handle}` })),
});
```

The insert menu is one of these, in `plugins/embedMenu.ts`: on `/` it lists its own blocks of markdown (headings, lists, a task list, a table, a code block, a quote and a divider, each with a picture) under Blocks, then `host.embeds.list()` under Embeds, so an embed is in the menu as soon as its plugin registers it. On `::` it lists the embeds alone, made by the same `embedItems`, so picking one writes what `/` writes in place of the `::` and what was typed; `::` is not a prose trigger, so Enter picks after words too, and what a member types past an embed's name, as in `::image{`, matches nothing and closes the list, as does a block's closing `:::`. A block whose words go on its line, as a heading's do, is a `block` item with a `select`, which puts the cursor there. It offers an item only when what was typed starts its title, a word of its title, or its name (`starting` in `plugins/lib/match.ts`), so `yes /no` and Enter is a new line and not a board. It gives `prose: true`, so `A /B`, `date /time` and `start /stop` with Enter are new lines, though the list shows what they start. The list itself is CodeMirror's autocompletion, which one place in the core configures (`src/web/completing.ts`), so completions from several plugins share one list, one set of keys, and vim's insert mode. They are one source to CodeMirror, asked again within each keystroke when every completion that fits answers at once, so an open list is never a key behind what was typed. The first opening still waits on CodeMirror's typing delay, set to nothing, which is one turn of the event loop. A plugin that added its own `autocompletion()` as an editor extension would fight it. A completion that throws offers nothing, and the Plugins page says so.

## Editor extensions

`host.editorExtensions.register({ id, extension })` adds a CodeMirror 6 extension to the editor of every note, including notes already open, in every editor group. Turning the plugin off takes it back out the same way. One registered with `anyText: true` is given to the editors of the settings JSON and the agents file too, which are drawn as a note's is: that is for how an editor is worked, as vim, typewriter mode and line numbers do, and not for what a note holds. Only Common Ink's own plugins may, since such an extension could read and change every setting, and the agents file. It is made for those editors with `noteId` set to `/settings.json` or `/agents-file.md`.

```ts
import { EditorView } from "@codemirror/view";

host.editorExtensions.register({ id: "wide-caret", extension: EditorView.theme({ ".cm-cursor": { borderLeftWidth: "3px" } }) });
```

The plugin builds the extension from its own imports of `@codemirror/*`, which are packages and not the app, so the boundary test allows them. The API types `extension` as `object` to keep CodeMirror out of the plugin API's own imports. The app checks the value when it is added: one CodeMirror won't take is left out, and the Plugins page says so.

An extension that needs to know its editor is given as a function. It is handed the editor's context, which carries the id of the note the editor holds, and returns the extension for that editor:

```ts
host.editorExtensions.register({ id: "note-links", extension: ({ noteId }) => linksFrom(noteId) });
```

The function is called once for each editor, when the editor is made or when the extension is added to one already open. Two sides of a split each get their own call with their own note, and an editor holds one note for as long as it lasts. What the function returns is checked the way a value is. If it throws, or returns what CodeMirror won't take, the extension is left out of that editor, the note still opens, and the Plugins page says so. That is known only once an editor has been made, so a broken function shows on the Plugins page after a note has been open and not before.

A note is also drawn where it is only read: a card in a folder's list. That drawing gets the same extensions, called with `{ noteId, reading: true }`, and it can be there beside the note's editor, more than once. So an extension that keeps a note's editor by the note's id (to read its text, or to put the cursor in it) leaves a reading out, and one that keeps every editor to draw it again keeps a reading by `editorKey(editor)` from `plugins/lib/live.ts`. Nothing a reading does changes the note. `isReading(state)` from the plugin API says whether a state is a reading's, and `touched`, `within` and `lineTouched` in `plugins/lib/live.ts` answer false there, so nothing in a reading is shown as written whatever is selected. A link's shared page is a reading too. A reading is not an editor: an extension that is only for editing, as vim and line numbers are, gives a reading nothing (`(editor) => (editor.reading ? [] : extension)`), so it has no cursor, no mode bar and no keys, and its text is selected and copied as a page's is.

A panel an extension shows under the text (`showPanel`, as vim's mode bar is) is put at the foot of the note's pane by the editor, outside the scrolling text and as wide as the pane, one for each editor. It is styled in `style.css` under `.note-foot`, since it is no longer inside `.cm-editor` for an editor theme to reach. The editor sets `--text-left` on `.note-foot` to where the note's text begins across the pane, measured again whenever the pane or the column changes size (a split dragged, focus, the reading width), so a panel's words can begin where the text does, as vim's mode does with `padding-left: var(--text-left)`.

Plugins' extensions come before the editor's own, in the order of the plugins, so a plugin's keys are tried before the editor's. Wrap one in `Prec` to place it more exactly. An extension given as a value is shared by every editor. Keep what belongs to one editor in a `StateField` or a `ViewPlugin`, or give a function.

A plugin whose editing is heavy loads it when it starts, as Vim mode does with `import("./editing.ts")`, and registers the extension when the import settles unless it was turned off meanwhile. If the import fails it calls `host.report(error)`, which shows the reason against the plugin on the Plugins page.

One limit:

- Only the check when an extension is added, or made for an editor, reaches the Plugins page. An extension that throws later, while an editor is running, is CodeMirror's to log, and nothing holds it against its plugin. The markdown plugins report what they know can fail: a part of them that couldn't be loaded.

Don't add a `keymap.of(...)` for a key or two. CodeMirror runs all keymaps from one handler, placed where the first keymap is, and a plugin's extension comes before vim's. A keymap in a plugin therefore puts every editor key, Escape among them, ahead of vim, and insert mode stops ending. Register a command with `keys` and `when`, as the outline bullets do, or handle the one key in `EditorView.domEventHandlers`, as tables do for the arrow keys.

## Drawing markdown in a note

A note has one surface, its editor. Markdown is drawn there, in place of its source, and a construct is shown as written while the cursor is on that construct itself, inside it or at its edge, and not merely on its line: `touched(state, from, to)` in `plugins/lib/live.ts`, asked with the construct's own range. Six built-in plugins do it, each of which can be turned off alone: `gfm` (emphasis, headings, links, quotes, rules, inline code), `todos` (a todo's checkbox and its options), `tables`, `math`, `code-blocks`, and `bullets`. The editor parses GitHub-flavored markdown whether or not they are on, so each reads the same parse.

Three rules hold for all of them, and for anything drawn later:

- The note's text is never changed by drawing it. What a drawing changes, it changes with an ordinary edit dispatched to its editor (`userEvent: "input.<what>"`), so it is saved, synced, in History as the member's, and undone like typing. Ask `writable(state)` first: a member who can only read gets no way to write.
- Only what is on screen is drawn. `drawnInView` in `plugins/lib/live.ts` redraws from `view.visibleRanges`. Blocks that replace whole lines must come from the state, with `drawnInState`, and must find themselves cheaply.
- Nothing moves when a construct goes between drawn and written, but the words after it on its row, by the width of its own marks where those are taken out when drawn. The first letter of the line stays where it is, the words before the construct stay where they are, the line keeps its height, and the lines after it stay put. `test/browser/markdown-layout.spec.ts` measures it by line, and `test/browser/constructs.spec.ts` walks the cursor along a line one letter at a time and measures it by construct.

How each kind of mark keeps the third rule:

| What | Drawn | With the cursor on it |
| --- | --- | --- |
| A heading's `#`s | hang in the left margin, not painted | painted, in the same place, with the cursor anywhere on the heading's line |
| `>`, `---`, a code fence | kept in the line, not painted (`ghost`) | painted: a `>` with the cursor on the mark, a fence with the cursor on its line |
| A bullet's `-` | kept in the line, a dot painted over it; on a todo's line, nothing painted (`bullet-blank`), since the box marks the item | painted, with the cursor on the mark |
| `[ ]` of a todo | a checkbox drawn over the three characters' own width (`keepsWidth`), larger than they are wide, starting where the `[` does. The space after it is widened (`md-task-gap`, in `plugins/gfm/lists.ts`) so the words start `BOX_EM` + `TASK_GAP_EM` (1.1 + 0.6) of the text's size after the `[`, for `[ ]`, `[x]` and `[X]` alike, so ticking moves nothing | the characters, with the cursor on them; from anywhere else on the row the box stays drawn and is ticked with the keyboard left in the note |
| A todo's `!!`, `due:2026-10-14`, `done:2026-10-10x12` | a chip exactly as wide as the token (`keepsWidth`) | the token, with the cursor on it |
| A todo's `every:2w` | a chip in words, as wide as they are | the token, with the cursor on it: what follows it on its row moves by the difference, and nothing else does |
| `**`, `` ` ``, `~~`, a link's address, a formula in a line | taken out of the line. A formula sits on the line's baseline where KaTeX puts it, and each of its parts gives back in its margins the height its strut takes, so the line is no taller and a tall one reaches over its neighbours | put back, for that one construct: the words after it on the line move along by their width, and the words before it stay |
| A block of math | the formula, in the room its lines take when written, wrapped rows and blank lines counted | its lines, the last padded to the formula's height |
| A table | a table, always, under its own lines, which are out of sight | still a table: a click in a cell is typed where it is drawn, the cell held at the size it was drawn while it shows its source. The cursor moved into the table's lines with the keys shows them as written above the table, which stays the element it was and follows what is typed; what follows is lower by those lines and nothing else moves |
| A code block | code, always | the same: only a fence line changes, as above |
| A list item's wrapped rows | start under the first letter of its words: the line is padded by the width of its indent, mark and task box as written, and its first row pulled back by the same (`plugins/gfm/lists.ts`). Each level starts `STEP_EM` (1.5) of the text's size further in than the one above it, however little the note indents it: the indent is a box of that width with the note's own spaces in it | the same: the widths are the text's own and the level's, and a mark is as wide drawn as written. A line written under an item's words, indented to them, starts under them. An item in a quote is laid out as any line is |

One case moves, and is left that way on purpose: the marks inside a line are taken out when it is drawn, so a paragraph that fills its rows can need more rows with the marks of the construct under the cursor put back, and the lines after it move down by those rows while the cursor is on it. Measured on a three-sentence paragraph with bold, code and a link in each: 2 rows (47px) in a 720px column, 5 rows (118px) in a 314px one. Showing the line as written and moving nothing can't both hold there. The layout test asserts what is kept: the paragraph starts where it did, grows by whole rows, and everything after it moves by exactly that.

A background painted on a line or on words in it must let what is under it show (`--code-bg` is a tint, not a flat color). With vim on the editor draws the selection itself, in a layer behind the text, and a flat background would cover it: `test/browser/vim-selection.spec.ts` reads the painted color over a code block. A box inside a list item's line (an `inline-block`) must set `text-indent: 0`, or it takes the line's pull for its own first row; the line's direct children already do.

A formula's drawn height is kept in the plugin's storage, so a block of math has its room before KaTeX has loaded. The first time a formula is ever drawn in a browser, the lines after it move down once if it is taller than its lines. They never move up.

A table has two ways in. A click, or `tables.edit` (⌥⌘T), goes into its cells, and the arrows go through the rows from there and out past the first and last. From the line above or below, the arrow keys and vim's `j` and `k` go into the table's own lines, which are then shown as written above it and typed in as any lines are. A deletion that reaches into a table from outside (`3dd` from the line above) takes all of it; `dd` on one of its last lines while they are shown takes that line. Rows and columns are inserted and deleted from a cell's menu (a right-click, the menu key or Shift+F10; `actOnCell` in `plugins/tables/table.ts` is what each item does), from the palette for the cell last typed in (`tables.rowAbove` and the rest), and one plus on the table's bottom edge and one on its right edge add at the end. The table draws no other buttons. A line of plain words directly under a table, which GitHub reads as one more row, stays a line of text under the drawn table, so words typed after a table don't vanish into it.

A fold never hides an edit. It opens when the cursor lands in it, when a selection reaches into it, and when anything in it changes. Deleting a folded bullet's line leaves what was under it, shown.

### Chips

A token that is drawn as something else and edits its own source is a chip (`plugins/lib/chips.ts`). The checkbox, the formula, a link to a note, and a todo's options are chips, and a mention will be:

```ts
const checkbox: Chip<Checkbox> = {
  id: "task",
  find: (line, offset) => checkboxIn(line, offset), // the tokens on one line, with where they are
  keepsWidth: true,                                 // as wide as its source, for a chip at the start of a line
  draw(el, token, source) {
    const box = el.appendChild(document.createElement("input"));
    box.type = "checkbox";
    box.checked = token.checked;
    box.disabled = source.readOnly;
    box.addEventListener("change", () => source.rewrite(box.checked ? "[x]" : "[ ]"));
  },
};
host.editorExtensions.register({ id: "todos", extension: chips(checkbox) });
```

A chip is drawn again when the note writes its token another way. One that also shows something from outside the note, such as a linked note's title or today's date, gives `key(token)`, a string of what it read: the chip is drawn again when that changes. To have it asked when nothing in the note changed, dispatch `redraw` (from `plugins/lib/live.ts`) to the editor.

`chips` draws the tokens on screen, leaves the ones in code and the one the cursor is on as written, and hands `draw` a `source`: `rewrite(text)` writes the token another way, as the member's edit, and does nothing when the note no longer writes the token as it was drawn; `rewriteLine(next)` does the same for a change that reaches past the token, handing `next` the token's line and writing what it answers, which is how taking a todo's due date away takes the space before it; `edit()` puts the cursor after it, or `edit(offset)` that far into it; `line()` answers the token's line as the editor has it now, `{ index, text }` with the index counted from 0, which is what an operation that finds a todo by its line is handed, and is undefined once the note writes the token another way.

A chip with `written: "within"` is shown as written only while the member is working inside the token itself: a cursor past its first character and before its last, or a selection of part of it. A selection that covers all of it, as selecting a paragraph does, leaves it drawn. The rest of its line stays drawn while the member types on it. It is for a token nobody reads as written, which a link is (`[[k3j5h8d9f0a1]]`) and a mention will be. On a line with several links, the one the cursor is in is shown as written and the others stay drawn, so the only thing that moves is what follows that one link on its line, by the difference in width between the id and the title. Coming to the line, typing on it, and leaving it move nothing. `test/browser/links.spec.ts` measures both.

Such a chip is one thing to the keyboard while it is drawn. A selection that reaches into it takes all of it, and a deletion of any part of it, Backspace at its edge or vim's `x`, `dw`, `cw` or a visual `d`, deletes all of it, so half a token with a raw id is never left in the prose. It is a transaction filter in `chips`, not `EditorView.atomicRanges`, because vim works out its own ranges and never asks. Server changes, undo and redo, and the chip's own `rewrite` pass through untouched. A cursor with nothing selected is let in, by an arrow key or vim's `h`, `l` and `w`, which shows the token as written to be edited as text, and arrowing out draws it again. `source.edit(offset)` from the chip, as a click on a mention does, and `editWithin(chip, view, fromEnd)`, which the command `links.edit` (Alt+Enter with the cursor beside a link) runs, go straight to a place inside. A click on a drawn link follows it instead: see `plugins/links/drawing.ts`.

A chip is not drawn in what the editor's parse calls code. `inCode: true` leaves that to the chip's own `skip`, for one that has a better reading of code than the parse. Draw with elements and `textContent` only. Nothing from a note is ever set as HTML: HTML in a note stays text, and KaTeX is run with `trust` off (`plugins/math/options.ts`), so a formula can't make a link or load an image.

### Todos

The todos plugin (`plugins/todos/`) is the pattern for options written as tokens on a line. `parseTodo` and `rewriteTodo` from the plugin API read and rewrite a line, and `tagsOn` reads the tags written on one, the same functions the core indexes todos with (`docs/todos.md`). `plugins/lib/todoLines.ts` keeps where `todosIn` finds a todo in the whole text in a state field, and each chip is `inCode: true` with a `skip` that asks it, so a todo is drawn on exactly the lines the server lists. Each chip is shown as written only while the cursor is on its own token, so the rest of the line stays drawn, and each but the Repeat chip is `keepsWidth`, so its line never changes width. A click on a chip opens `ChipMenu` (`plugins/todos/ChipMenu.tsx`) in `openPopover` (`plugins/lib/Popover.tsx`) under it, the same component the Todos page opens from its chips; a mousedown on the chip is prevented, so the cursor stays where it was and the line stays drawn. `openPopover`'s fourth argument, `onClosed(hadFocus)`, is told when the popover has gone however that came about; the editor gives the keyboard back to the note there. A viewer's chip opens nothing. The token the cursor is on is marked `md-todo-token`, which keeps it from wrapping in the middle as its chip can't.

The plugin API has what reads and writes a todo, each the core's own function: `parseTodo`, `rewriteTodo`, `todosIn`, `locateTodo`, `changeTodo(line, change, on)`, which is the line `todo.set` leaves, and `completeTodo(line, on)`, which is what checking a todo off on a day leaves: for a repeating todo the open line with its next due date and `done:` mark, and the checked line that gets filed. For a repeat it has `parseRule`, `writeRule`, `describeRule`, `nextDue`, `WEEKDAYS` and the types `Rule`, `Unit` and `Weekday` (`src/core/recurrence.ts`). `today()` and `dayOf(date)` are the member's calendar day in this browser's time zone, which is the day every completion made in the app is said to be on. `TodoCompletion` is one entry of what `todo.history` answers.

Two chips are for a todo that repeats. The Repeat chip over `every:<rule>` says the rule in a few words from the core's `ruleLabel`, with `describeRule` as its name. Its words are longer than its token, so it is the one todo chip without `keepsWidth`: it takes its own width, and what follows it on its row moves by the difference when the token is shown. It is the third `ChipKind`, `"every"` (`plugins/todos/picking.ts`), and opens `ChipMenu` as the due date and priority chips do, which draws `RepeatMenu` for it: one column, the rule in words and its next dates at the head, then the rules `repeats(due)` lists (Doesn't repeat, Daily, Weekdays, Weekly on the due date's weekday, Monthly on its day, Yearly, Custom) with a check on the one in force, and under them, while Custom is checked, the form (`RuleFields` in `plugins/todos/RuleEditor.tsx`) that builds any rule the token can write as a sentence, kept as one `RuleForm` value that `ruleOf` turns into a `Rule` (`plugins/todos/recurrence.ts`, tested in `test/core/plugin-recurrence-form.test.ts`). A pick checks a rule and closes nothing; Done saves it with `onPick`, and Cancel is `ChipMenu`'s `onClose`. Skipping is in the due date's popover, "Skip to" the next date, for a todo that repeats. A pick in a note is `changeTodo(line, change, today)`, which is `todo.set`'s own: setting is `rewriteTodo`, skipping `skipTodo`, and Doesn't repeat takes the token away. "Edit as text" is `source.edit()`. The last-done chip over `done:YYYY-MM-DDxN` says the day and the count, and opens the todo's completions from `todo.history`: the day, who did it, and its daily note a click away. That chip works for a viewer too, since it changes nothing. In a note neither is a stop for Tab, as the due date and priority chips are not: the keyboard reaches a todo's options by putting the cursor on the token. Each opens a panel with `openPopover(anchor, label, content)` from `plugins/lib/Popover.tsx`: an element of its own at the end of the page, laid over the app and placed under the chip, which takes no room in the note. Where it fits neither under nor over its chip it goes on the side with more room, as tall as that room, and scrolls, so it never covers its chip. It closes on Escape and on a press outside through `useDismiss`, and when its chip is gone. On the Todos page both are chips to press too, and the row is marked while either's popover is open (`Opened` in `picking.ts` is a `RowChip` or `"done"`). The Repeat chip is on every row the member can change, set or not: unset, it is the quiet dashed "Repeat" pill, as Add date and Add tag are, and opens the same popover on Doesn't repeat.

The checkbox chip writes `[x]` on an open todo, or `[ ]` on any other, and then calls `app.saveNote(noteId)`, which sends what is typed in that note's editor at once instead of after the pause in typing, so the write holds the check and not what the member types on the line a moment later. `saveNote` answers with the note as that write left it, or with nothing when there was nothing to send: its `filed` says the write completed a repeating todo, and its `revision` is the change the toast's Undo reverts. The server completes a repeating todo whose box a write checked, files the line on the member's daily note in the same step, and answers with the line rolled forward, which the editor takes as it takes any merge. So typing `x`, vim, and the chip are one path, and nothing in the browser decides what a completion is. Every `note.write` and `todo.set` the app sends carries `on`, the member's day (`src/web/sync.ts`). When an answer says `filed`, or `unfiled` as an undo of a completion does, the app reads its notes and folders again and an open editor of each daily note takes what was filed on it or taken off it.

`todo.history` finds the todo by `revision`, `line` and `text`. From the editor the chip sends the revision the app knows for the note with `source.line()`. The host saves what is typed before it asks, so that revision can be one behind: the server then refuses, and the chip asks once more at the revision `note.read` answers.

The Todos page changes a todo through `host.perform({ type: "todo.set", … })`. The host saves what is typed in that note's editor first and hands the editor the result, as it does for a move through history. A click on a todo opens its note and puts the cursor on its line: the plugin keeps the todo it is going to, and the editor extension it registers for that note places the cursor when the editor is there.

A todo's row on the Todos page has its checkbox, its words and its note's name on one line, and a chip for each thing set on it, and a quiet one for each thing not set, on a second line under the words. Each chip is its own control and opens its popover under itself; the page keeps one small piece of state, which todo's chip is open (`picking` in `plugins/todos/picking.ts`, with what each chip offers in `choicesFor`), and marks that row. Everything else is the app's `ContextMenu` (`plugins/lib/Menu.tsx`), which a right-click on the row and the menu key or Shift+F10 open; an item with `separated` has a line before it, and Up, Down, Home and End move through the items. A page with rows of its own should keep to the same: what is shown is what is pressed, and the rest is behind one menu, not a row of buttons. The one exception is the two a todo's state takes most often, Abandon and Move to backlog, which sit quiet on the second line after what is set and before what isn't, and show only while the row is pointed at or has the keyboard, as a chip not set does.

Checking a todo off shows a notice with Undo, from the page and from a note's checkbox alike, and so does abandoning one or moving it to the backlog on the page: `putAway` in `plugins/todos/completed.ts`, which calls `app.notify` with the state's icon and words ("Task completed", "Task abandoned", "Task moved to the backlog", from `PUTTING` in `picking.ts`) and Undo. Its `undo` answers with what to say when it couldn't be done, which the card then says. Undo here is an ordinary change by the same path the tick took: `todo.set` with the state the todo had before on the page, and in a note an edit to the line the editor has followed since (`untick`), so it is in History and Ctrl+Z takes it back. When the line is no longer the todo that was checked off, nothing is written and the toast says so. A repeating todo checked off stays open, and its toast's Undo reverts the change that completed it, which takes the filed line and the completion back with it.

### Daily notes

The Blame plugin (`plugins/blame/`, id `blame`) is Blame mode, once called Who wrote this: Toggle blame mode (`history.whoWrote`, the id it had in History, so a member's keys for it carry over), Next change in blame (`history.whoWroteNext`) and Previous change in blame (`history.whoWrotePrevious`), none with keys of its own. It shares `plugins/lib/blameLink.ts` with History, which draws its switch in a note's History panel while Blame is on and opens the change a run is pressed for. A command may list `aliases`, other names the command palette finds it by: Toggle blame mode is found by "who wrote this" and "who changed what".

The daily plugin (`plugins/daily/`) declares the three settings the server makes a daily note by, under the keys in `DAILY_SETTINGS` from the plugin API, so the name the server reads and the name the member is shown can't drift: `daily.folder`, `daily.private` and `daily.timeZone`. `daily.folder` is a `folder` setting whose default is Daily. Its page at `/today` is the Today link in the sidebar. It performs `daily.open` with `today()`, tells the app about the note, has it read the folders and notes again, and puts the note at the page's own place in the browser's history with `app.show({ kind: "note", id }, { replace: true })`, so Back goes to where the member was. The command `daily.today` goes to that page. A refusal, as a viewer gets, is shown on the page in the server's words. It adds the commands `daily.yesterday`, `daily.tomorrow`, `daily.previous` and `daily.next`, with no default keys. The day is the browser's, as `today()` is. Previous and next count from the daily note in front, or from today on any other note. Today's and tomorrow's note are opened with `daily.open`. Any other day is looked up with `daily.find`, and a miss is said with `app.notify` as "No note for <date>". An editor extension draws ‹ › after a daily note's date heading, which show on hover or focus. They are drawn only after `daily.find` confirms the note is the member's daily note for that date.

### Dashboard

The Dashboard plugin (`plugins/dashboard/`) is the page at `/dashboard` and the home page (`home: true`), and the pattern for a view made of other views' operations. At `/` with no tab open the Tabs plugin opens the home page in a tab of its own, a preview as any page's first tab is, so it is focused, dragged into a split and replaced by the next page looked at like any other. Closing that tab leaves the editor area empty until something else is opened and closed. With Tabs off the core draws the home page at `/` alone. It asks nothing new of the notes: events are `event.list` over the member's day, todos are `todo.list` with `dueTo` that day, the notes created or edited today are read off `app.notes`, the daily note is `daily.find`, which makes nothing, and the summary is `visit.read` and then `history.list` with `from`, `to` and `notAuthors` naming the member. So the resolver decides everything on it, a guest's is what they were granted, and nothing there counts or names a note the member can't see. An agent limited to folders gets the pins and changes inside them, takes no pin from a note outside, and is refused `visit.read` and `daily.find`, which are the member's own and in no folder. The link from the summary goes to History as it is, which lists by time.

`today.ts` is what "today" means, as pure functions tested in `test/core/plugin-dashboard.test.ts`: `todayAt(now, timeZone)` is the member's date and the two instants it runs between, `aheadToday` keeps the all-day events on that date and the events that haven't ended, `editedToday` keeps the live notes whose `createdAt` or `updatedAt` is in the day, and `summarize` sums changes up by note and author. The page reads `now` with `useNow()`, so an event drops off when it ends and every section reads again at the member's midnight.

Each panel reads on its own with `useRead(read, { key, stamp })`, which keeps what it read before on show until the next answer is there. The key is the member's date; the stamp is what can change that panel's answer, read off `app.notes`: notes with an open todo for the todos, notes coming into or out of sight for the daily note and the pins, a change by someone else for the summary. A changed stamp is read again at most once in 30 seconds, or at once when the member comes back to the window, so the member's own typing reads nothing and nothing polls. A card is its full size from the first, with bars where its rows will be, and what it lists scrolls inside it: no section moves when another's answer arrives. `test/browser/dashboard.spec.ts` holds every answer back and measures that.

A note is opened with `app.openNote(id, { preview: true })`, as a single click anywhere does. A todo is opened on its line with `todoOpener(host)` from `plugins/lib/openTodo.ts`, which the Todos page uses too: it keeps the todo it is going to, and the editor extension it registers places the cursor once that note's editor is there.

Pins are the member's own, kept by the server (`pin.list`, `pin.set`) and held in the browser by `pinsOf(host)` (`pins.ts`), one store for the page and for the `mark` in a note's bar. The mark is drawn from the first, disabled until the pins are read, so nothing beside it moves. The page lists the pinned notes that `app.notes` says are live, so a pin leaves it the moment the app learns its note was archived, trashed or hidden.

The last visit moves only on Mark as read, which hands `visit.mark` the `now` of the `visit.read` the summary on screen was made from. The summary reads the latest hundred changes and no more; past that each count says it is the least it can be, and the card points at the History page.

The member picks the panels and arranges them. `PANELS` in `Dashboard.tsx` is every panel there is, each an id, a title, the size it is added at, and how it is drawn: the five above, Coming up (`event.list` over the seven days after today) and Recently edited (off `app.notes`). Which are shown, in what order and at what size is the layout, `{ id, size }[]` in `layout.ts`, changed only by `arrange(layout, action)` (move, resize, add, remove) and kept as the plugin's one `remembered` setting, `dashboard.layout`, a list of words such as `changes wide`. So it is on the server with the member's settings, the same in every browser, theirs alone, and changed by no agent and no other plugin. `readLayout` makes what it reads sound: a panel there isn't is left out, one named twice is shown once, a size that isn't one is the panel's own. Panels flow into two columns in that order, one column in a narrow window; small is a cell, wide two columns, tall two rows, large both. Edit dashboard is the one control on the page; it opens arranging, left by Done or Escape, where each panel has a grip (dragged, or the arrow keys, Home and End), a corner (dragged to the columns and rows it reaches, or the arrow keys: right and left for its width, down and up for its height) and a remove button, and the page has Add panel and Reset. While arranging a panel's own controls are inert, and a drag shows the layout as it would be dropped and saves only on release; Escape puts it back. The drag itself is `followDrag` in `plugins/lib/dragging.ts`: a press, a threshold, the pointer followed on the window (a drop preview moves the pressed element, which would lose a pointer capture) and Escape, with where it lands left to the caller, so tabs, cards or a board could use it by drawing their own drop preview from the pointer.

### Archive and Trash

The Archive and Trash plugin (`plugins/trash/`) is a note's life after it is written. `plugins/lib/lifecycle.ts` holds the steps (`setArchived`, `trash`, `restore`, `purge`) and the menu items a folder's list and a tab's menu offer, so every place that can archive or trash a note does it the same way: perform the operation, hand the answer to `app.noteChanged`, `app.refresh()` for the folder counts, and say a refusal in a notice in the server's words. Moving a note to Trash shows the notice "Moved to Trash" with Undo, which restores it, and archiving one shows "Archived" with Undo, which brings it back. A card in a folder's list has an Archive button in its corner beside its menu (one click, with Undo; Unarchive on an archived note), Archive and Move to Trash in the menu, and Archive as the `E` key while the card has the keyboard. A `MenuItem` may carry an `icon`, drawn before its label, and a menu with one has room for it in every row. The menu's items are a table in `plugins/noteCard.ts` (`cardItems`): an item the person may not use is left out, not greyed. A card's note is read and drawn only once the card comes within `NEAR_PX` of the list's window, and who has edited the notes that are drawn is one `history.summary` for all of them. The command `note.toggleArchived` (`mod+shift+e`) and `note.trash` (no key) act on the open note.

The app itself, not the plugin, makes an editor on a note in Trash read-only and stops sending what was typed in it, since the server would refuse it: that has to hold with the plugin off. Typing that wasn't saved before the app learned the note was trashed stays in the editor, the bar says it isn't saved, and it is sent when the note is restored. The plugin adds what the member sees and does: the banner with the days left, Restore, and Delete forever, and the page at `/trash`, last under More. Delete forever is offered to an admin and to an editor, since the app can't know who made a note, and a refusal is shown in the server's words.

### Uploads

The uploads plugin (`plugins/uploads/`) is everything about files: five embeds, the ways a file gets into a note, and the Uploads page. A note refers to an upload by id and never by name, written by `writtenUpload` and read by `uploadIn` and `sizeIn` from the plugin API, the functions the core reads a note's uploads with:

- `::image{id 640x480}` and `::video{id 640x360}` are shown below their line, in a room read from the size after the id (`boxFor` in `sizing.ts`): the column's whole width, never wider than the size written, at its shape. An optional word after the size, `small`, `medium` or `large`, or a whole percent from `1%` to `100%` (`shareIn`, `withShare`), draws it a third, a half, three quarters or that percent of the column wide, still never wider than the size written; no such word, `full`, or any other word is the whole column. The first such word after the id is the one read, and writing another width puts it right after the size and keeps every other word, so what a later feature adds to the embed survives a resize. The app writes a size word where the width is one at a whole percent, `33%` being `small`. A picture's `crop=X,Y,WIDTH,HEIGHT` (`cropIn`, `withCrop`) draws only that part of it, in the pixels of the size after the id from its top left corner, written after the size, and after the width where that follows the size; its room is the crop's shape and no wider than the crop, so the size handle and its ghost follow it. Only as much of a crop as is in the picture is read, and one of all of it is none. A video's crop word is not read. With no size the room is at most 480 by 270. The size is written when the file is sent, the server's reading of a picture's bytes or else the browser's own measurement taken before sending, so the room is whole before a byte of the picture arrives and nothing moves when it loads. A picture is an `<img>`, a video a `<video controls preload="metadata">`: nothing plays until asked, and nothing is ever an `<object>`, an `<embed>`, a frame, or markup built from what the server said.
- `::audio{id}` is below its line at a fixed 56 pixels, an `<audio controls preload="none">`, with no border.
- `::drawing{id 820x460}` is an Excalidraw drawing, shown below its line as a picture in a room read as a picture's is, with the same size handle. Its upload, `Drawing.excalidraw`, is the scene as Excalidraw writes its file, JSON an agent reads and Excalidraw opens, with `preview`: a PNG of it as a `data:` address and the fingerprint of the elements it is of (`scenes.ts`). The embed reads the scene with `host.uploads.bytes` and shows the PNG, or, where there is none or it is of other elements, as for a scene an agent wrote, the one Excalidraw draws of the elements then (`pictured`). A member who can change the note has an Edit drawing button where a picture has Crop, which opens Excalidraw over the whole window (`editScene` in `excalidraw.tsx`), with Save and Cancel above it. Every key is Excalidraw's there: the app's keys pass over what is in `[data-keeps-keys]`, and what is behind it is inert. It is not a modal `<dialog>`, since Excalidraw puts its own dialogs, menus and tooltips at the end of the page, where a modal dialog would hide them. Save draws the PNG, at twice the size written and no more than 4096 pixels on a side, sends the scene with it as a new upload in the note's folder, private where the note is, and writes its id and size into the embed with `withUpload`, keeping the width: one change by the member, which undo takes back to the drawing before. The editor stays open until the embed names the upload, and says in its bar why it didn't: a refusal, or a note that changed meanwhile. A scene with no fresh picture is drawn by Excalidraw for each reader, share pages too, until a member saves it. `::drawing{}` keeps 120 pixels for a button that draws it, and is what the `/` menu's Drawing writes, among the upload entries. A picture of a scene is a PNG and not SVG because an SVG would carry Excalidraw's fonts only as Excalidraw cuts them down, which compiles WebAssembly and evaluates code the page's policy refuses. Excalidraw is imported by `import()` from `drawings.ts` the first time a drawing is edited or drawn from its scene, a chunk of its own, and its fonts are the app's own assets at `/assets/excalidraw-<version>/`, which `vite.config.ts` writes and serves; it takes Excalidraw's CDN out of where a font is loaded from, and fails the build for a version that adds one some other way.
- `::file{id}` among words is a chip with the file's name and size, which opens it as its file class opens (`openUpload`). On a line of its own it is a file card below the line (`below.alone`): a head of its name (which opens it), its size and what the preview says (`5 pages, the first 3 shown`), and a Download that shows on hover or focus, over a file preview (`drawPreview` in `previews.ts`, the kinds in `previewing.ts`): the first three pages of a PDF, a picture, a player, the first six rows of a CSV or TSV, the first eight lines of other text, or nothing under the head for a file with no preview. The card's height is known from what the note was told of the file (`cardHeight` in `sizing.ts`), so nothing moves while it loads; text shorter than its room shrinks the card once. Pressing the preview, or Enter on it, shows it larger over the app (`previewUpload`). Text is put in the page only as text, and a PDF only as canvases: pdf.js is imported by `import()` from `pdf.ts` the first time a PDF is shown, with its worker from the app's own assets, scripting and XFA off and no layer to press. The Uploads page's panel leads with the same preview, at the size of its place (`SHOWS`), and the overlay draws up to 30 pages, 200 rows or 400 lines, with Download, Open for text, and Open in a tab for a PDF where there is a site kept for files.

A picture, a video, a recording and a drawing are the thing itself: none has `render`, so nothing of it is in its line until the cursor is on it, and the host draws no frame around it. Its name, kind, size and bytes are its tooltip. A picture, a video and a drawing have one size handle on their right edge (`handle.ts`), seen on hover or focus, for a member who can change the note: a drag shows the width it will draw, any whole percent of the column from 10% to the picture's widest (`dragged`), snapping to a size word's width within 12 pixels of it unless Shift is held, and writes it on release; at its widest it writes nothing, the whole column. On the keyboard it is a slider whose value is the percent, which the arrow keys step by 5% (1% with Shift), stopping at a third (`stepped`), and Home and End take to 10% and the whole column. A picture also has a Crop button at its top right, seen with the handle (`cropButton` in `drawing.ts`), which opens the whole picture in a dialog over the app (`cropPicture` in `cropper.ts`): a rectangle, dimmed outside, whose corners and edges are dragged to size it and whose inside is dragged to move it, held to Free, Square, 4:3 or 16:9 (turned to stand as the rectangle does), with the geometry in `cropping.ts`. The rectangle is a group whose arrow keys move it, and each edge is a slider whose arrow keys move it; Shift steps ten times as far. Enter or Done writes the crop, Reset removes it, and Escape or Cancel writes nothing. The picture is drawn in a frame of its room (`.upload-picture`), larger by as much as the crop is smaller and moved by where it starts (`placed`), so nothing is cut from the file. The width and the crop are written with `update`, one change by the member that History records and undo takes back, and what was drawn is kept (`BelowDrawn.update`), so a video playing goes on playing and the handle keeps the keyboard. A video shows its first frame before it is played.

What an embed knows of its upload is `host.uploads.referred(id)`, which the app fills from each read of a note before the note's editor is made. An id nothing was said of, as one typed into a note since it was read, is asked about once with `upload.read`. Each drawing is made once and made again only when what is known of its own upload changes (`live` in `drawing.ts`), so typing elsewhere, the cursor, and other uploads' news leave a picture and a playing video alone. Three things are drawn in place of the file, in the same room:

- For `null`, "This file isn't available", and nothing else: not the name, the type or the size, and its bytes are never asked for. A reader can't tell a file that was deleted from one they may not see.
- For one in Trash, "This file is in Trash" and its name, to those who can see it. An archived upload shows as usual.
- For one whose bytes then fail to load, the first again.

A file gets into a note by a paste, a drop, or one of the four Upload entries in the `/` menu (`sending.ts`, an editor extension made per note). `pastedFiles` in `pasting.ts` says which pastes are files: any that carry a file, except one that also carries text both plain and formatted, which is what a spreadsheet or a document copies beside a picture of the cells. Pasted text is left to the editor. The file goes to the note's own folder, and private when the note is private, so a picture isn't shown to people the note is hidden from. A file over `MAX_UPLOAD_BYTES` (25 GB) is refused in the browser before any of it is sent, and the server's own refusal is said as it gave it, both through `app.notify`. The bottom bar says how far a file has got. A file of up to 8 MB goes in one request, and once the server has it the embed is written on a line of its own where the file was put (the place is kept through whatever is typed meanwhile), as one edit by the member with the user event `input.paste` or `input.drop`. A larger one goes in parts (`host.uploads.send`'s `onStarted`, ADR 13): its embed is written the same way as soon as the server gives it an id, and the room its line keeps shows its name, how far it has got and a bar (`OnTheWay` in `drawing.ts`) until it is there, when the picture, player or card takes the room.

Uploads are listed on the Uploads page (`/uploads`, and `/uploads/<id>` with one selected) and nowhere else: a folder's list and the folder counts are of notes. It has one "Upload files", and a file sent from it, or dropped on it, is private to the member in no folder until it is put in a note (`upload.place`). Each row says who uploaded it ("You" for the member, `uploaderWords`) and how far it is seen (`reachWords`): "Only you", "In 1 note" or "In N notes" by `upload.list`'s `uses`, or "Not in a note". The page is found by the query language with `QueryBar` at `scope="uploads"`, beside Mine and Everyone's, a switch that writes `uploader:@me` into the query or takes it out (`withMine` and `onlyMine` in `finding.ts`); kind, folder, archived and the rest are the builder's. For the selected upload it shows a preview, what it is, the notes that use it, Open (`openUpload` in `opening.ts`), and one "…" menu, which Shift+F10 or the menu key in the card opens too: Download, Share… (the Share dialog), Copy embed, Move to folder… (a second menu of the folders), Make private or Share with the folder, Archive or Unarchive, and Move to Trash (which says first how many notes use it). Trash lists trashed uploads beside trashed notes. Quick open offers uploads by file name after the notes (`openable`), so the notes are ranked among themselves as they are without uploads, and picking one opens the Uploads page on it.

A link's page (`SharedPage.tsx`) starts `uploadDrawing`, the four embeds alone. There `host.uploads.address` is `/api/shared/<token>/uploads/<id>`, `referred` is what `shared.read` said and `null` for anything else, and there is no `send`. A link on a note opens none of the uploads the note refers to, so each is the "isn't available" placeholder. A link on a folder opens the uploads in that folder and below it.

### Links to notes

The links plugin (`plugins/links/`) is the pattern for anything a note stores by id and shows by name. The note says `[[id]]` or `[[id|display text]]` (`docs/adr/0001-links-stored-by-id.md`); `linksOn` and `linksIn` from the plugin API read them, the same functions the core records backlinks with. The editor keeps `linksIn` of the whole text in a state field and draws exactly those, so what is drawn as a link is what the server records as one: text in a fence or in inline code is not, and an indented line is, since a bullet nested three deep is indented as far as a code block. The chip's `key` is the target's title and state from `host.app().notes` and `host.app().trashed`, and `host.onNotes` dispatches `redraw` to the open editors when any of them changed. A link to an archived note reads and opens as any link, and says "Archived" when hovered. A link to a note in Trash reads as its title followed by "(in Trash)", in the line's own size so the line is no taller, and still opens the note. A target that is in neither list is drawn as "Unavailable note" and goes nowhere: that is the one wording for a note removed from Trash, one that never was, and one the member can't see, and the app never has that note's title to leak. `plugins/links/words.ts` holds the wording. The `[[` list is a listing, so it leaves archived notes out. The `[[` list is a completion with `spaces` and `anywhere`; text after a `|` is taken as the link's display text while the list goes on narrowing by what came before it.

A link to a folder is `[[folder:id]]`, or `[[folder:id|display text]]`, written by the folder's id as a note's link is by the note's, so it follows the folder through every rename and move (`linkedFolder` and `writtenFolderLink` in `src/core/links.ts`). The server leaves it as written: it is no note's title to resolve, and no backlink. The editor draws it as a note's link is, as the folder's name now from `host.app().folders`, and redraws it when a folder is renamed; a click opens the folder's list with `app.openFolder`, and hovering it says it is a folder. A folder the member can't see, or one deleted, reads "Unavailable folder". `@` is the way to write one; `[[` lists notes only.

Following a link is the command `links.follow`, which opens the note the cursor is on a link to, through `app.openNote` as any note is opened, or opens a web address in a new tab with `noopener` when it starts `http://`, `https://`, or `mailto:`. Vim's `gd` runs that command, and so can a keybinding. On a mention, a reference or a file, which a click opens, `gd` does what the click does: an editor extension gives `following` from the plugin API a function that does it where the cursor is on its kind of thing and answers whether it was, as mentions do, and an inline embed marks what to click with `data-follow`. Only where none answers yes does `gd` run `links.follow`. ⌘-click does the same for a link to a note, drawn or as written.

### Mentions

The mentions plugin (`plugins/mentions/`) registers the `@` completion, the chip that draws a mention, and the offer to share. A mention is a link to a person, `[[person:id]]` for a member and `[[person:Name]]` for anyone else, and `[[person:id|words]]` shows the words in place of the name (`docs/adr/0019-everything-a-note-opens-is-a-link.md`). `people.ts` is its pure part: what `@` offers for what was typed, how a mention is shown, and who a change newly mentions. The members come from `member.list`, read when the plugin starts and again when `@` is typed more than a minute later. The member's contacts come from one `contact.list` with no query, read when `@` is first typed and kept in memory for ten minutes; what is typed after `@` narrows them in the browser and is sent nowhere. A completion item's `tone` (`accent` or `muted`) colours its label, which is how members are in the theme colour and contacts gray. Where `member.list` is refused, for a guest and on a share link's page, there are no members and every mention is drawn as the name the note writes, and a member's id as "Someone". A member reading the id of someone who is no longer a member sees "A former member". The chip is `written: "within"`, as a link's is, with `key` the name it shows, so it is drawn again when the members are read again. On a todo's line it has the look of the todo's other chips. The offer to share is made from an `updateListener` that looks only at transactions with an `input` user event, so a change that arrives from the server asks nothing; it goes through `host.sharing` and `app.notify` with `stays`, and its switch is the plugin's `offerToShare` setting. A click on a drawn mention opens the person's page (`/person/<who>`, `PersonPage.tsx`, from `person.read`); the keys go into it to change it, and on a share link's page, where `app.go` is absent, a click is for the cursor. `fields.ts` says what a contact's card lists, one `Field` per label, lines one after another with the same label under it once, and is the pure part of editing one: `labelWords` is a line's label in plain words (Google's own from `CONTACT_LABELS` in the protocol, the member's own as written, the field's name for none), `labelChoices` what a line's label menu offers, and `typeOf` a label typed after Custom…, which is Google's own where it names one by its type or words in any case; `draftOf` a card is the form's state, and `changeOf` the card and the draft is the `ContactChange` that Save sends (only the fields that differ, each as a whole) or why it can't be saved. `ContactEditor.tsx` draws the contact on the page, each line in the form led by a quiet menu of its label whose Custom… puts a box in its place (Enter or leaving it keeps the label, Escape goes back), with Edit where its data source is `writable`, and "Connect again to edit contacts" where it is `reconnectToWrite` (a `source.connect` with `edit`); a picture is made at most 512 pixels a side as a JPEG in the browser and sent at once with `contact.photo`. A person who isn't among the member's contacts gets "Add to my contacts" (`contact.create`), into the first connected contacts data source that is `writable` (`addingTo` in `people.ts`). The page's open todos are the Todos page's rows (`TodoList` from `plugins/todos/Todos.tsx`, read for `person.read`'s `todoQuery`); a tag's chip there opens the Todos page narrowed to them and the tag. The page searches with the `QueryBar`, its query prefixed with the page's `mentions:`. Contacts lists each contact as a card that opens its page (`plugins/lib/person.ts`).

### `@`: everything to point at

`@` is one list of everything a note can point at, from five completions on the same trigger, each registered by the plugin that owns its kind and made from the same item producer as that kind's own way in: people from the mentions plugin (`offered` in `people.ts`), notes and folders from the links plugin (the item `[[` offers, and a link to a folder), uploads from the uploads plugin (`plugins/uploads/pointing.ts`), events from the calendar (the items `[[` offers), and days from the dates plugin (below). The list groups them by kind, People, Dates, Notes, Folders, Uploads, Events. `@` alone lists a few of each kind, as many as `AT_ALONE` in `plugins/lib/pointing.ts` says: three people, the member first, Today and Tomorrow, the three notes edited last other than the one being written in (which `items` is told), the two latest uploads, and the next two events of the connected calendars (`upcoming` in `plugins/calendar/finding.ts`). Typing narrows each. `@` alone also starts reading the contacts, the uploads and the events. Every completion on `@` answers at once, so the list takes Enter from its first key, and the member is among the members before `member.list` lands, so `@` and Enter writes their own mention however soon. What arrives later joins the open list: the uploads, the events and the contacts each ask it again with `reask` (`plugins/lib/reasking.ts`), which asks as a typed key does, at once, so the list never stops taking Enter, and keeps what the member highlighted. A highlight the list put on its first item of itself goes to the first item as it now is, so a contact that arrives ahead of the events `@sam` found is the one Enter takes; a row of a kind that waits, which only the member highlights, stays highlighted. An option is found again by its kind, label, colour and line, not its heading, which a list of one kind doesn't show. A list that isn't open stays shut, but for the contacts when a contact, or the offer to create one, would now be the first thing offered, so a list that matched nothing gains what the contacts were read for. `[[` instead waits up to 800 ms for the events, as it always has. What is typed is a name: a few words, no bracket or bar (`namable` in `plugins/lib/pointing.ts`). Notes and uploads are found by `pointed` there, which takes those with a word starting with each word typed, those that start with all of it first; events by the calendar's own `finding`, which reads a day too. `@` offers at most eight of each kind but people. Picking one writes what that kind's own way in writes: a mention, a link (`[[id]]`), an upload placed in the note (`upload.place`, `placedIn` in `plugins/uploads/inserting.tsx`, which "Insert an upload" uses too) and written as pasting would, a picture, a video or a recording on a line of its own and a file as a chip among the words, and an event's reference. The uploads are the latest 500 the member can see, read again each time `@` is typed alone, unless they were read in the last five seconds, and kept in memory, so what is typed after it is sent nowhere. A member's preview is their role and the email the member list told; a contact has none, since a contact's email is never put on the page. A note's is its first lines (`snippet`), an upload's its picture and who sent it when, and an event's when it is, start to end, and where. `@` lists folders too, under Folders after the notes, at most eight, and none for `@` alone (`foldersAt` in `plugins/links/folderPaths.ts`): found by `pointed` by name, or, where what is typed has a slash, by path, the last part matched against the folder's name and each part before it, in order, against the folders it is in, so `proj/gar` finds Projects/Garden and `proj/` lists every folder inside Projects; each says the folder it is in, and picking one writes a link to the folder, `[[folder:id]]` (below). Where no note listed is titled what was typed, ignoring case, and it can be a name with a letter in it (`newTitle` in `plugins/links/creating.ts`), `@` ends with Create note “…”, of the kind that waits, as Create contact is, and only where the member can make a note in front (`app.canCreateNote`). Picked, it makes a note whose text is that title as its heading, in the folder of the note being written in where the member may add to it and otherwise where the server puts a note with no folder, tells the app with `noteChanged`, says so with a way to open it, and writes a link to it. `@` offers to create a tag too, last of what is new (`tagAt` in `plugins/tags/completing.ts`, a completion of the tags plugin's with `order: 2`): Create tag #name, where what is typed is one word that can be a tag's name and no tag is named that, ignoring case. Picked, it writes `#name` in place of `@` and the name. Between creating a note and creating a tag, the links plugin offers Create folder “…” (`newFolderPath` in `plugins/links/folderPaths.ts`): what is typed is a name, made at the top, or a path such as `Projects/Garden`, whose folders already there from the top down, ignoring case, are used again and the rest made inside them. It is offered where some part of the path isn't there, every part is a name with a letter or a digit, and the member may make it there: `app.canEdit`, and edit access to the last folder there, or not a guest for one at the top. Its line says where it goes, "New folder in Projects", or "New folder at the top". Picked, it sends `folder.create` for each folder to make, inside the one before, with `ifExists: "return"`, so a folder made meanwhile is used, reads the folders again with `app.refresh()` and waits, up to three seconds, for the app to hold the last of them, so its link reads as its name from the first, says "Created folder …" with Open, and writes a link to the last. Where a part fails, as one too deep does, those made before it are read again and nothing is written. A guest is offered no note to create with nowhere beside the note they are in that they may add to. So `@compost` ends with Create contact “compost”, Create note “compost”, Create folder “compost” and Create tag #compost, in that order.

Where no member or contact is named what is typed, ignoring case, and it has a letter and is a name, the mentions plugin offers, after everyone it found, "Create contact “<typed>”", described "New contact in <source>", in the member's first connected contacts data source that is `writable` (`addingTo`). It is offered only once the contacts are read whole (`contact.list` with `more` false), so finding nobody among them means there is nobody, and not at all where no contacts data source takes changes, as Google's doesn't until the member connects it again to edit. Nor is it offered until the members are read, or refused, so a member's name typed early isn't taken for nobody. Its kind is `new`, the last row of `COMPLETION_KINDS`, so it comes after every person, day, note, upload and event the list holds, and that kind `waits`: Enter never takes it, so `@home` and Enter at the end of a line is still a new line, and Tab or an arrow key picks it. A name that is someone's whole name, such as `sam okafor` with Sam Okafor among the contacts, is that person, so it can't be created from `@`; one that only starts it, such as `Sam`, can be, below Sam Okafor. Picking it sends `contact.create` with the name alone, once however often it is picked while that is on its way, adds the contact to those kept in memory, kept there until a read of the contacts holds it, writes `[[person:name]]` as picking a contact does, and says "Created contact <name>" with Open, to the person's page, where a typo is put right; a refusal or a failure says why and writes nothing. Undo takes out the mention and leaves the contact.

### Dates

The dates plugin (`plugins/dates/`) offers days on `@` and draws the days a note writes. `when.ts` is its pure part, tested in `test/core/plugin-dates.test.ts`. `saidFor(typed, now, order)` is what `@` offers for what was typed, best first: today, tomorrow and yesterday by any start of their names; a weekday, the coming one and never today; `next` and a weekday, that day of next week, which starts on the Monday after today's, offered only once `next` is typed whole; `now`; a date by its month's name either side of the day (`oct 21`, `21st october`), in the year that puts it nearest today unless a year is given (Feb 29 the nearest leap year's); a date in numbers (`10/21`, `10/21/27`) in the order the member's locale writes month and day (`orderIn`); an ISO date; and any of them with a time before or after it (`3pm`, `3:30 pm`, `15:30`, `noon`, `at 3pm`). A time alone is today's, and hours with no am or pm are a number, not a time. "Today" is the browser's day, as `today()` is everywhere in the app, and `now` the browser's clock. `@` alone offers Today and Tomorrow (`soon`), and not Pick a date…. A day is written as `written` writes it: a link to the day, `[[2026-10-21]]`, with `HH:MM` after a space for a time, `[[2026-10-21 15:00]]`, a day and a clock's time where the member is with no time zone, as a due date has none. Each item's label is the day's name, or its short date with its weekday for a date typed as one, its description the day in full, and its preview the weekday and how far it is from today (`howFar`, `Intl.RelativeTimeFormat`). After the days, or alone for `pick`, `pick a date` on the way, or `date`, comes Pick a date…, whose `insert` opens `openPopover` (`plugins/lib/Popover.tsx`) at the cursor with the date field a todo's due date chip has (`DayField` in `plugins/lib/DayField.tsx`) and answers the day picked, at the time typed where one was, or null when it is closed. The field starts empty, so picking today is a change too. The popover hangs from the `anchor` the list hands `insert`, a mark of no width in the editor's scroller at the cursor, so it scrolls with the text. A day in a note is a link to it, `[[2026-10-21]]` or `[[2026-10-21 15:00]]` with a time, or `[[2026-10-21|words]]` with words of its own, read by the link machinery that reads `[[id]]` (`linkedDay`, `dayLinksOn` and `writtenDayLink` in `src/core/dateLinks.ts`, from the plugin API): a note's id never looks like a day, so a link is to one or the other. It goes to that day's daily note. The server leaves it as written, however strict the write, though a daily note is titled its date, and records it among the note's links by its day, `day:2026-10-21`, so `note.backlinks` of a daily note, and `has:backlink`, take in every note that links its day, the daily note itself left out. `@`'s days and the picker write it (`written` in `when.ts`). A date written bare is words: it draws as nothing and links nothing, and so is a daily note's own title, `# 2026-10-21`, and a todo's `due:2026-10-21`, which is the todo's field. The chip (`drawing.ts`, found by `dayLinksOn`) is drawn wherever a link is, a heading too, and not in code. It reads Wed, Oct 21, with the year only where it isn't this year's and the time where one is written, or as the link's own words, and is `written: "within"` as a link to a note is, so it is drawn with the cursor at its edge, shown as written with the cursor inside, and taken whole by a deletion. A click opens, under the chip, the picker a todo's due date opens (`ChipMenu` from `plugins/todos/ChipMenu.tsx`, through `openDayPicker` in `plugins/dates/picking.tsx`, with its field called Date and no Clear), so a date link and a due date are changed alike: Today, Tomorrow, Next week, or any day in the field, then the time, Add time, which is an hour and minute field once pressed, or the field with Remove time beside it, and last Open daily note, which makes the day's note where there is none, so a screen with no pointer to rest on a date still reaches it. A day picked is written at once in place of the link by the chip's `source.rewrite`, with the time as the picker then has it and the link's own words kept, as the member's own edit, undone as typing is, and closes the picker. A time changed or taken off alone is written as the picker closes, by Enter in the field or a press away, since writing it redraws the date the picker hangs from, and Escape closes it with the time as it was. While a picker is open no date shows its card (`picking` in `plugins/dates/picking.tsx`), which would cover it. ⌘-click (Ctrl-click) opens the daily note for its day as the daily plugin's commands do (`openDay` in `plugins/daily/opening.ts`): today's and tomorrow's are made when they aren't there, and any other day's is only found. So does vim's gd, through the editor's `following` facet (`src/web/following.ts`, from the plugin API), which gd asks before it follows a link: the date plugin's follows the date link under the cursor, not one the cursor is just after. Resting on a date shows its card (`dateCards` in `plugins/dates/card.tsx`, a `hoverCards("date")` as tags' and folders' are, marked `data-date`): the whole date and how far it is from today, "Thursday, March 4, 2027 · in 4 months", with Change date, which opens the picker, and Open daily note, which reads Create daily note where `daily.find` finds none for that day and then makes it with `daily.open`. `dates.pick`, Change the date at the cursor, on Alt+Shift+D, opens the picker at a date link the cursor is in or at the edge of, and writes the day picked there if the link is still as it was. It isn't on Alt+Enter, which edits the link at the cursor: a chord runs the one command `bind` gives it, whatever its `when` says, so commands can't share a key by what is at the cursor. Where the note can only be read, as for a viewer, a click opens the daily note as ⌘-click does, changes nothing, and the card has no Change date. Each start of the plugin keeps the dates it draws in a `WeakMap` of its own (`DrawnDates`), so where a page draws markdown twice over, as the app does with a reading of a file in it, a date shows one card. A share link's page draws dates too, the dates plugin being among those its drawing host starts (`src/web/drawingHost.ts`); there `app.go` is absent, so a date opens no daily note and its card says the date alone.

Dates were written bare before they were links, and drawn as dates then. Each note written before is converted once, the first time someone who may change it opens it: the dates plugin sends `note.linkDates` for each note a member's editor opens whose `access` is edit, once a page (waiting for the notes to be listed where they aren't yet), and the server writes the dates the old chip drew as links (`bareDatesOn` and `datesAsLinks` in `src/core/dateLinks.ts`): a date on its own in prose, and not one in a heading, code, a link's words or address, an embed's braces, `due:`, or the lines of a block embed or a `$$` formula, whose HTML or card words would show the brackets as written. It is a change of the member's, made with `commitNote` as any write is and labeled "Dates written as links", so History shows what it was and puts it back; `performInSync` pulls it into the open note at once. Which notes are still to convert is the notes' `dates_linked` (migration `0066_date_links.sql`), 0 for a note there before and 1 for one made since. The server claims a note by setting it before converting, so two openings at once convert it once, and sets it back where the write fails; a note put back after is left bare. It is a member's: an agent writes date links itself, and the server refuses a guest, and anyone who may only read the note, whom the app doesn't ask for. A note no member who may change it opens keeps its bare dates, which read as words. It is a write on opening rather than a migration of every note at once because a change by nobody, a system author, isn't something the history, blame and authors know how to show.


### Data sources: Calendar, Contacts, and references

The calendar plugin (`plugins/calendar/`) and the contacts plugin (`plugins/contacts/`) show a member's own data sources, through `host.perform` and the operations `source.*`, `event.*`, `contact.list` and `record.*`. Nothing in either names a provider: which data sources there are, what each is called, whether it is connected, to what account, and whether it takes changes all come from `source.list`. `plugins/lib/Sources.tsx` is the part both pages share: it says each data source's state and offers Connect, Reconnect, and Disconnect, which names every data source that goes with it, since those of one provider are connected as one account. `source.connect` may answer with `redirect`, a path the browser is sent to, which comes back to the page.

Every date the Calendar works out is in `plugins/calendar/dates.ts`, a pure module that is handed the time zone, tested in `test/core/plugin-calendar-dates.test.ts`. A day is a calendar date and never 24 hours: the days of a view are counted as dates, and `startOfDay(day, timeZone)` finds the instant each starts, so a day the clock changes on is 23 or 25 hours long and `spanOf` still asks `event.list` for exactly the days on show. `daysOfEvent` says which days an event is on where the member is: an all-day event on its own dates wherever it is read, any other on the day it starts in the member's zone. The zone is the browser's, and every time is said in it.

The views are Day, 3 days, Week, Month and Agenda, in that order (`VIEWS` in `dates.ts`, with each one's key and, for a grid of hours, its days: 1, 3 and 7). A week starts on the member's `calendar.weekStarts` (Monday unless they choose), which is the first day Week shows and Month's first column, and `calendar.weekends` shades Saturday and Sunday (on unless they turn it off). The New event button in the header opens the form for the next half hour, as `c` does. Day, 3 days and Week are one time grid (`plugins/calendar/TimeGrid.tsx`), drawn as v1 drew it: 48px an hour, the hours down a gutter, a header of days and an all-day row that stay put, a now line in today's column, and each event a card tinted with its calendar's colour (`--cal-tint` of it, more in dark) with its title over its time. Three pure modules hold its rules, each tested in `test/core/plugin-calendar-*.test.ts`. `layout.ts` lays out a day's events as v1 did: those that start under 30 minutes apart side by side, a later one inside another on top of it and indented, and all-day bars stacked across the days on show. `sideways.ts` is where the days are, `x`, the first day in view counted from a fixed Sunday (`EPOCH` in `listing.ts`), and how it moves: a sideways wheel or trackpad scroll (or shift and the wheel) moves it continuously, the axis of a gesture is decided by its first event so a sideways scroll never moves the hours, and once the wheel stops it settles on a day's edge, nudged the way it was moving, or on the next edge the way it was heading once it went 72px (or half a day, if less) past the edge it left, so a modest swipe of Day's one wide day is the next day; the arrows, Today and the keys glide to a day. Each frame applies `x` to the three strips (header, all-day row, body) as one transform and never goes through React, which draws again only when the window of days drawn (`SPARE` days either side of those in view) has to move. `drafting.ts` is the pointer as a reducer: the half hour under it outlined, a press that moves 5px a draft snapped to 15 minutes, a press on an event a move or, from its bottom edge, a new end; `released` says what letting go asks for. `listing.ts` reads `event.list` 14 days at a time for the days drawn and a week either side, keeps what it read, and reads again after a change without taking what was shown off the page, so a day slides into view already read. A Week too narrow for seven days at 76px each shows as many as fit.

An event is added with `event.create`, from the form a drag or a click on the grid opens, into the member's default calendar, the remembered setting `calendar.default`, chosen in the Calendars dialog or with Make default in the form. When it is unset, hidden, read-only or no longer connected, it goes in the calendar used last in that browser (`calendarTarget` in the plugin's storage) or the first, and the form says which and why (`choosing.ts`). With nothing connected, the page offers `Sources` inline in place of the grid, and nothing is added until Save. A drag moves an event, or changes its end, with `event.update` at once, and the notice that says so has Undo, which changes it back with the etag the change answered. The Calendars button opens a dialog that holds `Sources` and, under each connected calendar data source, a checkbox per calendar (`calendars` in the `event.list` answer); a calendar unticked is left out of the grid, kept in the member's remembered setting `calendar.hidden`, so every browser they sign in on shows the same calendars. Calendars hidden in a browser before that, in the plugin's storage, join the setting the first time the Calendar opens there once the member's settings are read (the host tells plugins when the settings are read, even when nothing in them changed), and the storage is cleared so it happens once. The list is written whole, so two browsers changing it at the same moment can lose one change.

An event's panel ends with the notes about it and, under them, its main action, New note about this event: it asks for a folder, the one used last first (`noteFolder` in the plugin's storage), and makes a note there headed with the event's title and day and holding its reference, shared as everything in that folder is. At its foot the panel lists the notes that reference the event, from `record.notes`: the notes the member can see, not in Trash, that hold the member's own reference to it, and for an event the member can read now, another member's reference to the same event: a teammate's note about a meeting on a calendar they share. Each is marked Private (a private note nobody else is let in to), Shared (a private note shared with some people or by a link) or Workspace (every member sees it). A note the member can't see is never in the answer, title and all; a teammate's reference counts only while the member's own calendar has the event (one `get` of it, asked only when a teammate referenced it); and a contact is the member's own, so another's reference to a contact lists nothing here. A teammate's reference still opens nothing for the member: following it is its maker's alone. A note is found by the reference it holds, whoever wrote it there, so someone who copies a reference into a note they can write adds that note to the list of whoever is told of the reference, as a copied reference always has; the note is still one the reader can see. At most 50 references are looked for, the member's own first, then the oldest; a calendar that fails to answer lists the member's own notes only.

Events are linked as notes are. `[[` in a note offers, after the notes, the member's events whose title has words starting with what was typed, and quick open (Cmd/Ctrl+P) lists them after the notes whose title holds it. Both look from 30 days back to 90 days ahead, the nearest to now first, each occurrence of a repeating event an entry of its own, each said with its day, its time and its calendar. A day typed with the words narrows to that day's: `sync oct 20`, `20 oct`, `October 20`, `10/20`, `2026-10-20`, `today`, `tomorrow` (`plugins/calendar/finding.ts`, tested in `test/core/plugin-calendar-finding.test.ts`; a day with no year is the one nearest today). They are read with `event.list`, so from the member's own calendars alone, once a minute at most, and `[[` alone starts the reading so they are there by the first letter. Picking one under `[[` asks `record.refer` for that occurrence then and writes its reference, so the event lists the note; picking one in quick open opens the Calendar at its day with the event open (`/calendar?source=…&event=…&day=…`, which the page then drops from its address). Copy reference is the palette's Copy event reference, for the event last opened on the Calendar page.

An event is changed with `event.update`, which is sent the event's `etag` and only the fields the member changed. A refusal is shown in the server's words, and the events are read again either way. The form is made again for each reading of the event (`key={event.etag}`), so after a refusal for a stale reading it holds the event as it is now, and saving again can't write an old value over someone else's change.

A note references an event with a link, `[[event:ref]]`, and a contact with an inline embed, `::contact{ref label}`. `record.refer` answers either as `text`, and for an event its title as `label`, one line (`docs/adr/0019-everything-a-note-opens-is-a-link.md`). `[[` in a note offers the member's events after the notes, and picking one writes its reference; the palette's Copy event reference copies the reference to the event last opened on the Calendar page. `eventLinks` in `plugins/lib/references.tsx` draws a link to an event as a chip, `written: "within"` as a link to a note is, and `referenceEmbed` there draws a contact. The chip is drawn at once with what the note holds, a contact's label, a link's own words after `|`, or "Event", and then asks `record.read`: the member who made the reference gets the record as it is now, and the chip says its title and when it is, or the contact's name. A link's own words are kept in place of the title, for every reader. Anyone else, and anyone at all once the record is gone, is answered `not_found`, and the chip stays as it was drawn, saying that only the member who referenced it sees its details. Nothing else is asked for them. A reading is kept for 30 seconds by member and reference, so a reference written twice is read once and typing in the note asks nothing, and `forgetReferences()` drops them after a change made in the app. The chip is text in the line's own face and size with a tint behind it, not a box: it wraps as words do, so its line is as tall as any other, drawn or as written, and the lines after it stay where they are when its details arrive. One case moves: a line that just fits with the labels can need another row once a chip also says when its event is, the first time it is read. `test/browser/sources.spec.ts` measures both.

A press on a live chip, with ⌘ or without, Enter or Space on it, or vim's `gd` on a link to an event, opens a popover under it with what `details(record, { noteId, close })` draws, given the note the chip is in. A contact's is its details. An event's (`plugins/calendar/EventLink.tsx`) is led by what to do with the event, a short list under its title, day and time, calendar and place, with the keyboard on the first action: Open note about it opens the note about the event changed last that the member can see, other than the one the link is in, and says which; where there is no other, New note about this event takes its place, the panel's own flow, asking for a folder. The notes about it are listed under that, each marked Private, Shared or Workspace, only when there are more than one; Go to calendar opens the Calendar at the event (`/calendar?source=…&event=…&day=…`, as quick open does). Which note Open note picks and when the list shows is `linkNotes` in `plugins/calendar/linking.ts`, tested in `test/core/plugin-calendar-linking.test.ts`; Up and Down, Home and End and Tab move through the actions, and Escape closes it and gives the keyboard back to the link (`test/browser/event-links.spec.ts`).

### Tags and search

The tags plugin (`plugins/tags/`) draws a `#tag` in a note with a mark that changes its color and nothing else, the same whether or not the cursor is on its line, so there is no drawn and as written to move between. It keeps the marks in a state field read from the whole text with `linesOutsideCode` and `tagsOn` from the plugin API, the functions the core indexes tags with, so what is drawn as a tag is what `tag.list` counts. A todo's line gets the same mark: the todos plugin draws no chip for a tag. ⌘-click on a tag goes to its page, as ⌘-click follows a link written out, and a plain click puts the cursor in it. In a reading, as a folder list's card is, there is no cursor, and a plain click goes to the page. `test/browser/tags.spec.ts` measures every letter of a tagged line: none moves with the cursor, and against the note with the plugin off none is further than the 1/64 of a pixel the browser places a run of text by.

## Keybindings

In a chord, `mod` is ⌘ on a Mac and Ctrl elsewhere. `ctrl` is the Control key: on a Mac it is its own key, and elsewhere it is the same key as `mod`, so `ctrl+o` and `mod+o` are one chord there.

The app tries a keybinding before the editor or anything else with focus sees the key, and a key that ran a command goes no further: not to the editor, and not to a key handler of the element that has focus. A command that should stand aside at times gives `when`, a function that answers whether its keys run it now. While it answers false the key is left to whatever has focus. Vim mode's `vim.back` answers false in a text field and in a note in insert mode, where `ctrl+o` is the field's or vim's own.

A command's `keys` are its default chords. The member's are settings too: `keybindings.<command id>` holds a list of chords, and an empty list unbinds the command. The member changes them in the Keyboard shortcuts category of the Settings page, a table of every command with its keys and whether they are the default or the member's: Record takes the keys wanted as they are pressed, one after another for a sequence, with Start over to take them back, and Reset goes back to the default. It warns when another command already has the keys, or has keys that these begin or go on from. A press in the recorder is written down and runs nothing. Enter saves there and Escape cancels, so those two alone are bound in the JSON. A member's keys are whatever the app can run a command on: one chord, with a modifier or bare, or a sequence. Keys that would type, whose first chord has no `mod`, `ctrl`, or `alt` and is neither Escape nor an F key, are left to a field or a note's text while one has focus, unless their command gives a `when` and so says for itself where it runs. So no key that types in a note runs a command that didn't ask to be run there. Enter and Space, alone or with Shift, are likewise left to a button, a link, a checkbox or another control that acts on them while it has focus, unless their command gives a `when`. The palette shows the chord that runs a command now. A plugin does nothing to take part.

**?** opens the keyboard shortcuts over the page (the command `commands.shortcuts`, also in the palette as Keyboard shortcuts): every command that has keys now, under its `group`, Navigation, Notes, Editor and then a plugin's own such as Vim, with Other last for a command that gives none. It reads `host.commands.list()` each time it opens, so a key the member changed is shown changed. Its key is `shift+?`, a key that types, so it is left to every field and to a note's text. In vim's normal mode `?` is vim's search backwards, and the sheet is opened from the palette there.

A command's default `keys` may be a sequence: chords pressed one after another, written with spaces between them, such as `g g` or `ctrl+w h`. The keys that begin a sequence are taken only while a command that can run now goes on from them, so `g` is nobody's key in a text field. A key that doesn't go on from what was begun runs what it runs by itself, and otherwise goes nowhere. A sequence that was begun is given up when focus moves, when the pointer is pressed, or after a second and a half, and then the next key is whatever it would have been with nothing begun. A default may also be a bare key such as `j`: give such a command a `when` that answers false wherever the key would be typed, since a command with a `when` is trusted with it and one without is never run by such a key while something is being typed in. Don't give one command a key that begins another's sequence: the shorter keys run on their last press and the longer never do. A member who does is told so, in Settings.

### Lists, rows and regions: vim's keys outside a note

With Vim mode on, vim's keys work outside a note's text. They are one table in `plugins/vim/keys.ts`: each row is a surface, the keys, and the command they run, and every row is registered as a command under `vim.`, so the keys are listed in Settings among the keyboard shortcuts and a member can change or remove them. In what an embed draws in a note, such as a kanban board, the list, row, search and tab surfaces answer no: the keys there are the embed's. Ctrl-w still leaves it. A surface is a question about where focus is, answered by `plugins/vim/surfaces.ts`, and it is the command's `when`.

| Surface | Keys | What they do |
| --- | --- | --- |
| A list, when nothing is being typed | `j` `k`, `g g` `G`, `ctrl+d` `ctrl+u` | next and previous row, first and last, half a page down and up |
| The selected row | `enter` or `l`, `z a`, `h` | open it; expand or collapse it, by its `data-row-toggle` or its button with `aria-expanded`; collapse it, or go to its parent |
| The selected row, when it has a `data-row-delete` | `d d` | press it: on the Todos page, abandon the todo |
| Anywhere a search box is in reach, when nothing is being typed | `/` | go to the search box |
| A text field with a list in reach | `ctrl+j` or `ctrl+n`, `ctrl+k` or `ctrl+p` | next and previous row of the list the field is for |
| A search box, or the field of a row | `escape` | back to the list |
| Anywhere but a text field or a note in insert mode | `ctrl+w` then `h` `j` `k` `l` | the region on that side |
| Anywhere but a note or a text field | `g t`, `g T` | next and previous tab |

In a note in normal mode `gt` and `gT` are mapped in vim itself, to the same commands, since `g` begins many of vim's own keys there.

None of this names a plugin or a page. The keys find lists, rows and regions by what the page says they are, so a plugin's view takes part by saying so:

- **A list** is an element with `role="tree"`, `role="listbox"`, `role="list"` or `role="menu"`, a `<ul>` or `<ol>` with an `aria-label` or `aria-labelledby`, or anything with `data-list`.
- **Its rows** are its `role="treeitem"`, `role="option"` and `role="menuitem…"` elements and anything inside it with `data-row`. A list that has none of those has its children as rows.
- **The selected row** is the one with focus in it. Focus rests on the row when the row can take it, and otherwise on the first thing in it that can be pressed. A row that begins with a text field is given focus itself, so nothing is typed into the field until the member opens the row. The row is marked with `data-vim-at`, which `style.css` draws, and scrolled into view.
- **A list with its own keys** is one that takes focus itself (it has a `tabindex`) and keeps its own cursor, as History's list of changes does with `aria-activedescendant`. Vim's `j` and Ctrl-w put focus on that list and from there every key is the list's own: none of vim's row keys run while focus is on it. The moves a keyboard has a key for are sent to the list as that key, a `keydown` on the list itself: `g g` as Home, `G` as End, Ctrl-d as Page Down and Ctrl-u as Page Up. So a list with its own keys answers Home, End, Page Up and Page Down, and vim's four follow. A key that ends a sequence begun there without finishing it, such as the Enter after a lone `g`, is the list's too: the app drops such a key everywhere else.
- **Opening a row** clicks what the row marks `data-row-open`, or else the row when it is itself the thing pressed, or its first link, or goes into the field it begins with, or clicks what it rests on. Mark the opener when a row has a checkbox before it, as a todo has. A note that comes to the front because of it takes focus in normal mode.
- **`h`** clicks the `data-row-toggle` of a row whose `aria-expanded` is true. Otherwise it goes to the row before it with a lower `aria-level`, or to the row a nested list is in.
- **A list a field is for**: `ctrl+j` and `ctrl+k` are sent to the field as the arrow keys Down and Up, so a field that already answers those needs nothing. A field that doesn't answer them sends focus to the first or last row of the nearest list.
- **A region** is an `<aside>`, `<main>`, or anything with `data-region`; of two that nest, the inner one. Going to a region puts focus where it last was there, or in its note's text, or on its list's row. `data-focused` marks the region to start from when focus is nowhere.
- **Tabs** are the `role="tab"` elements of the first `role="tablist"` in the region, and the one in front has `aria-selected="true"`.

## Turning plugins off

A plugin with `enabledByDefault: false` is off until the member turns it on. Its setting `<id>.enabled` then defaults to false, and only `true` is kept in the member's document.

A member turns a plugin off on the Plugins page, on the plugin's card or in its details, or from the palette (`Disable plugin: Tabs and splits`). Both write the setting `tabs.enabled`, so the choice follows the member to another browser. The Settings page has no switch for a plugin: it shows the setting only as a line of the JSON.

The Plugins page is under More in the sidebar and the Settings page is in the workspace menu. The Plugins page lists each plugin as a card, like a note in a folder's list: a press anywhere on the card opens the plugin's details (the name is a link laid over the card), and the switch on it still only switches. They are always at `/plugins` and `/settings`, and each has a `go.` command. They belong to the core, so they are there by their address when the palette and the sidebar are off. A plugin's details are at `/plugins/<plugin id>`, and a category of settings at `/settings/<category>`, such as `/settings/keyboard` and `/settings/plugins/<plugin id>`. Settings is not a page in a tab: at any address under `/settings` the app draws it as a large dialog over whatever the window shows, which stays as it was under it (the tabs, a split, focus), and what the editor area puts in front meanwhile is kept as what is under it, not put in the address. Escape, its close button or a press outside it goes back to the address under it; going anywhere else closes it too. `Go to settings (UI)` (`go.settings`) in the palette opens it. The JSON is not in it: it is a document of its own, at `/settings.json`, opened in a tab like a page by `Go to settings (JSON)` (`settings.openJson`) or by Settings' Open settings (JSON), and edited in an editor drawn as a note's is (`SettingsFile.tsx`). It is the settings store's own text, not a note, so nothing that lists, searches or exports notes ever has it, and an agent can't read it. Typing there that isn't a JSON object is the store's draft (`store.draft()`): it is marked, saved nowhere, and Settings' options wait for it. The old address `/settings/json` is written as `/settings.json` by the router's table of moved addresses (`src/web/moved.ts`). Both commands kept the ids they had, so a key bound to either still works: a page of the app's own names its command with `command`. Storage and Export are under Account. A tab kept on the Settings page from before says it opens over the window now.

With every plugin off, the core still opens the note its address names, takes typing, and saves.

A plugin's details end with its **source**, to read. A third-party plugin shows its `manifest.json` and its `plugin.js` as the workspace has them, which every member can read (`plugin.read`). A plugin that comes with Common Ink shows the file it starts from and every file of `src/web/plugins/` that file imports, however far down: `SOURCE_OF` in `src/web/plugins/index.ts` names each one's first file, and `test/core/plugin-source-map.test.ts` holds the table to the imports beside it. The text is bundled when the app is built (`import.meta.glob` with `?raw` in `src/web/pluginSource.ts`), each file in a piece of its own, so what is shown is what was built, no server keeps a second copy, and nothing is fetched until the section is scrolled near: the files, and the editor they are drawn in (`src/web/pluginSourceView.ts`, CodeMirror with the language's colors, read-only). One list picks the file, so a plugin of twenty files adds one control to the page and not twenty.

Under an installed plugin's source is **Edit a copy**, which makes a **draft**: the member's own copy of the manifest and the code, kept on the server beside their settings and out of sight of the notes (`plugin_drafts`, migration `0033`; `draft.list`, `draft.read`, `draft.save`, `draft.discard` in `src/core/pluginRecord.ts`). A draft is no note: it is in no folder, search or history.

- **It is its author's alone.** Every statement about drafts names the asker and no operation takes a person, so nobody else reads or changes one, an admin included: another member is answered "You have no draft of that plugin". Plugins are refused the four operations, the draft itself included. The member's own agent reads and writes the member's drafts as the member does (`list_drafts`, `read_draft`, `save_draft`, `discard_draft`), a read-only one only reads them, and one limited to folders is refused all four. A member who is removed or leaves loses their drafts in the same batch, so none is waiting if they are added again, and uninstalling a plugin removes every draft of it.
- **Run my draft** runs it in the original's place, for its author only and in frames like any installed plugin, with what the original is allowed and the draft's own manifest still asks for, and never more. The app decides that in `decideRun` (`src/web/pluginRun.ts`) and the server decides it again: a draft's operations come to `/api/workspaces/<id>/plugins/<install id>/draft/ops`, where `actingPlugin` reads the draft of the session's person and allows the original's standing permissions that the draft still declares. A capability the draft adds is off, the sites of `network` are the ones an admin allowed the original, and an admin turning a permission off turns it off for every draft. For anyone else that address answers "You have no draft of that plugin that is running". A draft whose manifest can't be read, or that asks for something no manifest may, is kept as text and never runs. While one runs, the plugin's card and page say "Running your draft".
- **Publishing is installing.** Only an admin has "Publish to the workspace", which is `plugin.install` with `replaces`: the existing admin-only path, refused to everyone else by the core. The new code has no approval, so every permission has to be allowed again.
- The list of a draft's files ends with "What I changed", which compares the draft with the plugin as it is now, and says so when the plugin has been replaced since the copy was made. What was typed and not saved is kept, as text, when the page is left.
- A draft's writes are recorded as the plugin's, for its author, as a write the member posts to the plugin's own address already is. They are the member's own writes: a draft can change only what its author can.

Plugins that come with Common Ink show their source and can't be copied.

A plugin whose `activate` throws is left out whole. A view that throws while being drawn is left out alone, an embed that throws is shown as it is written, and a completion that throws offers nothing. Each way the Plugins page says what failed.

## One interface for a plugin that runs shut off

Word count, Quick timer and Backlinks come with Common Ink and run shut off from it, through the broker, the port and the address on the server a third-party plugin uses (ADR 10). Weather, a sample calendar, Coin and Dice are the same kind of plugin, one in each place a plugin can live, so those places can be tried without writing one. There is no second door: what the first three needed and a frame lacked was added for every plugin. Their manifests are in `src/core/ownPlugins.ts`, read by the schema every manifest is read by, and their code is one file each in `src/web/plugins/sandboxed/`, plain JavaScript written against `ink` and nothing else. The server holds each to what its manifest declares (`actingPlugin` in `src/core/pluginRecord.ts`): no row in any workspace is read for one, so nobody permits, locks or uninstalls it, and what it declares is all it can ask, in an admin's session as in a guest's. A guest's app runs them too, as that guest.

| Plugin | Runs | The Plugins page says |
|---|---|---|
| Common Ink's own that needs the editor or the app's layout | in the page, compiled in, as the member | Built-in, full access |
| Common Ink's own that needs nothing of the page | shut off, in frames | Built-in, sandboxed |
| A workspace's | shut off, in frames | Third-party |
| A workspace's that asks for `full-trust` | in the page, for each member who turned it on, while an admin's grant of that exact code stands. Otherwise not at all | Third-party, full trust |

What sets the three apart from a workspace's plugin, and all of it is decided by the app from where the plugin was read, never from anything a manifest or a record says:

- **Their words are the app's.** Commands, tabs and questions are not marked `<name> plugin:`, their views keep the ids they had in the page, their frames are named `ink-own-plugin`, and a manifest of theirs may name an `icon`. A workspace's manifest that names an icon is refused, as one with a name of the app's own is.
- **Their frames are never stopped for holding the keyboard.** Any frame can hand the keyboard to another (`top.frames[i].focus()`), and the app can't see which did. The keyboard goes back to the note either way. A workspace's plugin's frame is stopped for it, as before, so one workspace plugin can still have another's frame stopped.
- **They are on from the start,** and placed among the built-ins where they were (`PLACED_AFTER` in `src/web/plugins/index.ts`).
- **Their code for commands starts with the app,** not at the first command, so what a command shows is there at once. A workspace's plugin runs nothing until the member asks something of it.

What was added to the sandbox, for every plugin:

| Added | For | Needs |
|---|---|---|
| `views[].slot: "bar"` with `width`, and `end` for the right side | an item in the app's one bottom bar. The frame is as wide as what `ink.root` holds, which the SDK reports as it changes, and never wider than `width`. With nothing drawn it takes no room. It is not told which note is in front and not started again for each: it asks with `ink.onNote`. A press in it works, and the keyboard goes straight back to where it was. A plugin has one, and beside a workspace's the app writes the plugin's name | nothing |
| `ink.onNote(fn)` | the note in front as its editor has it, `{ id, text, selected }`, typing not yet saved included, or null when no note is open in an editor. Told again when any of the three changes, 150 ms after the last change | `notes.read` |
| `ink.onItems(fn)` | told when the notes the member can see have changed | `notes.read` |
| `ink.storage.get(key)`, `ink.storage.set(key, value)`, `ink.onStorage(fn)` | JSON kept in this browser for this plugin, this member and this workspace. At most 20,000 characters a key, 50 keys and 100,000 characters in all with the keys' names counted, refused with `invalid` past any of them. Setting a key to null takes it out, and leaves nothing under it. Every frame of the plugin hears a set. No plugin reads another's, and a second person in the same browser has their own | nothing |
| `ink.prompt({ title, label, value, hint, error })` | one line of text asked in a dialog the app draws, answered with the text or null. One at a time, and only within ten seconds of the member running one of the plugin's commands, or at once after an answer: no plugin puts a dialog up of its own accord, or again once it was turned away. Above a workspace's plugin's question the app says "The plugin <name> asks", and its title is `<name> plugin: ...`, so it can't be taken for the app's. Asked again within 120 ms of an answer, the dialog stays with what was typed | nothing |
| `ink.open(noteId, { background })` | open a note in a tab of its own behind the one in front | `notes.read` |
| `note.backlinks` in `notes.read` | the notes that link to a note, as the member may see them | `notes.read` |

What moving the three cost, which is what a workspace's plugin lives with:

- **A question is asked a moment after its command.** The command goes to the plugin's frame, which asks the app. With the frame already running that was 36 ms on a laptop, measured once, so Enter pressed twice at once is not what it was. What is typed is judged where the plugin runs, so the quick timer says a length is wrong once it is entered, not as it is typed.
- **A frame is under a shield until the pointer is on it.** With a mouse nothing is noticed. On a touch screen the first tap on a frame only takes the shield away.
- **The bar's frames are passed by Tab.** The quick timer in the bar is pressed with the pointer, or stopped with its command.
- **A link in a frame is not the browser's.** ⌘ or Ctrl and a press on a backlink opens it in a tab behind, as in the note list, and not in a new window.

Tab does reach into a frame in the inspector, and Enter there opens a backlink.

**A member's copy of one** runs in its place for them alone ("Edit a copy" on its page, as for a workspace's plugin). It has what the original declares and its own manifest still asks for, never more, its name may stay, and since it is no longer the app's code everything of it is marked `<name> plugin:`. It is never published over the original: an admin installs its two files as a workspace's plugin under another name.

### Full trust

A manifest asks for it as a capability:

```json
{ "name": "Deep Keys", "capabilities": [{ "name": "full-trust", "reason": "It adds keys to the editor." }] }
```

It runs in the page for a member only while both hold: an admin's grant of the code it is now stands (`plugin.permit`, the Allow on its permission row, which names the code's hash), and that member has turned it on for themself (`plugin.trust`, the plugin's own switch, behind a warning). Otherwise none of it runs, shut off or in the page, and its page says why in one line. ADR 11 has the whole of it.

- **Any change ends it for everyone, for good.** An update to its code, or to how it asks for full trust, ends the grant and every member's turning on in the batch that makes the change. Putting the old code back restores neither. Only a fresh grant and each member's own fresh turning on start it again.
- **An admin's decision starts it from nobody.** Taking the grant back turns everyone off. Granting again turns nobody back on.
- **Nobody turns it on for anyone else.** `plugin.trust` names no person. It is refused to agents, to plugins and to guests, and it is refused for code no admin granted.
- **Stopping loads the app again.** Code that has run in a page can't be taken out of it, so turning it off, a change to it, and going to another workspace each send what is typed and load the app again. A window open elsewhere does so when it next reads the record: when it is come back to, and every 15 seconds while it is in front. A window that is hidden reads nothing until it is shown. This ends honest code. Code that means harm can get in the way of it in a window it is already in, since it shares the page: what ends it there is closing the window. A window loaded after it was turned off, or after the grant ended, never runs it, because the app decides that from the record before any of the plugin's code runs.
- **The app hashes the code itself** and runs it only when that is the granted hash. Once the member's switch starts it, the app loads it as a module from its own address, `/api/workspaces/<id>/plugins/<id>/trusted/<hash>.js`, which answers only code whose hash it works out again to be that one, only to a member it runs for now. Loading it can run code written to step outside the function it is wrapped in, so the app counts it as running from then, and turning it off still loads the app again: the page's policy allows script from the app's address alone and no `eval`, and full trust leaves that policy as it is. A draft that asks for full trust never runs.

Its code is the body of a function handed `host`, the `PluginHost` on this page, and `modules`: the app's own `react`, `@codemirror/state`, `@codemirror/view` and `@codemirror/language`, since a second copy of either would not work with the app's. It may return a function that stops what it started. What its manifest lists as commands, views and embeds is not registered for it: it registers them itself through `host`, as a built-in does.

```js
const { keymap } = modules["@codemirror/view"];
host.editorExtensions.register({ id: "deep.keys", extension: keymap.of([{ key: "Ctrl-j", run: () => (host.commands.run("note.new"), true) }]) });
```

It is handed what the app's own plugins are: `host.agents`, `host.members`, `host.sharing`, `host.uploads`, and every operation `host.perform` takes from them. `host.perform` goes to the plugin's address, so what it writes is recorded as the plugin's, for the member, and the server answers it as it answers that member (uploads and mentions included), refusing only what is a member's alone to ask. Three things about whose it is stay as for any plugin a workspace installed: its embeds are written `::x-name{}`, its name can't be one of Common Ink's own, and it can't take the page at `/`.

**What it can do** in the session of a member who turned it on: anything that member can do in Common Ink. Read and change every note they can open, private ones included; see what they type; read and change their settings and drafts; and call the server with their session directly, which the `host` object does not limit. That reaches every workspace the member belongs to, not only the one that granted it, because the session is the same in all of them. Some of it outlasts the switch: it can create an agent token in the member's name and share their notes by link, and both keep working after it is turned off. In an admin's session it can also invite people, change roles, and install and approve plugins, including approving a new version of itself or another plugin and turning that on for that admin, with no warning shown: `plugin.trust` is the admin's to call, and the code calls it as them. That holds in any workspace where the member is an admin, not only this one. It can't turn anything on for anyone else. The warning a member reads before turning it on says this, an admin is shown the admin's part, and the grant an admin gives says that the code can act as any member who turns it on.

**What it can't**: see a note its member can't, do an admin's work in a non-admin's session, or run for anyone who hasn't turned it on themself. The server decides those by who the member is.

## Third-party plugins

A third-party plugin is one a member wrote and an admin installed in a workspace. It is two pieces of text: a **manifest**, which is JSON and says what the plugin is, and its **code**, which is JavaScript. An admin pastes both into the form on the Plugins page. They are kept in the workspace and nowhere else: nothing is fetched from another site to run a plugin, now or later.

```json
{
  "name": "Word counter",
  "version": "1.2",
  "description": "Counts the words in your notes.",
  "capabilities": [
    { "name": "notes.read", "reason": "To count the words in your notes." },
    { "name": "network", "reason": "To look words up.", "origins": ["https://api.example.com"] }
  ],
  "commands": [{ "id": "count", "title": "Count notes" }],
  "views": [{ "slot": "inspector", "id": "words", "label": "Words" }],
  "embeds": [{ "name": "wordcount", "title": "Word count", "height": 96 }],
  "settings": { "unit": { "type": "string", "default": "words", "enum": ["words", "characters"], "title": "Unit" } }
}
```

```js
ink.onCommand("count", async () => {
  const { notes, next } = await ink.perform({ type: "note.list", limit: 1000 });
  await ink.notify("Counted " + notes.length + (next ? "+" : "") + " notes");
});

if (ink.context.kind === "view" && ink.context.noteId) {
  ink.perform({ type: "note.read", id: ink.context.noteId }).then(
    (note) => (ink.root.textContent = note.text.split(/\s+/).filter(Boolean).length + " " + ink.settings.unit),
    (refused) => (ink.root.textContent = refused.message),
  );
}

// A note writes this one as ::x-wordcount{all}.
if (ink.context.kind === "embed") ink.root.textContent = "Counting: " + ink.context.config;
```

### The manifest

`Manifest` in `src/core/plugins.ts` is the schema, and it is strict: a key it doesn't know is refused. The app lists a plugin's commands, views, embeds and options from the manifest without running any code.

- `name` (60 characters), `version`, `description`. No control or invisible characters anywhere. A name that is Common Ink's own, or reads as one, is refused when the plugin is installed and again when it would start: the app, its pages and its built-in plugins (`OWN_NAMES`, and in the app the built-ins it actually has). Names are compared by `nameSkeleton` in `src/core/plugins.ts`: compatibility forms folded, accents off, Cyrillic and Greek letters drawn as Latin ones read as those, case, spaces and punctuation dropped, and `l`, `1`, `0` read as `i` and `o`. So `Сommon Ink` with a Cyrillic С, `HISTORY` and `Hist0ry` are all refused. It covers Latin, Cyrillic and Greek look-alikes and no other script.
- `capabilities`: each `{ name, reason }`, and for `network` also `origins`, up to ten sites such as `https://api.example.com` (no path, no wildcard). The reason is in the author's words and is shown to whoever decides.
- `commands`: `{ id, title }`. In the app the command is `<install id>.<id>`, titled `<plugin name> plugin: <title>`, and can be given a keybinding like any other.
- `views`: `{ slot, id, label }` with `slot` `inspector` (a tab about the open note), `page` (at `/x/<install id>/<id>`, linked under More) or `bar` (one item in the bottom bar, with `width` from 24 to 480 and `end: true` for the right side, and the plugin's name written beside it by the app). All are labelled `<plugin name> plugin: <label>`, so none reads as part of the app. A third-party page is never the home page at `/`: only Common Ink's own plugins register one with `home`.
- `embeds`: `{ name, title, description, height, options }`. A note writes `::x-name{config}`: every third-party embed's name starts with `x-`, which no built-in's does, so a plugin can't take a built-in embed's name, on or off. `<plugin name> plugin: <title>` stands in the line and in the `/` and `::` menus, under its `description` there where it has one (a line of words, up to 120 characters), and the plugin's frame is below the line, in a room `height` pixels tall, which comes from the manifest so nothing moves when the frame loads. A name an earlier plugin already has is refused, and the Plugins page says so. `ink.context.name` is the manifest's own name, without the `x-`. **`config` and `body` are written by whoever can edit the note and run in every reader's browser: treat them as untrusted input.** An embed runs with no Run button, as the reader, with everything the plugin is permitted, so a plugin that acts on its config (reads the note it names, writes what it says) lets any editor of a note steer it in another member's session. The install prompt tells the admin so when a manifest declares embeds. `options` is a list of up to twelve declared options (see [Options](#options-1) under Embeds, with the table of types): the app draws them beneath the embed and writes them into its config, and the frame is handed their values as `ink.context.options`, each as its type or its default, so a plugin reads `ink.context.options.times` and never parses its config. A manifest whose option couldn't be written or read back (a default its own range refuses, a choice value of two words, a text default with a quote) is refused.
- `settings`: options as built-ins declare them (`boolean`, `string`, `number`, `integer`), kept in each member's settings under `<install id>.<name>`.

### Capabilities

`CAPABILITIES` in `src/core/plugins.ts` is the whole of what a plugin can be permitted, and the operations each one opens:

| Capability | Opens |
| --- | --- |
| `notes.read` | `note.list`, `note.read`, `note.backlinks`, `folder.list`, `search`, `daily.find` (the member's daily note for a day, when there is one: nothing is made), `ink.open(noteId)`, `ink.onNote` and `ink.onItems` |
| `notes.write` | `note.create`, `note.write` |
| `todos.read` | `todo.list` |
| `members.read` | `member.list`: names and roles, never emails |
| `network` | no operation: the sites its frames may load from and send to |
| `full-trust` | no operation: where the code runs. See "Full trust" above |

An operation in no row is refused to every plugin that runs shut off, whatever it was permitted: settings, members and invites, sharing, uploads, data sources, History and its reverts and labels, agents, the plugin record itself, and what a member keeps for their own dashboard, their pins and how far they have read the changes (`pin.*`, `visit.*`). A plugin that could mark the changes read would hide from the member what they haven't seen, and no capability covers pins: they are the member's own arrangement, as settings are. `daily.open` is refused too, since it makes a note. A new operation is refused to plugins until a row lists it.

A plugin acts for the member whose app it runs in and never has more than they do: a viewer's plugin with `notes.write` allowed is still refused the write, and a note the member can't see is not found. What it is answered is narrowed too: `note.read` comes without the uploads and members the note refers to. A plugin running with full trust is the exception to both: it is answered as its member is, and asks anything that isn't a member's alone to ask.

### Installing, permitting, asking

The workspace keeps a record of its plugins (`src/core/pluginRecord.ts`, migration `0021`): what is installed, what each is permitted, and who is waiting on an admin. It is the workspace's and no part of anyone's settings. Every member reads it on the Plugins page; only an admin changes it. An agent acts in its member's role: an admin's agent installs, updates, uninstalls and permits as the admin does, and is recorded beside them ("installed by Claude for Ada", migration `0041`); a member's agent reads the record and asks. Turning full trust on stays each member's own click. `docs/mcp.md` lists the tools, and `scaffold_plugin` / `validate_plugin` (`ink plugin-new`, `ink plugin-validate`) make and check a plugin's two files without installing anything.

- **Install.** An admin pastes the manifest and code and presses Review. The prompt lists each capability with the plugin's reason and a checkbox, all unchecked. Install puts the plugin in the workspace and allows what was checked. Installing alone allows nothing.
- **On, for each member.** An installed plugin is available, and off for each member until they turn it on on the Plugins page (`<install id>.enabled` in their settings). Nobody runs a third-party plugin they didn't turn on.
- **Permissions** are the workspace's: one decision per capability, for every member. An admin allows one or turns it off, and can lock it. A locked permission takes no requests and is changed only after an admin unlocks it.
- **A member who isn't an admin** sees the same prompt with "Ask an admin" in place of Allow. Their yes is a request. It allows nothing, and the capability stays off until an admin approves it. A denial clears the requests.
- **A change voids what it changes.** The code is named by its SHA-256. An approval records the code and the capability as declared (`approvalOf`), and stands only while the plugin is still that: new code voids every approval, and a capability declared with another reason or other sites voids its own. The page shows a voided permission as off, saying the plugin changed. Allowing names the code: `plugin.permit` is refused without the hash the admin was shown (`codeHash`), and refused if the plugin was replaced since.
- **Uninstall** takes the plugin's permissions and requests with it. The server refuses the plugin from that moment, and an app that is open loses its commands, views and frames the next time it reads the record: when its window is come back to, every 15 seconds, and at once when the server refuses the plugin. History still names the plugin for the changes it made.

Operations: `plugin.list`, `plugin.read`, `plugin.install`, `plugin.uninstall`, `plugin.permit`, `plugin.request`, `plugin.frame`, and `plugin.trust` for a plugin that asks for full trust.

### Where the code runs

Never in the app's page, unless it asks for full trust and has it (see "Full trust"). Each running piece of a plugin is a frame of its own: the shell the Worker serves at `/embed-frame`, and inside it a frame with no address, an origin no other document has, `sandbox="allow-scripts"`, and a policy of `default-src 'none'`. It is the frame an HTML embed runs in, described under [Frames](#frames). So a plugin's code can't read the app's page, the member's session, cookies, or anything the browser keeps, can't fetch from the app or anywhere else, can't navigate itself, the shell or the app, and can't open a window.

A plugin runs in up to three kinds of frame, each with all of its code and an `ink.context` saying which it is:

- `{ kind: "background" }`: hidden, started the first time one of the plugin's commands is run, and kept. Commands are heard here.
- `{ kind: "view", id, slot, noteId }`: in the inspector, on its page, or in the bar. `noteId` is the open note's id for an inspector tab when the plugin has `notes.read`, and null otherwise.
- `{ kind: "embed", name, config, body, readOnly: true, options }`: below the line that writes the embed. `options` holds the value of each option its manifest declares. It runs without a Run button, since the member turned the plugin on. It is made again when the note says something else of the embed.

The app and a frame talk over a `MessagePort` the app makes for that frame (`src/web/remote/`). The port is who the frame is: nothing in a message is read as an identity. Every message is parsed against a strict schema (`protocol.ts`): another version, an unknown key, a wrong type, a key naming a prototype, or more than 600,000 characters is dropped. One function decides what a message leads to (`decide` in `broker.ts`), from the record as it is now. Each plugin may send 30 messages at once and 15 a second after that, with 8 operations under way; the rest are answered `rate_limited`, and a plugin that keeps on is stopped, with its frames taken out and the reason on the Plugins page. Nothing a frame sends is run, read as markup, or set as HTML.

What the code is given, as `ink`:

- `ink.context`, `ink.granted` (the capabilities allowed now), `ink.settings` (its own options' values), `ink.plugin` (`{ name, version }`), `ink.root` (the element to draw in). A permission that changes starts the plugin's frames again.
- `ink.perform(op)`: an operation from the table above. The app refuses one the plugin isn't permitted, and sends the rest to the server at an address that names the install (`/api/workspaces/<id>/plugins/<install id>/ops`), where it is checked again against the record and performed as the plugin, for the member. A refusal rejects with `{ code, message }`.
- `ink.notify(message)`: a notice at the foot of the app, as text, 200 characters at most, starting with `<plugin name> plugin:`.
- `ink.open(noteId, { background })`: opens a note, with `notes.read`.
- `ink.onCommand(id, fn)`, `ink.onSettings(fn)`.
- `ink.scheme` (`"light"` or `"dark"`) and `ink.onTheme(fn)`, called with the new scheme after the frame's look has changed with the app's. The frame's colors also change when Night shift comes and goes over the dark theme, which leaves the scheme as it was and calls nothing.
- `ink.onNote(fn)`, `ink.onItems(fn)`, `ink.storage`, `ink.onStorage(fn)` and `ink.prompt(question)`: see [One interface for a plugin that runs shut off](#one-interface-for-a-plugin-that-runs-shut-off).

Nothing of the member is sent to a frame: no name, no email, no role.

**A plugin's writes are the plugin's.** `note.create` and `note.write` by a plugin are recorded in History with the plugin as author and the member it acted for, are filtered by it, and are reverted as an agent's are ("Revert all by"). An open editor of the note takes the result as it takes another member's change.

The frame's look is the app's, and follows it from one theme to the other: see [Styling a plugin](#styling-a-plugin). Each frame is cut to its slot, and the frame focus guard applies to every one, the hidden background frame included: a frame that takes the keyboard without the member's pointer on it is stopped.

### Styling a plugin

The app draws a plugin's card, its title, its options and its errors; the plugin draws only what is inside its frame, and the frame starts out looking like the app. Its document is given the app's look as CSS variables on `:root`, and given them again each time the member's theme changes, so nothing a plugin draws with them is left in the other theme:

- Colours: `--bg`, `--bg-elev` (a card's surface), `--bg-side`, `--ink`, `--muted`, `--faint`, `--line`, `--line-strong`, `--hover`, `--accent`, `--accent-soft`, `--accent-ink`, `--on-accent`, `--danger`, `--added`, `--warn`, `--code-bg`.
- Faces and sizes: `--prose`, `--mono`, `--text-small` (12px), `--text` (14px), `--text-large` (16px).
- Corners and room: `--radius-small` (6px), `--radius` (10px), `--space-1` to `--space-4` (4, 8, 12 and 16px).

The app's controls come with them as classes, for a plugin to take or leave: `ink-button` (with `primary` for the one main action, or `quiet`), `ink-input`, `ink-chip`, `ink-card`, `ink-title` (the small capitals of a card's title), `ink-muted`, `ink-row` and `ink-stack`. One line takes all of it for the plain elements too:

```js
document.body.classList.add("ink-kit"); // buttons, fields, lists and headings as the app draws them
```

Before, a plugin that styles itself carries colours that are right in one theme and wrong in the other:

```js
ink.root.innerHTML = `<div style="border:1px solid #ddd;padding:12px;background:#fff">
  <h3 style="color:#333">Votes</h3><button style="background:#5b5bd6;color:white">Vote</button></div>`;
```

After, the same thing is the app's in both themes and says nothing of colour:

```js
document.body.classList.add("ink-kit");
ink.root.innerHTML = `<div class="ink-card ink-stack"><h3>Votes</h3><button class="primary">Vote</button></div>`;
```

A plugin that draws on a canvas, where CSS variables don't reach, reads them with `getComputedStyle(document.documentElement)` and draws again in `ink.onTheme`. The plugin `ink plugin-new` (and `scaffold_plugin`) makes uses the kit and declares an embed with options, as an example of both. The variables and classes are in `src/web/remote/frame.ts`. A built-in in the page uses the app's stylesheet and the same variables.

### What a third-party plugin can't do in this version

- **Editor extensions and completions.** An editor extension is code inside the editor, built from the app's own copy of CodeMirror, with the note's text and every key typed. It can't cross to a frame, and no declarative subset is offered yet.
- **Drawing in the app's page.** No `Embed.render` or `Below.render`, no inline widget in the line beyond the embed's title, no block embeds, and no view in the `column`, `section`, `rail`, `editor`, `overlay`, `mark` or `notice` slots. A view in `bar` is a frame.
- **Writing a note from an embed** (`update`). An embed is read-only. A plugin changes a note only through `note.write`, with `notes.write`, as itself.
- **Keeping much in the browser.** `ink.storage` holds small JSON for this member in this browser. Anything else a plugin keeps, it keeps in a note.
- **Running commands**, its own or any other: there is no call for it, so `plugins.toggle.<another>` is out of reach. It can't change or read settings other than its own options' values.
- **The `app` snapshot**, uploads and their bytes, data sources, sharing, members' emails, agents.

### What isolation does not cover

- **WebRTC.** A frame can open a WebRTC peer connection, which no header a browser honours stops (see Frames). So a plugin can send what it is permitted to read to another computer, with or without `network`. The install prompt says so. Permit a plugin `notes.read` only if it would be acceptable for it to send those notes out. `network` governs `fetch`, images, media, fonts, WebSocket and the rest.
- **The reader's processor.** A frame can spin. The focus guard and the rate limit keep the app answering; they don't make a busy frame free.
- **Names.** Everything a plugin shows in the app carries `<name> plugin:` in front: its commands, notices, page, inspector tab and embeds. A plugin can't take a name of Common Ink's own or a Latin, Cyrillic or Greek look-alike of one, and can still choose a misleading name of its own, or a look-alike from another script. An admin reads the manifest before installing.
- **`updatedBy`.** A note listed for a plugin with `notes.read` says who changed it last, by name, without `members.read`.
- **One notice at a time.** A plugin's notice takes the place of the app's, as any notice does.

`test/browser/third-party-attacks.spec.ts` installs a hostile plugin and has it try, from inside its frame: the page's DOM, cookies and storage; the API with and without credentials; other plugins' frames, and forged ports and messages at them and at the app; malformed, oversized, flooding and identity-claiming messages on its own port; operations it wasn't permitted, prototype keys and path tricks; navigation of itself, the shell and the app; the keyboard; drawing outside its box; writing without attribution; running commands; outliving its uninstall; and the network without a grant and past the granted sites. Each fails, beside the allowed path working in the same run. `test/core/third-party.test.ts` and the plugin actors in `test/core/access-matrix/matrix.ts` hold the server to the same.

### Plugins put on the page by a test

`window.__INK_FIXTURE_PLUGINS__` puts plugin values straight into the app's page. It is for testing what the host refuses an untrusted plugin that does run in the page (`test/browser/plugin-failures.spec.ts` and others), and it is read only where the Worker says `dev` in `/api/me`, which is where dev sign-in is on: this machine and Previews. Production ignores it. A plugin put there is not trusted and gets the refusals below.

## What a plugin in the page that isn't Common Ink's own is refused

A third-party plugin runs in the page only with full trust, which lifts the first two of these. So this is about fixture plugins and about defence in depth. The host is told its own plugins as the values it was built with (`trusted` in `createPluginHost`), and which of a workspace's runs with full trust by the app's own runtime (`inPage` on what `createInstaller` lists), so a plugin can't become either by the id or name it gives itself. Any other plugin:

- is handed `host.agents`, `host.members` and `host.sharing` with every method refusing, and a `host.uploads` that knows no upload, answers `about:blank` for every address and refuses `send`;
- is refused, through `host.perform`, the member's data sources (`source.*`, `event.*`, `contact.*`, `record.*`), every `upload.*` operation, every `plugin.*` operation, and the member's pins and their last visit (`pin.*`, `visit.*`): one that could mark the summary read would hide from the member what they haven't seen;
- can't register a page with `home`, and so can't take over `/`;
- is refused, as every plugin is, settings, changes to who is in the workspace, sharing, an upload's bytes, and installing, permitting or reading plugins.

These are refusals by the host's own objects, and not a boundary: code in the page can read the page. That is why third-party code is not in it unless an admin granted it full trust and the member turned it on.
