An audit of `main` at `5f5383de`: the Worker (`src/worker`), the web app (`src/web`), the core they share (`src/core`), `wrangler.jsonc`, the migrations and `public/_headers`. It follows Cloudflare's [security-audit skill](https://github.com/cloudflare/security-audit-skill): map the code, hunt by coverage unit, give every candidate to a fresh verifier that tries to refute it, write schema-checked records, and report. Earlier audits (#60, #116, and PRs #83, #123, #134, #135) fixed or decided many items. None of those are filed again here.

Seven findings are confirmed. Each was reproduced with a test that fails on `main`, and each was fixed with that test, one change each (#186). Five more needed a decision. Audrow took the recommendation on each on 22 October, and they are fixed the same way in #197. Five candidates were refuted.

## Confirmed and fixed

Each fix is one change in #186 with the test that reproduces the finding. The tests fail on `main` and pass with the fix.

### 1. A plugin frame runs the app's keys as the member

**Severity:** medium. **Reproduced:** `test/browser/third-party-attacks.spec.ts` "a plugin's frame that doesn't hold the keyboard can't run the app's keys".

**Exploit.** An admin installs a third-party plugin that asks only for `notes.read`. Its code posts `{ v: 1, key: "mod+shift+e" }` on its port from a frame that holds no keyboard, such as the background frame its command starts. The app runs the command bound to that key as the member: the open note is archived. `mod+z` and `mod+shift+z` undo and redo the member's own changes, and any command the member has bound to a key is reachable the same way. The changes are recorded as the member's, not the plugin's. On `main` the test's note ended up archived.

**Where.** `src/web/remote/broker.ts:68` returns `{ kind: "key" }` before it reads the plugin's capabilities. `src/web/remote/adapter.tsx:227` runs the bound command with no check that the frame holds the keyboard.

**Fix.** The adapter takes a chord only while an iframe inside that plugin's box holds focus. The frame guard (`src/web/frameGuard.ts`) already lets a frame keep focus only after the member reached it.

### 2. An agent or app connected as its person signs out everywhere stays connected

**Severity:** medium. **Reproduced:** `test/core/sessions.test.ts` "leaves no agent or app connected by a request its session made in the moment before".

**Exploit.** Someone holds a stolen session cookie. The member signs out everywhere, which is the documented answer to a lost laptop. An agent request already in flight checked the session before the sign-out and writes the agent after it. The new agent token, or an OAuth app's code and tokens, keeps working, because agent tokens don't carry the session they came from. The attacker can keep requests in flight, and reconnecting one OAuth app isn't held back by the 20-agent cap. On `main` the request answered 201 and left a live agent.

**Where.** `src/core/agents.ts` `prepareAgent` and `connectAgent`; `src/core/oauth.ts` `consent`; `src/worker/mcp/agents-api.ts` and `src/worker/oauthConsent.ts`, which threw away the session's sign-out count. `connectClipper` (`src/core/clipper.ts:56`) already does this right.

**Fix.** The routes pass the session's `sessions_ended` along. The agent is written by `INSERT … SELECT … FROM people WHERE id = ? AND sessions_ended = ?`, and the OAuth code only for an agent that was written. When nothing is written, the answer is 409 "You were signed out everywhere as this was being connected".

### 3. A link or grant made as a note becomes private stays on it

**Severity:** medium. **Reproduced:** `test/core/grants.test.ts` "keeps no link or grant that another member made in the moment it became private".

**Exploit.** An editor makes a public link to a note just as its maker makes the note private. The editor's check runs before the note becomes private, and the link is written after the batch that clears other people's grants. The link stays on the private note, and its token opens the note's text from then on. The same holds for a grant to a person, and for an upload made private. On `main` the public link row was left on the private note.

**Where.** `src/core/sharing.ts` `setGrant` and `linkTo`: the check is in JavaScript and the `INSERT` has no condition. `makePrivate` removes only the grants that exist when it commits. ADR 0002 lists this window as still open.

**Fix.** Both `INSERT`s are `INSERT … SELECT … WHERE NOT EXISTS` the item being someone else's private note or upload. A grant that writes nothing is refused with the reason read again.

### 4. A dev server started with `--host` signs in anyone who names `localhost`

**Severity:** medium (a developer's machine, not production). **Reproduced:** live against `npm run dev -- --host <lan address>`, and `test/node/this-machine.test.ts`.

**Exploit.** A developer runs the dev server with `--host`, as `scripts/dev.ts` documents, on a home network or a tailnet. Another machine sends `Host: localhost:5173` to the server's network address. The Worker reads `localhost` from that header and treats the request as this machine's, so it is the dev user with no cookie, and `/auth/dev?email=` hands out a 30-day session as any email. That opens the developer's local notes, and their Google calendar and contacts if `.dev.vars` holds a real Google client. Vite's own host check always lets `localhost` through. Before the fix the spoofed request got 200 as Dev User and the sign-in a session cookie; the same server's own address got 401.

**Where.** `src/worker/auth.ts:25` `devSignIn` trusts `url.hostname`. Behind Vite that is the client's `Host` header.

**Fix.** `scripts/this-machine.ts`, the first middleware in `vite.config.ts`, reads the hostname from `Host` the way the Worker does (`new URL`) and answers 403 when it is one `devSignIn` takes for this machine but the request did not come from a loopback address. The Worker and the guard share one pattern, `THIS_MACHINE` in `src/worker/hosts.ts`. Checked live afterwards, with the forms a string match would miss (`localhost:`, `LOCALHOST`, `[0:0:0:0:0:0:0:1]`, `[::0001]`, `127.0.0.1:`): every one gets 403, the network name still gets 401, and the machine itself still signs in.

### 5. A clipper token can tell which note titles and members exist

**Severity:** low. **Reproduced:** `test/core/clipper.test.ts` "learns nothing of the member's notes or fellow members".

**Exploit.** The clipper's grant is told to the member as create-only: it "can't read, change or delete anything". Someone holding a clipper token sends `create_note` with `[[Guessed Title]] [[Nothing Has This]]` and `linkTitles: "resolve-strict"`. The refusal names whichever title no note has, so a title the member has answers differently from one nobody has. With `"resolve"` the answer carries the matched note's id, and `mentionNames: "resolve"` does the same for members. The real extension always sends `"keep"`.

**Where.** `src/worker/mcp/tools.ts` `callTool` passed the clipper's `linkTitles` and `mentionNames` through to `note.create` as the member.

**Fix.** A clipper's `create_note` always keeps links and mentions as written.

### 6. A guest can confirm a member's name with `editor:`, `author:` or `uploader:`

**Severity:** low. **Reproduced:** `test/core/grants.test.ts` "can't confirm a member's name by searching for what they wrote".

**Exploit.** Since #135 a guest sees "A member" for every author. A guest who searches `editor:"Ada Lovelace"` got back the note Ada wrote, while a name nobody has was refused. That confirms the guessed name. The same worked for a plugin without `members.read`, and in `todo.list` and `upload.list`.

**Where.** `src/core/operations.ts` `finding()`: `authors()` and `uploaders()` matched names without the `namesMembers` rule that `unnamed()` applies.

**Fix.** A member is found by name only for an asker who is told members' names, or when the member is the asker. `@me` still works. The access matrix now expects a guest's search by a member's name to be answered as one by a name nobody has.

### 7. A file-site address outlives sign-out everywhere and leaving the list

**Severity:** low; it applies only where `FILE_ORIGIN` is set. **Reproduced:** `test/core/upload-http.test.ts` "lapses with the member's sessions".

**Exploit.** A PDF opened in a tab goes to an address on the file site that is good for 10 minutes and needs no cookie. The address was checked against the grant on every request, but not against the allowlist or sign-out everywhere. A person taken off `ALLOWED_EMAILS`, or a stolen session that was signed out, kept reading the PDF through an address made just before. On `main` the address still answered 200 after the sign-out.

**Where.** `src/worker/files.ts` `fileSiteResponse` and `siteAddress`.

**Fix.** The address carries the session's sign-out count. The file site refuses it unless that count still holds and the person is still on the list.

## Decided, then fixed

These needed a product decision. Each was decided as recommended, and fixed in #197, one change each, with a test that fails on `main` first.

### 8. An invite takes effect without being accepted

Every person who signs in is admin of a workspace of their own, and `member.invite` takes any email. The invitee becomes a member the next time they open the app (`arrive()`, `src/core/accounts.ts:71`), with no accept step. That is by design (`CONTEXT.md`). Two things follow for any two people on the allowlist:

- **Daily sign-out.** The inviter can then sign the invitee out everywhere (`member.signOut`, `src/core/membership.ts:135`). That ends every session in every workspace, revokes their agents that aren't pinned to a workspace, and stops their real admins from signing them out for a day. The invitee can leave, but a new invite brings them back. The once-a-day limit's stated reason, "a day is time enough to leave it", doesn't hold.
- **Agent reach.** The inviter's workspace joins the reach of the invitee's unpinned agents. Its name and its agents file go into the agent's instructions (`src/worker/mcp/mcp.ts:75`), and its writes can land there. ADR 0017 keeps guest workspaces out for exactly this reason ("anyone can share a note with an email"), but an invite is just as easy to make.

**Decided and fixed:** an invite to someone who already had an account waits for them to accept it. `arrive()` takes up only invites made before the person's account (their first sign-in), and an invite's link shows anyone else it is for the workspace, the role and who invited them, with Join and Not now. Joining is a `POST` to the invite's address from Common Ink's own page (`acceptInvite`, `src/worker/index.ts`), so a link followed from another site joins nobody. Tests: `test/core/members.test.ts` "waits for a person who already has an account to accept it" and "an invite's link tells the invited person what it is", and `test/browser/members.spec.ts` "someone who already has an account joins a workspace only by saying so".

### 9. A database restore brings back access that was taken away

The restore runbook (`docs/runbooks/restore.md`) rewinds D1 with Time Travel, then replays only account and workspace deletions (`src/core/erase.ts:422`). Removing a member, revoking a grant or a link, disconnecting an agent and signing out everywhere live only in D1. After a restore to a time before them, each of those people, links and tokens works again, and nobody is told. Taking someone off `ALLOWED_EMAILS` survives, since that list isn't in D1.

**Decided and fixed:** each of these, and a member's role being changed, is kept in the bucket the way deletions are, as `deletions/<member|role|grant|agent|signout|clipper>/<id>`: by the operation that does it (`ctx.revoked`, kept once it succeeds), and by the Agents page and the clipper's routes. `scripts/redo-deletions.ts --since` takes each away again, and the runbook says so. A record of a kind it doesn't know is refused, and the rest are still made again. Not kept, and listed in the runbook for admins to check: an invite taken back, a grant narrowed from edit to view, a link changed from public to signed-in, an agent's limits narrowed, an older clipper or OAuth connection replaced by a newer one, and an OAuth token revoked by its app. Test: `test/core/redo-deletions.test.ts` "is taken away again by the same run that makes deletions again".

### 10. A running plugin draft an agent saved keeps running after the agent is disconnected

A full-scope agent may save a draft of a plugin with `running: true` (tested as intended in `test/core/drafts.test.ts`). The draft then runs in the member's browser in place of the original, with the original's permissions. Disconnecting the agent leaves it running: the draft row doesn't record who saved it (`src/core/pluginRecord.ts:532`). An agent's plugin requests, by contrast, end with the agent (`src/core/pluginProposals.ts:6`). The reach depends on the original: notes.read for the app's own plugins, or notes.write and network for a third-party one an admin allowed.

**Decided and fixed:** an agent may save a draft but not switch it on. Its `save_draft` with `running: true` is refused, and any save by an agent leaves the draft off until the member switches it on in the app, so code an agent wrote never runs as the member unless they chose it, and nothing of the agent's runs on once it is disconnected. Test: `test/core/drafts.test.ts` "runs only once its member switches it on".

### 11. Abandoned uploads in parts can hold up everyone's upload removal

`upload.start` makes an R2 upload in parts with no limit on how many one person has pending (`src/core/uploads.ts:279`). After a day, the hourly job marks them for removal, and it removes at most 1000 a run across all workspaces, in a fixed order with no fairness (`src/core/purge.ts:175`). One person who starts tens of thousands of uploads keeps other workspaces' uploads that are due (30 days in Trash, or abandoned) waiting past what `docs/legal/privacy.md` promises. Nobody can read them meanwhile. If the chunk's R2 calls pass the run's subrequest limit, the same chunk fails every hour.

**Decided and fixed:** a person, with their agents and plugins, may have 100 uploads in parts started and not finished (`MAX_PENDING_PARTS`), counted in the statement that writes the next. The hourly job takes removals in turns across workspaces, in chunks of 100. In a chunk that fails, each upload is tried alone, so one that won't go holds up no other; three failing in a row stop the tries, so a bucket that is away costs a few calls a chunk. Tests: `test/core/uploads.test.ts` "is removed when due though another workspace has left more abandoned uploads than a run removes" and "refuses someone a 101st upload in parts".

### 12. Download addresses tell another site whether its visitor is in a workspace

The session cookie is `SameSite=Lax`, so a top-level navigation from another site carries it. `GET /api/workspaces/<id>/export`, and an upload's address for a file that is downloaded, answer a member with a download and anyone else with a JSON error (`src/worker/files.ts`). A page that opens one in a popup can tell the two apart, a known XS-Leak, and so learn whether its visitor can see a workspace whose id it knows. The export also streams a whole zip to the visitor. The ops route already checks `Origin`; these don't.

**Decided and fixed:** a browser's request for an upload or an export that comes from another site (`Sec-Fetch-Site` neither `same-origin` nor `none`) is sent into the app, to `/uploads/<id>` or `/`, the same for a member, anyone else and nobody, so it tells that site nothing. The app then finds the workspace the upload is in (`/api/uploads/<id>`, as for a note), so it opens there. The app's own links, an address typed or bookmarked, and agents' tokens are answered as before. A link to an upload opened from a chat or an email now opens it in the app rather than downloading it. Test: `test/core/upload-http.test.ts` "an upload or an export asked for by another site".

| A heading of many `#`s makes the title quadratic | Not in the Worker: in workerd, `summarize()` reads a 500,000-character run of `#` in about 1 ms. Node's V8 is quadratic on the same pattern (4.2 s at 40,000 characters), so it is a hardening note below. |

## Hardening notes

None of these crosses a boundary on its own.

- **`unclosed()` in `src/core/markdown.ts:9`** strips a heading's closing `#`s with `/#+$/`, which is quadratic outside workerd. An index loop is linear everywhere.
- **Excalidraw scenes** keep `iframe` elements whose `customData.generationData.html` the editor draws as a `srcdoc` frame, without the HTML embed's Run step. The page's CSP stops script, so it is static HTML only. Dropping that field before `initialData` would close it.
- **Idempotent writes** key a note write's `writeId` on the note alone (`changes_by_write`), not on its author, unlike `PRIOR_WRITE` and uploads.
- **A `plugin.permit` proposal** binds only the code hash, not the manifest's origins and reason, and its card shows neither.
- **Byte routes have no per-person rate limit:** upload, download, export and part addresses are answered before `OPS_LIMIT`. `export.open` takes any `after`/`through` range, past the plan's part caps.
- **Workspace erasure** spends one budget in deletion order, so one large deleted workspace delays the others (the data is already cut off).
- **`folder.describe`** updates by id alone; adding `workspace_id` would make the statement stand on its own.
- **The 20-agent cap** is counted in a statement of its own before the agent is written, so requests at the same moment can pass it together.
- **A grant's write** now checks that its item isn't someone else's private one, but not again that its maker may still share it (`MAKER_SHARES` does that for grants taken up later). A maker demoted in the same moment still writes it.
- **The file site in development** answers 404 where `.dev.vars` sets a Google client or an allowlist and `FILE_ORIGIN` is a `*.localhost` address, since dev sign-in doesn't take that name.

## Coverage and how it was done

- **Method.** The skill's six phases in its `quick` profile, scoped to the paths above. A deep run of the same skill earlier the same day (at `69cedb40`) mapped the code and covered 51 units, but validated nothing. This run read that run's ledger and candidates. It gave its 14 in-scope candidates to fresh verifiers against current source, hunted its 9 deferred units, and hunted the code changed since: tag and folder descriptions, the agents file, the MCP dispatcher, Excalidraw and crop, and the plugin frame bridge. One final coverage critic then checked the ledger.
- **Agents.** 4 hunters, 8 verifiers and 1 critic. One verifier's answer was not valid JSON; as the skill says, it was discarded and its three candidates given to a fresh verifier.
- **Evidence.** Agents read source only. The skill runs target code only inside an OS sandbox this Mac can't fully provide, so the parent reproduced each confirmed finding afterwards with the repository's own tests: vitest on local Miniflare with dummy data, Playwright against a dev server on this machine, and the dev server itself for finding 4. That is outside the skill's sandbox rule, and was done because each fix needed a test that fails first.
- **Not covered.** The critic found two gaps, recorded as deferred: superlinear parsing of another person's note text in the viewer's browser (the reader, the share page, CodeMirror decorations), and drag-and-drop data that may come from another site's page (`src/web/dragged.ts`). The Chrome clipper extension was out of scope; the earlier run left one lead there, the clipper's document fetch following redirects with the member's cookies.
- **Records.** The skill's ledger and findings records, both checked by its validators, are kept outside the repository with the run's files.
