# Connecting an agent

A member connects an agent in the web app, on the Agents page (`/agents`, from the workspace menu or the "Go to Agents" command), and gets a token for it. The page shows the token once, inside a prompt to paste into the agent: what Common Ink is, what the agent may reach, the server's URL and the token, how to add the connection to its own client (the config's shape, and `claude mcp add` for Claude Code), how to check it works by listing its workspaces and folders, and to keep the token secret (`src/web/plugins/agents/prompt.ts`). The commands and config to set it up by hand are under "Set it up by hand". An agent's "Set up again" shows the prompt later with no token in it, since the token can't be shown again. The page also lists the member's agents, edits what each may do, and disconnects them. The agent sends the token to `/mcp` (the MCP server) or uses the `ink` command, which calls `/mcp`. Both go through the same operations as the web app (`src/core/operations.ts`), as the member who connected the agent.

## Rules

- An agent acts with its person's access in each workspace, and no further: their role where they are a member, narrowed by any grant that names them, and where they are a guest only what was granted. A viewer's agent can read and cannot write. A note its person can't see, such as another member's private note, is no note to the agent: it is in no listing, count, backlink, link title or history, and asking for it by id answers `not_found: No such note`, the same as for an id that was never a note's. Every listing of a note carries `access`, `edit` or `view`: what the agent may do with it.
- An agent can't share. Granting a note, a folder or an upload to someone, making or removing a link, making a note private, and reading who a note is shared with are for the member, signed in, in the Share dialog. A link can put a note before the whole internet, and none of this is a change in history that could be reverted.
- Its changes are recorded with the agent as author (`author_kind = 'agent'`, `author_id` = the agent's id), under the name the member gave it, so they can be told apart from the member's own.
- A member who loses access to a workspace takes their agents' access with them: every call checks the member's membership at the time. Removing a member, or their leaving, ends it on the agent's next call, and a change of role changes what the agent can do on its next call.
- An agent can see who is in a workspace (`list_members`: each member's person id, name, and role, and never an email, whatever its member's role) and can't change it. Inviting, changing a role, removing a member, leaving, and listing or revoking invites are for the member, signed in, on the Members page. Who is in a workspace decides who can read and change everything in it, that isn't a change in history that could be reverted, and an agent reads notes other people wrote, so one that was talked into it could invite a stranger as admin. The core refuses these to an agent whatever its member's role, not only the tools.
- An agent works with plugins in its member's role (`src/core/operations.ts`, handlers marked `by: "owner"`: the member or their agent, never a plugin). Every agent reads the record (`list_plugins`, `ink plugins`: each third-party plugin, what its manifest declares, each capability with its reason and whether it is allowed, locked or voided, who is waiting on an admin, and full trust as its member is told of it), reads a plugin's code (`read_plugin`, `ink plugin`), and makes and checks plugins: `scaffold_plugin` (`ink plugin-new NAME --out DIR`) answers a manifest and code to start from, and `validate_plugin` (`ink plugin-validate`) says what installing them would make of them, or why it would be refused, without keeping anything. An admin's agent installs, updates (`pluginId`, the plugin it takes the place of), uninstalls and permits, as the admin does (`install_plugin`, `uninstall_plugin`, `permit_plugin`), granting full trust included; the plugin's page then says "installed by <agent> for <admin>", and each decision "decided by <agent> for <admin>" (migration 0041). Any member's agent keeps that member's own drafts (`list_drafts`, `read_draft`, `save_draft`, `discard_draft`: nobody else's, and one it sets running runs for its member alone) and asks an admin for a permission (`request_plugin_permission`). A read-only token reads and changes nothing here, and a token limited to folders is refused all of it, the record included: none of it is in a folder. Two things stay the member's own, in the app: turning full trust on for themself (`plugin.trust`), which runs the plugin's code in their session and is their consent to that, and a frame's token (`plugin.frame`), which opens a frame in their browser. `--manifest` and `--code` take the text, or `@file` to read it from a file. A plugin's changes are in history under its own id: `history` and `revert_author` take the author `plugin:<id>` as they take an agent's.
- A token expires after 90 days by default (`expiresInDays`, 1 to 365, or `"never"` for a token that doesn't expire). An expired token is refused like an unknown one.
- A token can be pinned to one workspace (`workspaceId`: it sees only that workspace, even if its member is in others) and can be read-only (`readOnly`: it can read and can't change anything, even for an editor or admin). Both are checked in the core operations, not only in the tools.
- A token pinned to one workspace can be limited to folders there (`folderIds`): the agent reaches those folders, the folders inside them, and the notes in those, with what its member may do with each and no more. Everything else is to it as a note its person can't see: in no listing, count, backlink, link title, history or author list, and `not_found` by id in the words used for an id that was never there. A link in a note it can read to a note outside reads as a link to no note (`title: null`); the link's target id is part of the text it can read. Checking off a repeating todo in its folders completes it and files nothing on a daily note outside them, and it is given no daily note (`daily_note` is refused). It makes notes and folders only inside its folders: `create_note` needs a `folderId` unless Unsorted is one of them, a note can't be moved in or out, and the folders it is limited to can't be renamed or moved by it, since a name refused as taken would name a folder beside them. It moves a folder (`move_folder`) only from inside one of its folders into one of them, never to the top. The limit follows the folders as they are: a note or folder moved in is reached and one moved out isn't. A folder deleted since stays in the list and stands for nothing, so an agent whose folders are all gone reaches nothing, never everything. It isn't told who is in the workspace (`list_members` is refused), since some of them have only written outside its folders. An admin's limited agent deletes a folder of its own that is empty to it as the admin would, and a note there that the admin can't see goes to Unsorted. `list_workspaces` answers the agent's own `folderIds`, null when it has no limit. Checked in the core where access is resolved (`resolve` and `SEEN` in `src/core/access.ts`), not in each tool.
- Names aren't unique: a member can have several tokens named "Claude", told apart on the Agents page by the first characters of each token. Each token is its own author in history. An agent has a name and nothing else to call it by.
- What an agent may do can be changed after it is connected, by the member who connected it and nobody else: whether it is read-only, when it expires, which workspace it reaches, and which folders it is limited to there. The token stays the same, and the agent's next call is held to the edit. A disconnected agent can't be edited; an expired one can be given a new expiry.
- Disconnecting an agent stops its token at once. Only a SHA-256 hash of a token is stored; the token is shown once, when the agent is connected.
- A token works only in an `Authorization: Bearer` header. It is not a cookie, so a web page can't use it.

- An agent can't sign anyone out, its own member included. Signing out everywhere is for the member, signed in, from Settings, and for an admin from the Members page. By default it disconnects the member's agents too (`agents: true` on `member.signOut`): all of them when the member does it, and those that reach the workspace when an admin does. Unticked, it ends sessions only and every agent stays connected.
- An agent can archive a note, move it to Trash and restore it, with edit on the note, since each can be taken back. It can't remove a note from Trash for good: that takes the note's history with it and nothing brings it back, so it is for the member, signed in, on the Trash page.

- An agent can find uploads with the query language, read one's details and where it is used, upload a file of up to 25 GB (in parts its own shell sends, so the bytes never pass through the model), download one, put one in a note, move, archive, trash and restore one, with the same access its member has. It can't remove an upload from Trash for good or make one private: both are for the member, signed in. A token limited to folders is given the uploads in those folders and no others, by every tool and by the address that serves the bytes, and it uploads only into them: it names the folder, since Unsorted isn't one of them.

- An agent reads its member's data sources and no other member's: `list_events`, `list_contacts` and `read_record` answer for the member who connected the agent, whatever their role, and there is no argument that names anyone else. `update_event` and `create_event` change the member's real calendar, as the member, and a read-only token is refused them and `refer_record`. A change to an event, or an event added, is not in Common Ink's history and can't be reverted from here. An agent can't connect or disconnect a data source: agreeing is the member's, in their browser. Nor does it change or add a contact (`contact.update`, `contact.photo`, `contact.create` are in `NOT_FOR_AGENTS`): a contact is where the member's mail and calls go in every app that reads it, a change to one is in no history here, and an agent talked into it by a note could send them to a stranger. It reads them with `list_contacts` and `read_person`. A token limited to folders is refused all eight tools: the calendar and the contacts are in no folder, so they are outside any limit. It still reads `::event{…}` and `::contact{…}` in its notes as every reader does, as a reference and a label. What an agent reads from a data source is the member's private data, and an agent that writes it into a shared note has shared it (`docs/adr/0006-data-sources-are-one-persons.md`).

## Connect, edit and disconnect (signed in, from Common Ink's own origin)

    POST   /api/agents        {"name": "Claude"}   ->  201 {"agent": {...}, "token": "cink_..."}
    GET    /api/agents                             ->  {"agents": [...]}   (never the token; shows expiresAt, workspaceId, readOnly, folderIds)
    PATCH  /api/agents/<id>   {"readOnly": true}   ->  {"agent": {...}}
    DELETE /api/agents/<id>                        ->  204

Optional fields on the POST: `expiresInDays` (default 90, at most 365, or `"never"`), `workspaceId` (one of the member's workspaces), `readOnly` (true or false), `folderIds` (1 to 50 folders of `workspaceId` that the member can see; left out, the agent reaches all notes). Any other field is refused with a 400 and no token is made: each option narrows the token, so one misspelt and dropped would leave it wider than was asked for. For example, a read-only token for two folders of one workspace that lasts 30 days:

    {"name": "Claude", "expiresInDays": 30, "workspaceId": "<workspace id>", "readOnly": true, "folderIds": ["<folder id>", "<folder id>"]}

The PATCH takes the same four fields, each optional, and changes only the ones it is given: `expiresInDays` counts from the edit, a null `workspaceId` lets the token reach every workspace again, and a null `folderIds` lets it reach all notes again. Folders go with one workspace: `folderIds` without a `workspaceId`, on the POST or on a token that reaches every workspace, is refused, a folder that isn't in that workspace or that the member can't see is `404 No such folder`, and a limited token is moved to another workspace only by an edit that also names its folders there, or null. Any other field is refused. These calls need a member's session, which an agent's token is not, so an agent can't connect, edit or disconnect an agent, its own included. They aren't workspace operations, so they have no tool and no entry in `NOT_FOR_AGENTS`: an agent belongs to a person, across their workspaces.

## MCP

`POST /mcp` with `Authorization: Bearer cink_...` and `Content-Type: application/json`. Streamable HTTP, stateless: one JSON-RPC message (or a batch) per POST, answered as JSON. No server-sent events, no sessions. Without a valid token the answer is 401, which says where to sign in by OAuth (see Connecting by OAuth).

Tools: `list_workspaces`, `list_notes`, `read_note`, `note_syntax`, `create_note`, `write_note`, `edit_note`, `backlinks`, `rebuild_links`, `list_todos`, `todo_filters`, `set_todo`, `todo_history`, `daily_note`, `find_daily_note`, `rebuild_todos`, `move_note`, `note_history`, `search`, `list_tags`, for a note's state `archive_note`, `trash_note`, `restore_note`, `list_trash`, for the member's data sources `list_sources`, `list_events`, `update_event`, `create_event`, `list_contacts`, `refer_record`, `read_record`, `notes_about_record`, `read_person` for a person a mention names, for uploads `list_uploads`, `read_upload`, `place_upload`, `move_upload`, `archive_upload`, `trash_upload`, `restore_upload`, `list_trashed_uploads`, `start_upload`, `resume_upload`, `finish_upload`, `abort_upload`, `upload_file`, for folders `list_folders`, `find_folder`, `create_folder`, `rename_folder`, `move_folder`, `delete_folder`, and for history `history_summary`, `history`, `change_diff`, `note_blame`, `history_authors`, `history_diff`, `preview_reverts`, `revert_many`, `label_revision`, `revert_note`, `revert_changes`, `preview_revert`, `revert_author`, `undo`, `redo`, for the member's dashboard `list_pins`, `pin_note`, `last_visit`, `list_members` for who is in the workspace, and for its plugins `list_plugins`, `read_plugin`, `scaffold_plugin`, `validate_plugin`, `install_plugin`, `uninstall_plugin`, `permit_plugin`, `request_plugin_permission`, `list_drafts`, `read_draft`, `save_draft` and `discard_draft`.

An argument that holds an id is named for what it is the id of, the same in every tool: `workspaceId`, `noteId` (`noteIds` for several), `folderId`, `uploadId`, `pluginId` (a plugin, or the plugin a draft is of), and `parentId` for the folder a folder is made in. Each tool takes an optional `workspaceId`, which can be left out when the member belongs to only one workspace. Each tool's description ends with an example call, such as `Example: {"noteId":"k3f9q2m8x1ab"}` for `read_note`; its ids are made up. The names arguments had before are still taken, so an agent written for them keeps working: `workspace` for `workspaceId` in every tool, and `id` for `noteId` in the tools on one note, for `folderId` in `rename_folder`, `move_folder` and `delete_folder`, for `uploadId` in the tools on one upload, and for `pluginId` in the tools on one plugin or draft (`replaces` in `install_plugin`). A tool's schema lists each old name marked `deprecated`, and passing an old name and its new one with different values is refused. An argument a tool doesn't take is refused by name, with the names it takes and a guess at the one meant: `list_folders takes no "workspace_id": did you mean "workspaceId"? It takes workspaceId.` `test/core/agent-parity.test.ts` holds each tool to these names and checks that each example is a call its tool takes.

Every time in an answer is an ISO 8601 string with the offset of the member's time zone (the `daily.timeZone` setting, or UTC): `"createdAt": "2026-10-15T09:30:00.000-07:00"`, and so `updatedAt`, a history change's `createdAt`, `firstAt` and `lastAt`, a completion's `at`, a plugin's `installedAt`, `stateAt`, `trashedAt` and `purgesAt`, and `last_visit`'s `readUntil` and `now`. Due dates and days are plain dates, `2026-10-14`. An argument that is a time (`updatedSince`, `from`, `to`) takes an ISO 8601 time or milliseconds since 1970. A page's `next` is the one exception: it is passed back as `before` exactly as given, and keeps its time in milliseconds. The `ink` command prints the same answers.

Every operation the web app performs has a tool with the same fields, and every tool has an `ink` command. `test/core/agent-parity.test.ts` reads the operation schema and fails when one is missing; an operation kept from agents on purpose is listed with its reason in `NOT_FOR_AGENTS` (`src/worker/mcp/tools.ts`). The three operations that carry a file's bytes, `upload.create`, `upload.part` and `upload.open`, have no tool of their own because a tool call carries only text: they are listed in `OVER_HTTP` beside it with the address an agent uses instead, and each has an `ink` command (see Uploads over HTTP). `upload_file` is the one tool with no operation of its own: it takes a small file as base64 and performs `upload.create` with it. Two kinds are kept from agents: reading and writing the member's settings, which shape the member's own app and are checked against a schema only the app has, and every change to a workspace's members and invites (see Rules). The core refuses them to an agent, not only the tools. Connecting and disconnecting agents is not an operation: it needs a member's session, so an agent can't make another token.

`note_syntax` takes no arguments and writes nothing. The answer is a short example of each thing a note can hold besides plain paragraphs, among them a form, a kanban board, a timer, an upload, a link, a mention and a todo. The examples are one table in `src/core/noteSyntax.ts`. `test/core/plugin-note-syntax.test.ts` fails when a built-in embed has no row in it. `create_note` and `write_note` say to call `note_syntax` before writing a form, a board, or any other embed, and so do the instructions `initialize` answers with. `ink note-syntax` prints the same answer.

`edit_note` changes lines of a note and leaves the rest. Each edit is `{ from, to, text }`. Lines are counted from 0 in the note at `baseRevision`. `from` is included and `to` is not, so equal numbers insert and an empty `text` deletes. A newline after the note's last line is not a line of its own, and a newline after the last line of `text` is not kept. Every range is counted in the revision that was read, so one edit does not shift another, and two that overlap are refused. What was put in is merged with edits made since `baseRevision` the same way `write_note` merges a whole note. A line the edit doesn't name stays, including a form's JSON that a member answered after the agent read the note. Checking a repeating todo's box here completes it as `write_note` does. `ink edit` takes `--from`, `--to` and `--text` for one range, or `--edits` as a JSON list of them.

History only goes forward. A revert, an undo, or a redo is a new change under the agent's name that names the changes it reverted (`reverts`), and each change it reverted names it (`revertedBy`). There is no putting a change back: to have a reverted change again, revert the change that reverted it, which `revert_changes` does like any other, however many reverts deep. `revert_changes` refuses a change that is already reverted and names the change to revert instead. Read history from the top down: `history_summary` lists the notes that changed, latest first, each with its count of changes and the lines they added and removed; `history` lists changes, each with the lines it added and removed (`added`, `removed`) and, unless `diffs` is false, its diff; `change_diff` reads one change's diff. All three take the same `noteIds`, `authors` and time range, and a summary counts only the changes that match. `history` filters by `authors`, so an agent's changes can be listed on their own and passed to `revert_changes`. `preview_revert` says what a revert would do and writes nothing: pass `revisions` for what `revert_changes` would do, `to` for what `revert_note` to that revision would do, or `author` for what `revert_author` would do to that one note, and it answers with the note's `revision` it was worked out at, the `revisions` that would be reverted, the `diff` from the note as it is to the note after, `overlaps`, the later changes that still stand and edited the same lines, and `conflicts`, each place they did, top of the note first: the lines as they were before the reverted changes (`before`), as they are now (`now`), as the revert leaves them with the later edits kept (`kept`, starting at `line` of the result), and the later changes that edited them with their authors (`later`). What a later change did to other lines is no conflict and always stays. A revert settles each conflict with a choice, passed as `resolve: { at, choices }` to `revert_changes` or `revert_note`: `"keep"` keeps the later edits on a line the revert otherwise returns to how it was (what a revert does when `resolve` is left out), `"back"` returns the lines to `before` and drops the later edits to them, and `{ "text": "..." }` puts the lines given there (an empty string for none). `choices` is one of the first two for every conflict, or a list with a choice for each in the order the preview lists them; `at` is the `revision` the preview answered with, and the revert is refused when the note has changed since, so preview again. Pass the same `resolve` to `preview_revert` to read the diff of the revert settled that way. The revert is one change whichever way its conflicts are settled, and reverting it takes what was chosen out with it. It refuses what the revert itself would refuse, in the same words. A read-only token can list history and preview a revert, and is refused the rest. `revert_many` and `preview_reverts` take `author` in place of `revisions` for a note, which picks that author's changes to it as `revert_author` does, when the call is made. `revert_author` reverts every change one author made that still stands, across the workspace or in `noteIds`, as one new change in each note by whoever asks. It leaves alone what somebody else already reverted and what the author undid themselves, and has stand again what the author reverted of others'. It covers ten notes a call and reads only those notes: while the answer's `next` isn't null, call again with it as `after`. A note that refuses the change, such as one it would make too long, is left as it was and named in `failed`, and the notes after it are still covered. A note the revert leaves with no text, such as one the author created, is named in `emptied` with the title it had: it stays, since there is no deleting a note yet. `ink revert-author` makes those calls itself until every note is covered. `ink revert-author <author> --preview` writes nothing: it lists the notes the author changed (`history_summary`) and prints `preview_reverts` with `author` for them. `ink` refuses a flag a command doesn't take before it sends anything, so a misspelt or misplaced flag can't turn a look into a write. The web app does the same from an agent's entry on the Agents page and from History mode when it is filtered to one agent, after showing what it would change in each note (`preview_revert` with `author`). Where one of those notes has conflicts with later changes, they are settled as any revert's are: `preview_revert` with `author` lists them and takes `resolve`, and `revert_author` takes `resolve` as an object with a `{ at, choices }` for each note id. A note it leaves out keeps every later edit, and a note that has changed since its preview is left as it was and named in `failed`. A read-only token can list history and preview a revert, and is refused the rest.

A selection of changes across notes is read and reverted in one call each. `history_diff` takes `changes`, up to 40 notes each as `{ noteId, revisions }`, and answers note by note: a note's selected changes that follow one another are one run with one diff, from the note before the first to the note after the last, and a run after changes that were left out says how many it `skipped`. One answer holds about 2000 diff lines; a run past them has `diff: null` and its note asked for alone returns it. `preview_reverts` says what `revert_many` would do to each note and writes nothing. `revert_many` reverts each note as one new change and answers with `reverted` and `skipped`: a note is skipped, never half-reverted, when it is no longer at the revision passed as `at` (`changed`), when the revert would change nothing (`nothing`), or when it can't be made (`refused`, with the reason). Each note is asked for itself: one the agent can't see, by its person's access or its own folder limit, is `refused` as `No such note` with no title, word for word as an id that was never a note's, in the preview and in the revert, and one it may read and not change is previewed and then `refused` by the revert. `history_diff` answers `not_found` for all of a selection that names such a note. A selected change that was already reverted is left as it is and listed in the preview's `already`. To undo a revert, revert the revision it made with `at` set to that revision: the note is skipped if it has been edited since. `history_summary` and `history` also take `by`, `"people"` or `"agents"`. Each conflict a preview of chosen changes lists also says where it is on `history_diff`'s diffs of the same changes: `runs`, one for each run, with the run's last revision and the `line` and `lines` of the note at that revision.

    npm run ink -- diffs <id>:<n>,<n> <id>:<n>
    npm run ink -- revert-many <id>:<n>,<n> <id>:<n> --preview
    npm run ink -- revert-many <id>:<n>,<n>@<revision of the preview> <id>:<n>@<revision of the preview>

A link from one note to another is `[[<note id>]]` or `[[<note id>|display text]]` in the note's text (`docs/adr/0001-links-stored-by-id.md`). The text holds the id and never the title, so an agent gets the titles beside it: `read_note` answers with `links`, each linked note's id and its title now, or a null title for a note that doesn't exist or that the member can't see. An agent may write a link by title, `[[Title]]` or `[[Title|display text]]`, and `create_note` and `write_note` store it by the id of the one note with that title, ignoring case. When no note the member can see has the title, or several do, the link stays as written and the write is made: the answer lists it in `unresolved`, as `{ "target": "Budget", "matches": [] }`, with the ids of the notes that have the title in `matches` when several do. A link to a note the agent can't see is named the same as one to no note. `linkTitles: "resolve-strict"` refuses the whole write for such a link instead, with nothing written and the ids to choose from in the message, as every write did before. Only links the write introduces are looked up: one whose target, as written, was already in the text at `baseRevision` is left exactly as it is, so an agent is never refused, or told of, a link someone else wrote. A new target that reads as an id, twelve lowercase letters and digits, is taken for the note with that id, or failing that the one note with that title. `linkTitles: "keep"` stores every link as written, for a note that means `[[` literally. Text in code, fenced or inline, is never read as a link. `backlinks` lists the notes whose text links to a note. `rebuild_links` makes the record behind it again from the notes' text, for every note in the workspace; every write keeps that record, so it is only for one changed some other way, and it needs the admin role.

No two folders in one place have names that differ only in case, in any script: `Écoles` and `écoles` can't both be in Projects, and `Ecoles` can. `create_folder` answers a name that is there already with that folder and `"created": false` (`ifExists: "return"`, the default for an agent), or refuses it with `ifExists: "error"`, as the web app does; a folder it makes has `"created": true`. Two calls at once make one folder. `list_folders` gives each folder's `path`, its name after those of the folders it is in, as far up as the agent can see: `Projects/Skills`, or `Skills` for an agent limited to that folder. `find_folder` takes a path and answers with that folder, matching names as written, then ignoring case, then ignoring accents too, so `projects/cafe` finds `Projects/Café` unless there is a `Projects/cafe`. Two folders that match at once are named and not chosen between, and a path that matches nothing is `not_found: No such folder`, as a folder the agent can't see is.

A mention of a person is `@[[<person id>|<name>]]` for a member of the workspace and `@[[<name>]]` for anyone else, such as one of the member's contacts (`docs/adr/0007-mentions-are-ids-for-members-and-names-for-everyone-else.md`). `read_note` answers with `mentions`: each person once, with `member` true and their name now for a member, and otherwise the name as written. An agent may write `@[[Name]]` or `@[[id]]` for a member, and `create_note` and `write_note` store it as `@[[id|Name]]`; `list_members` gives the ids. A name several members have is refused with the ids to choose from. A token limited to folders is not told who is a member, by a mention any more than by `list_members`: what it writes is kept as written, a name is never refused, and `mentions` and `assignees` answer every person with `member` false and the name as the note writes it. A name no member has is kept as written, a mention of someone by name. `mentionNames: "keep"` stores every mention as written. A mention gives nobody access, tells nobody, and makes no offer to share: that is the member's, in the app. Every reader of the note sees the name, so an agent writes only the name of a contact, never their email or anything else `list_contacts` told it. A mention on a todo's line assigns the todo: `list_todos` answers each todo's `assignees` and narrows by `assignee:` in its query (a member's id or a name, and `@me`), as by the `assignee` and `assignedToMe` fields, `todo_filters` lists the assignees there are, and `set_todo` takes `assign` and `unassign`. `search` finds the notes that mention someone with `mentions:` the same way. `read_person` takes `who`, a member's id or a name, and answers that person's page as the agent may be told it: `member` only where `list_members` would answer, the member's own contacts that are them with all they hold (never another member's, and none for a token limited to folders, which is not asked of a data source at all), the open todos assigned to them, `mentionedIn` with each line that mentions them in the notes the agent can see, newest note first, and `query`, the `mentions:` query `search` takes to find those notes.

A todo is a checkbox line in a note, with its options as tokens on the line: `- [ ] !! Call the bank due:2026-10-14` (`docs/todos.md`). An agent makes one by writing that line with `create_note` or `write_note`. `list_todos` lists the todos in the notes the member can see, open ones unless `includeCompleted`, narrowed by `folderId` (the folder and every folder under it), `tag` (a tag of the todo's note, on its own line or anywhere else in the note), `importance` (the priority levels: 0 None, 1 Low, 2 Medium, 3 High), and a range of due days, and ordered by `sort`: `due` (the default), `priority`, `changed` (the todos whose note changed last first), `note` (by its title) or `text` (by the words, A to Z), the done ones always last. Due dates are calendar dates and the server never works out today, so an agent passes the days it means: overdue is `dueTo` yesterday. `set_todo` checks one off or changes its priority (`importance`), its due date or its `words` (everything but the checkbox, priority and due date, tags included, on one line; its due date is then written after them), by rewriting its line as a change under the agent's name. It takes `id`, `revision`, `line` and `text` as `list_todos` gave them, follows that line through every change made to the note since, and is refused as a conflict when the line itself was changed or deleted. A todo that reads the same is never taken for it, and the same call made twice changes nothing more. `rebuild_todos` and `rebuild_links` are one operation, for an admin: it makes the index behind `list_todos` and the record behind `backlinks` again for every note in the workspace, and answers only `done`. Notes written before there was an index need no rebuild: they are indexed the first time todos are listed. Asked by an agent limited to folders, it is for the notes in those folders.

A todo with `every:` repeats: `every:2w`, `every:mon,thu`, `every:3d-after-done`, `every:last-fri`, `every:1st-day,15th-day`, `every:mar-1`, and any of them with an end, `every:1m-times-5` or `every:mon,thu-until-2026-12-31` (`docs/todos.md` has every rule, and the descriptions of `list_todos` and `set_todo` carry the grammar as a short table, so a model can write one unaided). `list_todos` gives each todo's rule as written (`every`) and in words (`recurs`). `set_todo` takes `every` to set or clear it, and `skip: true` to move a repeating todo to its next due date with nothing checked off or filed. Checking a repeating todo off, by `set_todo` or by a `write_note` that checks its box, leaves it open with its next due date and files the checked line on the daily note of the agent's member, and the answer's `filed` says the day and the note. A rule that ends counts down with each completion and each skip, and its last time checks the todo off for good. Both take `on`, the day it is for the member; left out, it is today in the zone the member's `daily.timeZone` setting names, or in UTC. `todo_history` lists each time a repeating todo was checked off and by whom. `daily_note` finds or makes the member's daily note for a day.

A member's dashboard keeps two things of theirs, outside any note (`docs/adr/0009-the-dashboard-is-a-view-and-keeps-two-things.md`). Pins: `list_pins` lists the notes the member pinned that they can see now and that are live, and the archived ones with `includeArchived`; it changes nothing, so a pin on a note the member can't see now is back when the note is, and `pin_note` pins one or takes its pin away for the member, which needs only that the member can see the note, changes nothing in it, and is refused to a read-only token. The last visit: `last_visit` answers `readUntil`, the time up to which the member marked the changes on their dashboard read, or null, and `now`. What they haven't read is `history` with `from` set to `readUntil` and `notAuthors` naming the member, which is how the dashboard makes its summary. Only the member marks changes read (`visit.mark` is kept from agents): an agent that did would hide from them what they haven't looked at. `find_daily_note` answers the member's daily note for a day when there is one and makes nothing, where `daily_note` makes it.

A note is live, archived, or in Trash, and every listing of it says which as `state` (`docs/adr/0005-a-note-has-a-state-beside-its-access.md`). `archive_note` archives and unarchives. An archived note is left out of `list_notes`, `list_todos`, `todo_filters`, `list_tags` and `search` unless `includeArchived` is true, and is read and written as any note. `list_notes` and `search` also take `includeArchived: "only"`, for the archived notes alone. `trash_note` moves a note to Trash, where `list_trash` lists it with `purgesAt`, the time it is removed for good, 30 days on. Until then `read_note` reads it, every change to it is refused as a conflict, and `restore_note` brings it back as it was. `revert_author` with `trashEmptied` moves the notes it left empty to Trash. `list_notes` with `updatedSince` also reports a note whose state changed since, and each note has `stateAt`. A removed note reads as no such note, and a link to it has a null title, exactly as for a note that never existed.

`search` and `list_todos` take a query, in the language of `docs/search.md`: words and `"a phrase"`, filters such as `folder:"Common Ink"`, `#tag`, `editor:@me`, `updated:>=7d`, `is:archived`, `has:backlink`, `due:<today` and `importance:>=2`, with `-`, `NOT`, `OR` and parentheses. Each tool's description carries every form, so a query can be written from the description alone, and `ink syntax` prints them. A query that can't be read is refused as `invalid`, saying which characters and why, and so is a `folder:` or an `editor:` that names nothing the agent can see, in the words a name nobody has is refused in. `today` is the day it is for the agent, which `today`, `yesterday`, `tomorrow`, `7d` and `+7d` are counted from: a query with one of them and no `today` is refused, since the server never works out a day. `zone` is where a day begins for `updated:` and `created:`. The arguments from before the query could say them still narrow it: on `search`, `folderId` (the folder's own notes, not the folders inside it; a folder the agent can't see is no such folder), `hasTodos`, `includeArchived` and `sort`, which the query's own `sort:` wins over. Each result has the note and the first lines that matched, with `marks` saying where in each line. `list_tags` lists the tags of the notes the agent can see with how many notes have each, and `list_notes` with `tag` lists the notes under one.

An upload is a file in a workspace, kept in a folder as a note is, with a `state` and `access` as a note has. `list_uploads` lists the ones the agent can see that its `query` finds, in the query language of `search` (docs/search.md): `type:image uploader:@me`, `size:>1mb used:no`, `name:report uploaded:>=7d`. With no query it lists every live one, latest uploaded first. A query that can't be read is refused with the characters it is about, and its description carries the language's table, as `search`'s does. `folderId` and `includeArchived` still narrow it. Each has its `id`, `name`, `type` (what its bytes are served as), `kind` (`image`, `video`, `audio` or `file`), `size` in bytes, `width` and `height` for an image whose bytes say them, `uploadedBy`, `private`, and `uses`: how many notes the agent can see show it. `read_upload` answers one upload with `usedIn`, the notes the agent can see that refer to it. A note refers to an upload with an embed on a line of its own that starts with the upload's id: `::image{<id> WIDTHxHEIGHT}`, `::video{<id> WIDTHxHEIGHT}`, `::audio{<id>}`, or `::file{<id>}` for anything else. The size is the room the app keeps for it, and the upload's name is never in the note. `read_note` answers with `uploads`, each upload the text refers to, with a null `upload` for one that doesn't exist or that the member can't see. `place_upload` is asked before an existing upload's embed is written into a note with `write_note`, and writes nothing in the note itself: an upload private to the member, seen by nobody else, is refused, since only the member can let others see it, in the app (as for `upload.setPrivate`); in a private note it stays private and is placed, and any other upload is left where it is. It needs edit on the upload and on the note. `move_upload` puts one in another folder and `archive_upload` archives or unarchives it; neither changes what notes show. `trash_upload` moves one to Trash for 30 days, where `list_trashed_uploads` lists it with `purgesAt`, and the notes that refer to it say it is in Trash until `restore_upload` brings it back. Each of these needs edit on the upload.

Four operations on uploads are kept from agents, and the core refuses them whatever the tools do. How much a workspace's uploads take (`upload.storage`) counts every member's files, private ones and those in folders a token may be kept from; the members see it in Settings. Removing an upload from Trash for good (`upload.purge`) removes its bytes past recovery, as removing a note for good does its history. Making an upload private (`upload.setPrivate`) hides it from every other member and is not a change in history, as with a private note; an agent can't upload a file as private either. Reading an upload through a shared link (`shared.upload`) is for whoever holds the link, in a browser, with no token. Sharing an upload is kept from agents with all other sharing.

A member's calendar and contacts are data sources (`docs/adr/0006-data-sources-are-one-persons.md`). `list_sources` says which the member has and each one's `state` (`connected`, `needs_reconnect`, `not_connected`) and `writable`, and `reconnectToWrite` on one that is read-only only because the member agreed to read it and not to change it (Google's contacts, until the member connects them again to edit). `list_events` takes a span as two times and the `timeZone` whose days all-day events are matched by; an event's `when` is `{ allDay: false, from, to }` in milliseconds or `{ allDay: true, from, to }` with its first and last day, and its `calendarId` is the calendar it is in. `list_events` also answers `calendars`: every calendar in each connected calendar data source, with or without events in the span, each with its `sourceId`, `id`, `name`, `color` and `writable`. `update_event` takes the event's `sourceId`, `id` and `etag` as read and only the fields to change, and is refused with `conflict` when the event changed since, and with `forbidden` for an event whose `editable` is false. `create_event` takes a calendar's `sourceId` and `id` from `calendars`, a `title` and a `when`, and optionally a `location` and a `description`, and answers the event as it was made. It is refused with `forbidden` for a calendar whose `writable` is false and with `not_found` for one the member doesn't have. `list_contacts` lists contacts, narrowed by `query`. Each of a contact's emails, phones, addresses and websites, there, in `read_person` and in `read_record`, is `{ value, type }`, where `type` is its label: one of Google's own as People names them (`CONTACT_LABELS` in `src/core/protocol.ts`: an email's `home`, `work`, `other`; a phone's `mobile`, `home`, `work`, `main`, `homeFax`, `workFax`, `pager`, `other`; an address's `home`, `work`, `other`; a website's `homePage`, `work`, `blog`, `profile`, `other`), one the member wrote, as written, or `null` for none. A type Google has and Common Ink has no words for, such as `workMobile`, is read as Google shows it (`Work Mobile`) and written back as Google's own. A note references a record with an embed that holds no copy of it: `refer_record` answers the `::event{<ref> <label>}` or `::contact{<ref> <label>}` to write, and `read_record` reads what a `ref` stands for now. The label is plain text in the note, which every reader sees. The ref leads to the record only for the member who made it. `notes_about_record` takes a record's `sourceId` and `id` and answers the notes that hold the member's own reference to it, and for an event the member's calendar has now, another member's reference to the same event (a shared calendar's event has one id for everyone who has it), among those the member can see and not in Trash, each with its `id`, `title`, `updatedAt` and `audience`: `private`, `shared` or `workspace`.

Most clients take a URL and a header:

    claude mcp add --transport http common-ink https://commonink.app/mcp --header "Authorization: Bearer $INK_TOKEN"

## Connecting by OAuth

A hosted chat app (claude.ai, ChatGPT) can't send a pasted token, so it connects by OAuth 2.1 instead. Common Ink is both the authorization server and the resource. The app needs only the address `https://commonink.app/mcp`: the rest it finds. The decisions are in `docs/adr/0012-oauth-connections-are-agents.md`.

A connection by OAuth is an agent. Consent makes one with the limits the member picks, through the same checks as the Agents page, and everything in Rules holds for it. The Agents page lists it under the app's name, marked OAuth, and Disconnect ends every token it holds at once. It has no token to set up again.

    GET  /.well-known/oauth-protected-resource       where /mcp says to sign in (RFC 9728), also at .../mcp
    GET  /.well-known/oauth-authorization-server     the endpoints below (RFC 8414)
    POST /oauth/register                             an app registers itself (RFC 7591)
    GET  /oauth/authorize                            the member's browser, on to the consent page at /connect
    POST /oauth/token                                a code or a refresh token for tokens
    POST /oauth/revoke                               ends the connection (RFC 7009)

The steps, as an app takes them:

1. `POST /mcp` with no token answers 401 with `WWW-Authenticate: Bearer realm="Common Ink", resource_metadata="<origin>/.well-known/oauth-protected-resource"`. A token that was sent and is no good adds `error="invalid_token"`, which is how an app knows to refresh.
2. The app registers: `{"client_name": "...", "redirect_uris": ["https://..."]}` answers 201 with a `client_id`. Every app is a public client with no secret (`token_endpoint_auth_method: "none"`), whatever it asks for. A redirect address is https, or http to `localhost`, `127.0.0.1` or `[::1]`, with no fragment.
3. The app sends the member's browser to `/oauth/authorize` with `response_type=code`, its `client_id`, a registered `redirect_uri`, `state`, a PKCE `code_challenge` with `code_challenge_method=S256`, and optionally `resource=<origin>/mcp`. The member signs in if need be and lands on the consent page. It shows the app's name as the app gave it, the host they will be sent back to in punycode, and what to allow: which workspace, which folders, how long, and read only. An error in the request is said on a page and never sent to the app's address, since anyone can register one.
4. Allow sends the browser to the app's address with `code`, `state` and `iss`. Don't allow sends it there with `error=access_denied`.
5. The app trades the code within a minute at `/oauth/token` (`grant_type=authorization_code`, `code`, `client_id`, `redirect_uri`, `code_verifier`). The answer has an access token (`cink_at_...`) for an hour and a refresh token (`cink_rt_...`) for 30 days. Neither lasts past the agent's own expiry.
6. The app calls `/mcp` with `Authorization: Bearer cink_at_...`, as with a pasted token.
7. Before the hour is up it refreshes (`grant_type=refresh_token`, `refresh_token`, `client_id`). Each refresh token works once and is replaced.

What ends a connection:

- **Disconnecting it**, on the Agents page, by its member signing out everywhere, or by the app at `/oauth/revoke` with either token.
- **A code presented twice.** The second try is refused, and what the first was given ends, since the code may have been stolen.
- **A refresh token used again** more than 30 seconds after it was spent. Used again within 30 seconds it is only refused, as a retry after a lost answer.
- **Holding nothing that works**: a code that lapsed untraded, or every token run out. A sweep disconnects it, so it stops counting toward the 20 agents.
- **Connecting the same app again**, which replaces the earlier connection.

Limits, since anyone can register an app and start a sign-in:

- 20 registrations an hour from one address. An IPv6 address counts as its /64. Addresses are counted by a salted hash, logged nowhere.
- 1,000 apps waiting for a grant in all. An app that never sends anyone to sign in is forgotten after an hour, and one that never gets a grant after a day.
- 2,000 sign-ins waiting in all, 20 for one app and 10 from one address. Each lapses after ten minutes.
- Bodies past 16 KB are refused.

The discovery documents and `/oauth/{register,token,revoke}` allow any origin, with no credentials. Nothing there reads a cookie. `/mcp`, `/oauth/authorize` and the consent API (`/api/oauth/{request,consent,deny}`) allow none.

## Uploads over HTTP

A file's bytes never travel in a tool call, but for a small one an agent already holds, which `upload_file` takes as base64 (4 MB at most). An agent sends a file of any size, up to 25 GB, in parts (below), and sends and fetches one in a single request at two addresses, with the same token as `/mcp` in the same `Authorization: Bearer` header. The core decides each request as it decides a tool call: the member's role and grants, a read-only token, and a token pinned to one workspace all hold here.

    POST /api/workspaces/<workspace id>/uploads
         Authorization: Bearer cink_...
         Content-Type: application/octet-stream
         Content-Length: <how many bytes>
         X-Ink-Upload: <encodeURIComponent of the JSON {"name": "cat.png", "folderId": "<folder id>"}>
         <the bytes>
      ->  201 with the upload, as list_uploads gives it

    GET  /api/workspaces/<workspace id>/uploads/<upload id>
         Authorization: Bearer cink_...
      ->  200 with the bytes

`name` is required. `folderId` is optional, and the file goes to Unsorted without it. Uploading needs edit on the folder, so a viewer's agent and a read-only token are refused with 403. A workspace the token can't reach, and an upload the member can't see, answer 404. No token, or one Common Ink doesn't know, answers 401. `Content-Length` is required (411 without it) and the body must be exactly that long. Any type but `application/octet-stream` is refused with 415.

One request carries at most 80 MB, a little under the 100 MB a request to the Worker can be: a longer `Content-Length` is refused with 413 before any of the body is read. A larger file, up to 25 GB, goes in parts. There is no limit to a workspace's uploads together; Settings shows the members how much they take.

### A file in parts

    start_upload {name, size, folderId?}
      ->  {id, partSize, partCount, stored: [], address: "https://commonink.app/api/upload-parts/<secret>/{part}", expiresAt}

    PUT <address with {part} replaced by 1, 2, ... partCount>
        Content-Type: application/octet-stream
        <the part's bytes: partSize of them from (n - 1) * partSize, the last part what is left>
      ->  200 {id, number, stored}

    finish_upload {uploadId}
      ->  the upload, as list_uploads gives it, and line, the embed to write in a note

A part is 80 MiB, so a 25 GB file is 320 parts, sent several at once and in any order. The address needs no token: it is a 256-bit secret, kept only as its hash, that names one upload and lapses an hour after it is given, and it takes each part once, whether or not that part arrived whole. A part of the wrong length is refused (400) and stored as nothing; an address that lapsed or never was answers 410, a part sent to it again 409. `resume_upload {id}` answers the parts that are stored and a fresh address for the rest, so a dropped connection or a laptop closed half way loses nothing sent. `finish_upload` puts the parts together, checks that the file is the size `start_upload` was told, reads its type from its first bytes as for any upload, and makes it live; asked again it answers the same. `abort_upload {id}` throws the parts away.

Until it is finished the upload is no upload to anyone: in no listing, no note shows it, and its address answers 404. Only whoever started it can resume, finish or abort it, and each step and each part asks again whether they may still put it in its folder, so an agent disconnected, a token limited to other folders since, or a member made a viewer stops at the next part. One nothing is sent to for a day is thrown away with its parts by the hourly run (`clearUploads`), and the bucket's own rule aborts any it doesn't know of after a few days.

With a shell, `dd` cuts a part out of a file and `curl` sends it, from the agent's own machine:

    dd if=episode.mp3 bs=1048576 skip=$(( (n-1)*80 )) count=80 status=none | curl -sS --fail-with-body -X PUT -H 'Content-Type: application/octet-stream' --data-binary @- "<address with {part} replaced by n>"

What a file is served as is decided by the server from the ending of its name and its first bytes together, and never from a type the client declares. It is a picture, a video or a sound only when both agree: `.png`, `.jpg`, `.gif`, `.webp`, `.avif`, `.svg`, `.mp4`, `.m4v`, `.mov`, `.webm`, `.mp3`, `.m4a`, `.wav`, `.ogg` (`src/core/filetypes.ts`). Anything else, such as a PDF, an HTML page, or a file named `.png` whose bytes are not a PNG, is kept as it came and served as `application/octet-stream` with `Content-Disposition: attachment`, a download that no browser will show as a page. An SVG is served as `image/svg+xml` and also as a download, since opened as a page it could run script.

The GET honours `Range` (206 with `Content-Range`) and `If-None-Match` with the `ETag` of an earlier answer (304 with no body), and `HEAD` answers the headers alone. Every answer with an upload's bytes carries `X-Content-Type-Options: nosniff`, a `Content-Security-Policy` that sandboxes it, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer` and `Cache-Control: private, no-cache`. There is no other address for a file, and none that outlasts the request: access that was taken away stops the next one.

`ink upload` sends a file of any size in parts, four at once, read from disk a part at a time; a part that doesn't get through is sent again to a fresh address, and it gives up only after rounds that store nothing, saying how to go on (`ink upload-resume`). It prints the upload and the line a note shows it with. `ink download` is the GET. `download` saves under the upload's name in the current directory, using only the last part of the name, or at `--out`, and never replaces a file that is there unless `--force true`.
