# Connecting an agent

A member connects an agent in the web app, on the Agents page (`/agents`, from the workspace menu or the "Go to Agents" command), and gets a token for it. The page shows the token once, inside a prompt to paste into the agent: what Common Ink is, what the agent may reach, the server's URL and the token, how to add the connection to its own client (the config's shape, and `claude mcp add` for Claude Code), how to check it works by listing its workspaces and folders, and to keep the token secret (`src/web/plugins/agents/prompt.ts`). The commands and config to set it up by hand are under "Set it up by hand". An agent's "Set up again" shows the prompt later with no token in it, since the token can't be shown again. The page also lists the member's agents, edits what each may do, and disconnects them. The agent sends the token to `/mcp` (the MCP server) or uses the `ink` command, which calls `/mcp`. Both go through the same operations as the web app (`src/core/operations.ts`), as the member who connected the agent.

## Rules

- An agent acts with its person's access in each workspace, and no further: their role where they are a member, narrowed by any grant that names them, and where they are a guest only what was granted. A viewer's agent can read and cannot write. A note its person can't see, such as another member's private note, is no note to the agent: it is in no listing, count, backlink, link title or history, and asking for it by id answers `not_found: No such note`, the same as for an id that was never a note's. Every listing of a note carries `access`, `edit` or `view`: what the agent may do with it.
- An agent can't share. Granting a note or a folder to someone, making or removing a link, making a note private, and reading who a note is shared with are for the member, signed in, in the Share dialog. A link can put a note before the whole internet, and none of this is a change in history that could be reverted.
- Its changes are recorded with the agent as author (`author_kind = 'agent'`, `author_id` = the agent's id), under the name the member gave it, so they can be told apart from the member's own.
- A member who loses access to a workspace takes their agents' access with them: every call checks the member's membership at the time. Removing a member, or their leaving, ends it on the agent's next call, and a change of role changes what the agent can do on its next call.
- An agent can see who is in a workspace (`list_members`: each member's person id, name, and role, and never an email, whatever its member's role) and can't change it. Inviting, changing a role, removing a member, leaving, and listing or revoking invites are for the member, signed in, on the Members page. Who is in a workspace decides who can read and change everything in it, that isn't a change in history that could be reverted, and an agent reads notes other people wrote, so one that was talked into it could invite a stranger as admin. The core refuses these to an agent whatever its member's role, not only the tools.
- A token expires after 90 days by default (`expiresInDays`, 1 to 365, or `"never"` for a token that doesn't expire). An expired token is refused like an unknown one.
- A token can be pinned to one workspace (`workspaceId`: it sees only that workspace, even if its member is in others) and can be read-only (`readOnly`: it can read and can't change anything, even for an editor or admin). Both are checked in the core operations, not only in the tools.
- A token pinned to one workspace can be limited to folders there (`folderIds`): the agent reaches those folders, the folders inside them, and the notes in those, with what its member may do with each and no more. Everything else is to it as a note its person can't see: in no listing, count, backlink, link title, history or author list, and `not_found` by id in the words used for an id that was never there. A link in a note it can read to a note outside reads as a link to no note (`title: null`); the link's target id is part of the text it can read. Checking off a recurring todo in its folders completes it and files nothing on a daily note outside them, and it is given no daily note (`daily_note` is refused). It makes notes and folders only inside its folders: `create_note` needs a `folderId` unless Unsorted is one of them, a note can't be moved in or out, and the folders it is limited to can't be renamed by it, since a name refused as taken would name a folder beside them. The limit follows the folders as they are: a note or folder moved in is reached and one moved out isn't. A folder deleted since stays in the list and stands for nothing, so an agent whose folders are all gone reaches nothing, never everything. It isn't told who is in the workspace (`list_members` is refused), since some of them have only written outside its folders. An admin's limited agent deletes a folder of its own that is empty to it as the admin would, and a note there that the admin can't see goes to Unsorted. `list_workspaces` answers the agent's own `folderIds`, null when it has no limit. Checked in the core where access is resolved (`resolve` and `SEEN` in `src/core/access.ts`), not in each tool.
- Names aren't unique: a member can have several tokens named "Claude", told apart on the Agents page by the first characters of each token. Each token is its own author in history. An agent has a name and nothing else to call it by.
- What an agent may do can be changed after it is connected, by the member who connected it and nobody else: whether it is read-only, when it expires, which workspace it reaches, and which folders it is limited to there. The token stays the same, and the agent's next call is held to the edit. A disconnected agent can't be edited; an expired one can be given a new expiry.
- Disconnecting an agent stops its token at once. Only a SHA-256 hash of a token is stored; the token is shown once, when the agent is connected.
- A token works only in an `Authorization: Bearer` header. It is not a cookie, so a web page can't use it.

- An agent can archive a note, move it to Trash and restore it, with edit on the note, since each can be taken back. It can't remove a note from Trash for good: that takes the note's history with it and nothing brings it back, so it is for the member, signed in, on the Trash page.

- An agent reads its member's data sources and no other member's: `list_events`, `list_contacts` and `read_record` answer for the member who connected the agent, whatever their role, and there is no argument that names anyone else. `update_event` changes the member's real calendar, as the member, and a read-only token is refused it and `refer_record`. A change to an event is not in Common Ink's history and can't be reverted from here. An agent can't connect or disconnect a data source: agreeing is the member's, in their browser. A token limited to folders is refused all six tools: the calendar and the contacts are in no folder, so they are outside any limit. It still reads `::event{…}` and `::contact{…}` in its notes as every reader does, as a reference and a label. What an agent reads from a data source is the member's private data, and an agent that writes it into a shared note has shared it (`docs/adr/0006-data-sources-are-one-persons.md`).

## Connect, edit and disconnect (signed in, from Common Ink's own origin)

    POST   /api/agents        {"name": "Claude"}   ->  201 {"agent": {...}, "token": "cink_..."}
    GET    /api/agents                             ->  {"agents": [...]}   (never the token; shows expiresAt, workspaceId, readOnly, folderIds)
    PATCH  /api/agents/<id>   {"readOnly": true}   ->  {"agent": {...}}
    DELETE /api/agents/<id>                        ->  204

Optional fields on the POST: `expiresInDays` (default 90, at most 365, or `"never"`), `workspaceId` (one of the member's workspaces), `readOnly` (true or false), `folderIds` (1 to 50 folders of `workspaceId` that the member can see; left out, the agent reaches all notes). For example, a read-only token for two folders of one workspace that lasts 30 days:

    {"name": "Claude", "expiresInDays": 30, "workspaceId": "<workspace id>", "readOnly": true, "folderIds": ["<folder id>", "<folder id>"]}

The PATCH takes the same four fields, each optional, and changes only the ones it is given: `expiresInDays` counts from the edit, a null `workspaceId` lets the token reach every workspace again, and a null `folderIds` lets it reach all notes again. Folders go with one workspace: `folderIds` without a `workspaceId`, on the POST or on a token that reaches every workspace, is refused, a folder that isn't in that workspace or that the member can't see is `404 No such folder`, and a limited token is moved to another workspace only by an edit that also names its folders there, or null. Any other field is refused. These calls need a member's session, which an agent's token is not, so an agent can't connect, edit or disconnect an agent, its own included. They aren't workspace operations, so they have no tool and no entry in `NOT_FOR_AGENTS`: an agent belongs to a person, across their workspaces.

## MCP

`POST /mcp` with `Authorization: Bearer cink_...` and `Content-Type: application/json`. Streamable HTTP, stateless: one JSON-RPC message (or a batch) per POST, answered as JSON. No server-sent events, no sessions. Without a valid token the answer is 401.

Tools: `list_workspaces`, `list_notes`, `read_note`, `create_note`, `write_note`, `backlinks`, `rebuild_links`, `list_todos`, `todo_filters`, `set_todo`, `todo_history`, `daily_note`, `rebuild_todos`, `move_note`, `note_history`, `search`, `list_tags`, for a note's state `archive_note`, `trash_note`, `restore_note`, `list_trash`, for the member's data sources `list_sources`, `list_events`, `update_event`, `list_contacts`, `refer_record`, `read_record`, for folders `list_folders`, `create_folder`, `rename_folder`, `delete_folder`, and for history `history_summary`, `history`, `change_diff`, `history_authors`, `history_diff`, `preview_reverts`, `revert_many`, `label_revision`, `revert_note`, `revert_changes`, `preview_revert`, `revert_author`, `undo`, `redo`, and `list_members` for who is in the workspace. Each takes an optional `workspace` id, which can be left out when the member belongs to only one workspace. An argument a tool doesn't take is refused by name, not left out.

Every operation the web app performs has a tool with the same fields, and every tool has an `ink` command. `test/core/agent-parity.test.ts` reads the operation schema and fails when one is missing; an operation kept from agents on purpose is listed with its reason in `NOT_FOR_AGENTS` (`src/worker/mcp/tools.ts`). Two kinds are kept from agents: reading and writing the member's settings, which shape the member's own app and are checked against a schema only the app has, and every change to a workspace's members and invites (see Rules). The core refuses them to an agent, not only the tools. Connecting and disconnecting agents is not an operation: it needs a member's session, so an agent can't make another token.

History only goes forward. A revert, an undo, or a redo is a new change under the agent's name that names the changes it reverted (`reverts`), and each change it reverted names it (`revertedBy`). There is no putting a change back: to have a reverted change again, revert the change that reverted it, which `revert_changes` does like any other, however many reverts deep. `revert_changes` refuses a change that is already reverted and names the change to revert instead. Read history from the top down: `history_summary` lists the notes that changed, latest first, each with its count of changes and the lines they added and removed; `history` lists changes, each with the lines it added and removed (`added`, `removed`) and, unless `diffs` is false, its diff; `change_diff` reads one change's diff. All three take the same `noteIds`, `authors` and time range, and a summary counts only the changes that match. `history` filters by `authors`, so an agent's changes can be listed on their own and passed to `revert_changes`. `preview_revert` says what a revert would do and writes nothing: pass `revisions` for what `revert_changes` would do, `to` for what `revert_note` to that revision would do, or `author` for what `revert_author` would do to that one note, and it answers with the note's `revision` it was worked out at, the `revisions` that would be reverted, the `diff` from the note as it is to the note after, `overlaps`, the later changes that still stand and edited the same lines, and `conflicts`, each place they did, top of the note first: the lines as they were before the reverted changes (`before`), as they are now (`now`), as the revert leaves them with the later edits kept (`kept`, starting at `line` of the result), and the later changes that edited them with their authors (`later`). What a later change did to other lines is no conflict and always stays. A revert settles each conflict with a choice, passed as `resolve: { at, choices }` to `revert_changes` or `revert_note`: `"keep"` keeps the later edits on a line the revert otherwise returns to how it was (what a revert does when `resolve` is left out), `"back"` returns the lines to `before` and drops the later edits to them, and `{ "text": "..." }` puts the lines given there (an empty string for none). `choices` is one of the first two for every conflict, or a list with a choice for each in the order the preview lists them; `at` is the `revision` the preview answered with, and the revert is refused when the note has changed since, so preview again. Pass the same `resolve` to `preview_revert` to read the diff of the revert settled that way. The revert is one change whichever way its conflicts are settled, and reverting it takes what was chosen out with it. It refuses what the revert itself would refuse, in the same words. A read-only token can list history and preview a revert, and is refused the rest. `revert_many` and `preview_reverts` take `author` in place of `revisions` for a note, which picks that author's changes to it as `revert_author` does, when the call is made. `revert_author` reverts every change one author made that still stands, across the workspace or in `noteIds`, as one new change in each note by whoever asks. It leaves alone what somebody else already reverted and what the author undid themselves, and has stand again what the author reverted of others'. It covers ten notes a call and reads only those notes: while the answer's `next` isn't null, call again with it as `after`. A note that refuses the change, such as one it would make too long, is left as it was and named in `failed`, and the notes after it are still covered. A note the revert leaves with no text, such as one the author created, is named in `emptied` with the title it had: it stays, since there is no deleting a note yet. `ink revert-author` makes those calls itself until every note is covered. The web app does the same from an agent's entry on the Agents page and from History mode when it is filtered to one agent, after showing what it would change in each note (`preview_revert` with `author`). Where one of those notes has conflicts with later changes, they are settled as any revert's are: `preview_revert` with `author` lists them and takes `resolve`, and `revert_author` takes `resolve` as an object with a `{ at, choices }` for each note id. A note it leaves out keeps every later edit, and a note that has changed since its preview is left as it was and named in `failed`. A read-only token can list history and preview a revert, and is refused the rest.

A selection of changes across notes is read and reverted in one call each. `history_diff` takes `changes`, up to 40 notes each as `{ noteId, revisions }`, and answers note by note: a note's selected changes that follow one another are one run with one diff, from the note before the first to the note after the last, and a run after changes that were left out says how many it `skipped`. One answer holds about 2000 diff lines; a run past them has `diff: null` and its note asked for alone returns it. `preview_reverts` says what `revert_many` would do to each note and writes nothing. `revert_many` reverts each note as one new change and answers with `reverted` and `skipped`: a note is skipped, never half-reverted, when it is no longer at the revision passed as `at` (`changed`), when the revert would change nothing (`nothing`), or when it can't be made (`refused`, with the reason). Each note is asked for itself: one the agent can't see, by its person's access or its own folder limit, is `refused` as `No such note` with no title, word for word as an id that was never a note's, in the preview and in the revert, and one it may read and not change is previewed and then `refused` by the revert. `history_diff` answers `not_found` for all of a selection that names such a note. A selected change that was already reverted is left as it is and listed in the preview's `already`. To undo a revert, revert the revision it made with `at` set to that revision: the note is skipped if it has been edited since. `history_summary` and `history` also take `by`, `"people"` or `"agents"`.

    npm run ink -- diffs <id>:<n>,<n> <id>:<n>
    npm run ink -- revert-many <id>:<n>,<n> <id>:<n> --preview
    npm run ink -- revert-many <id>:<n>,<n>@<revision of the preview> <id>:<n>@<revision of the preview>

A link from one note to another is `[[<note id>]]` or `[[<note id>|display text]]` in the note's text (`docs/adr/0001-links-stored-by-id.md`). The text holds the id and never the title, so an agent gets the titles beside it: `read_note` answers with `links`, each linked note's id and its title now, or a null title for a note that doesn't exist or that the member can't see. An agent may write a link by title, `[[Title]]` or `[[Title|display text]]`, and `create_note` and `write_note` store it by the id of the one note with that title, ignoring case. When no note the member can see has the title, or several do, the write is refused and nothing is written; the message lists the ids to choose from. Only links the write introduces are looked up: one whose target, as written, was already in the text at `baseRevision` is left exactly as it is, so an agent is never refused for a link someone else wrote. A new target that reads as an id, twelve lowercase letters and digits, is taken for the note with that id, or failing that the one note with that title, and refused when it is neither. `linkTitles: "keep"` stores such text as written, for a note that means `[[` literally. Text in code, fenced or inline, is never read as a link. `backlinks` lists the notes whose text links to a note. `rebuild_links` makes the record behind it again from the notes' text, for every note in the workspace; every write keeps that record, so it is only for one changed some other way, and it needs the admin role.

A todo is a checkbox line in a note, with its options as tokens on the line: `- [ ] !! Call the bank due:2026-10-14 +Home` (`docs/todos.md`). An agent makes one by writing that line with `create_note` or `write_note`. `list_todos` lists the todos in the notes the member can see, open ones unless `includeCompleted`, narrowed by `project`, `tag`, `importance`, and a range of due days. Due dates are calendar dates and the server never works out today, so an agent passes the days it means: overdue is `dueTo` yesterday. `set_todo` checks one off or changes its importance, due date or project, by rewriting its line as a change under the agent's name. It takes `id`, `revision`, `line` and `text` as `list_todos` gave them, follows that line through every change made to the note since, and is refused as a conflict when the line itself was changed or deleted. A todo that reads the same is never taken for it, and the same call made twice changes nothing more. `rebuild_todos` and `rebuild_links` are one operation, for an admin: it makes the index behind `list_todos` and the record behind `backlinks` again for every note in the workspace, and answers only `done`. Asked by an agent limited to folders, it is for the notes in those folders. Notes written before there was an index need no rebuild: they are indexed the first time todos are listed.

A todo with `every:` recurs: `every:2w`, `every:mon,thu`, `every:3d-after-done`, `every:last-fri` (`docs/todos.md` has every rule). `set_todo` takes `every` to set or clear it. Checking a recurring todo off, by `set_todo` or by a `write_note` that checks its box, leaves it open with its next due date and files the checked line on the daily note of the agent's member, and the answer's `filed` says the day and the note. Both take `on`, the day it is for the member; left out, it is today in the zone the member's `daily.timeZone` setting names, or in UTC. `todo_history` lists each time a recurring todo was checked off and by whom. `daily_note` finds or makes the member's daily note for a day.

A note is live, archived, or in Trash, and every listing of it says which as `state` (`docs/adr/0005-a-note-has-a-state-beside-its-access.md`). `archive_note` archives and unarchives. An archived note is left out of `list_notes`, `list_todos`, `todo_filters`, `list_tags` and `search` unless `includeArchived` is true, and is read and written as any note. `list_notes` and `search` also take `includeArchived: "only"`, for the archived notes alone. `trash_note` moves a note to Trash, where `list_trash` lists it with `purgesAt`, the time it is removed for good, 30 days on. Until then `read_note` reads it, every change to it is refused as a conflict, and `restore_note` brings it back as it was. `revert_author` with `trashEmptied` moves the notes it left empty to Trash. `list_notes` with `updatedSince` also reports a note whose state changed since, and each note has `stateAt`. A removed note reads as no such note, and a link to it has a null title, exactly as for a note that never existed.

`search` finds notes by their text: every word must be in the note, each matching the start of a word, ignoring case and accents. `"a phrase"` matches in order, `#tag` narrows to notes with that tag, `+project` to notes with a todo in that project. `folderId` narrows to the notes in one folder (not the folders inside it; a folder the agent can't see is no such folder), `hasTodos` to notes with an open todo, and `sort` orders the results: `match` (title matches first, then the latest changed; the default), `recent`, `created` or `title`. Each result has the note and the first lines that matched, with `marks` saying where in each line. `list_tags` lists the tags of the notes the agent can see with how many notes have each, and `list_notes` with `tag` lists the notes under one.

A member's calendar and contacts are data sources (`docs/adr/0006-data-sources-are-one-persons.md`). `list_sources` says which the member has and each one's `state` (`connected`, `needs_reconnect`, `not_connected`) and `writable`. `list_events` takes a span as two times and the `timeZone` whose days all-day events are matched by; an event's `when` is `{ allDay: false, from, to }` in milliseconds or `{ allDay: true, from, to }` with its first and last day. `update_event` takes the event's `sourceId`, `id` and `etag` as read and only the fields to change, and is refused with `conflict` when the event changed since, and with `forbidden` for an event whose `editable` is false. `list_contacts` lists contacts, narrowed by `query`. A note references a record with an embed that holds no copy of it: `refer_record` answers the `::event{<ref> <label>}` or `::contact{<ref> <label>}` to write, and `read_record` reads what a `ref` stands for now. The label is plain text in the note, which every reader sees. The ref leads to the record only for the member who made it.

Most clients take a URL and a header:

    claude mcp add --transport http common-ink https://commonink.app/mcp --header "Authorization: Bearer $INK_TOKEN"
